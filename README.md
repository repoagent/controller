# RepoAgent

RepoAgent connects GitHub conversations to agent sessions. Its CLI, `RepoAgentController`, forwards observed activity; the agent replies through normal tools under a GitHub App installation identity. Discussions are the first supported interface; the name leaves room for issues and pull requests.

## Start here

- [Minimal PoC — issue #2](https://github.com/repoagent/controller/issues/2): the implementation starting point, with manual verification.
- [Full specification — issue #1](https://github.com/repoagent/controller/issues/1): broader design reference. The PoC's smaller scope takes precedence for the initial build.
- [Flows, payloads and session instructions](https://github.com/repoagent/controller/issues/2#issuecomment-6276915447).
- [Maintainer authentication-service deployment](docs/azure-auth-deployment.md): Bicep/OIDC setup and continuous deployment of the broker API and cleanup service from `main`.
- [Azure controller setup](infra/controller/README.md): public GHCR image, private persistent storage and a dedicated controller resource group, without ACR; includes cloud sign-in and the first-activation handover procedure.
- [Operate StoryBeam](docs/storybeam-operations.md): the selected lean app, private update/recovery directory, idle scaling and retained data.

The PoC uses one native Codex session per Discussion, a small JSON mapping/checkpoint, GraphQL observation, an ordinary skill plus `gh` for replies, and timestamped stdout logging. After the native harness accepts input, the bridge adds 👀 to the forwarded source Discussion, comment or reply.

Each bridge process monitors one configured repository. Specifications and tickets live in this repository's GitHub Issues.

## Run RepoAgent

For guided shared-App setup, use [PowerShell 7.4+ local installation](docs/local-installation.md): `.\install.ps1 -Repository owner/repo -BrokerOrigin https://broker.example.org -Instance example -Clone -NonInteractive` previews the plan; add `-Apply` to enroll and start. `-Clone` selects repository context with fresh Contents-read approval and exact-root native trust; omit it for the ordinary no-context path. It reuses host `gh` and existing Codex sign-in, persists choices per instance and supports explicit own-App mode. Windows uses Docker Desktop Linux containers directly; WSL is optional. Bash `./install.sh` retains its existing own-App setup. See [installation, skills and storage](docs/container-setup.md) and the [executable acceptance catalog](docs/acceptance-cases.md). For event-triggered operation behind your own HTTPS ingress, see [fixed-URL webhooks](docs/webhooks.md).

For an already-issued frozen broker enrollment, use the [PowerShell 7 local runtime](docs/local-runtime.md). It imports the private file into owned Linux storage and pins the selected image without requiring an App PEM.

PowerShell also supports [inspecting or withdrawing legacy Environment approval](docs/repository-approval.md) using host `gh`, without Docker or a controller credential. The [repository Actions-variable provider](service/auth/README.md#repository-actions-variable-enrollment-v3) ([#184](https://github.com/repoagent/controller/issues/184)) implements v3 setup and markers. The [Agent-variable v2 provider](service/auth/README.md#repository-agent-variable-enrollment-v2) from [#68](https://github.com/repoagent/controller/issues/68) remains an explicit legacy location, and controller files and runtime are unchanged. The [guided installer](docs/local-installation.md) composes the delivered controller enrollment and private-runtime commands; legacy Environment revoke remains separate. Live GitHub, Azure and native Windows acceptance remain required before reporting the assembled service as available.

After installation, inspect or change nonsecret [repository settings](docs/repository-settings.md) in `REPOAGENT_*` Actions variables with `./install.ps1 -Action Settings`. The controller reads them only with `--repository-settings` and an App installation that grants Variables: read. Broker-enrolled controllers also need a controller enrollment with an explicit [repository-settings profile](docs/repository-settings.md#broker-enrollments) (`-RepositorySettings`); existing controller enrollments are never widened.

> [!WARNING]
> Repository Actions variables must never hold secrets. A controller that reads repository settings, and so the agent it runs, can read every direct repository Actions variable, not only `REPOAGENT_*` settings ([ADR 0008](docs/adr/0008-add-an-explicit-repository-settings-runtime-profile.md)).

For local development without a public hostname, select [Quick Tunnel mode](docs/quick-tunnel.md).

Run the bridge in a Linux container containing `gh` and `codex`. The packaged bridge is Native AOT compiled and needs no installed .NET runtime. Native Codex uses its normal sign-in. GitHub access uses an installed GitHub App with **Discussions: read/write** and a read-only mounted PEM signing key. An agent GitHub-user login is unnecessary. Container bootstrap and live verification are tracked in [#5](https://github.com/repoagent/controller/issues/5).

Pass these arguments to the bridge **inside the configured container**:

```text
RepoAgentController --repo repoagent/controller --app-id APP_ID_OR_CLIENT_ID --mention-user repoagent \
--private-key /run/secrets/github-app.pem --workspace /workspace \
--state /data/bridge-state.json
```

The bridge discovers the App's installation for the configured repository; `--installation-id` optionally checks a specific expected installation. It verifies the token's actual `viewer.login` matches the App bot before starting Codex. Use `--check-auth` to check App credentials and prepare its `gh` wrapper without starting an agent session. See [App setup, token renewal and verification](docs/github-app-auth.md).

Mention the bot's actual login, such as `@repo-agent-connector[bot]`, in a Discussion body/comment/reply, or add `--enroll https://github.com/OWNER/REPO/discussions/123` (repeatable). Discussion enrollment uses literal polled text and does not require GitHub mention notifications or autocomplete. An explicitly enrolled URL persists in the state file and need not be repeated. With [repository settings](docs/repository-settings.md) enabled, `REPOAGENT_ENROLLMENT_CATEGORIES` also enrolls Discussions created in selected categories without a mention; see [category enrollment](docs/repository-settings.md#category-enrollment) for how preexisting Discussions are treated. Each Discussion gets one native Codex session across all comment threads. The default polling interval is ten seconds after each completed poll; every connection is paginated, so large repositories may take longer. Only observed versions are forwarded; changes reverted between polls can be missed.

Each turn states its Codex model and reasoning effort explicitly. A Discussion label `repoagent:<model>:<reasoning>`, such as `repoagent:sol6.1:xhigh`, selects them for that Discussion's next turn. Without such a label, the repository defaults `REPOAGENT_MODEL` and `REPOAGENT_REASONING` apply, then the native Codex configuration, then the model catalogue's default. Adding, changing or removing a label never starts a turn and never steers active work. Conflicting labels, malformed labels and values the Codex account does not offer are never substituted: the input waits and a `selection-error` names the problem. See [model and reasoning selection](docs/repository-settings.md#model-and-reasoning-selection).

Add `--mention-user repoagent` to enroll through the dedicated `@repoagent` account. Startup verifies that the configured user exists; Discussion enrollment recognizes GitHub-rendered mentions, including emphasized mentions, while profile links, code examples and email addresses stay inactive. The App still authors replies and EYES; the mention account needs no runtime login or token. See [mention-account setup](docs/github-app-auth.md#dedicated-mention-account) for repository access and autocomplete eligibility. Native agent registration remains a separate integration.

The response skill is copied beside the executable and injected through Codex's native skill input. Additional skills and workspace guidance load normally. Agent sessions receive the absolute path to an authenticated `gh` wrapper, which reads renewed credentials for every command. The native process inherits neither a static GitHub token nor the operator's GitHub-user token/configuration. Choose a Codex configuration whose normal tool permissions allow the agent's intended work and network access for `gh` publication. The bridge preserves those permissions and has no approval UI: interactive approval/input requests are logged and rejected for operator attention. Participant clarification questions should be published to GitHub by the response skill.

Logs go to timestamped stdout. Keep the process running for agent work and future activity. Ctrl+C stops the process. `--once` is an observation/acceptance check, **not a complete conversation run**: it exits after one poll and can interrupt unfinished agent work. Native acceptance means the input reached Codex, not that the answer finished. On normal restart, reuse the same state file and Codex sign-in/storage; the next change resumes the recorded session and its native history.

### Supplied Codex credentials

`--codex-auth FILE` supplies the Codex account credentials (an `auth.json` holding an API key or ChatGPT sign-in tokens), separately from the GitHub App credentials. It requires an explicit private `CODEX_HOME`. Startup validates the file before any GitHub or Codex use and installs it as the native home's `auth.json` only when its content differs from the last supply, so a restart keeps tokens Codex itself refreshed. The owned app-server then uses file credential storage.

Replace the file to change credentials while the controller runs; replace it atomically (write beside it, then rename). The pinned Codex (0.163.0) has no supported reload of a replaced `auth.json`: a running app-server keeps its loaded account. `account/read` with `refreshToken` adopts only a same-account ChatGPT file, `account/login/start` covers API keys only, and external `chatgptAuthTokens` are marked internal. The controller therefore checks the file every five seconds and, when no accepted turn is running (and in clone mode, no repository refresh is in progress), installs the replacement and restarts only its owned app-server. A running turn is never interrupted; the replacement applies before the next input. Each session resumes its recorded agent session and history on its next input. An unusable replacement is logged and the current credentials stay in use. If the restart itself fails, the controller stops.

A turn whose credentials are rejected (`401`/`unauthorized`) logs `codex-auth-failed` with what to do. New Discussion input then stays in the controller's waiting queue (`input-held`), without a turn or EYES receipt, and is dispatched once replacement credentials are applied. The rejected turn's own input goes back to the front of that queue (`input-requeued`) and is sent again, marked as a [redelivery](#checkpoints-and-manual-recovery), with the replacement credentials. Held input never counts as processed work.

## Status and retained logs

`RepoAgentController status --state PATH` prints the controller's current status as JSON, for a running or stopped controller, without taking its lease or requiring you to read checkpoint files. It reports the repository and App actor, controller lifetime (`starting`, `running`, `stopped` or `failed`, with mode and timestamps), authentication health (`healthy`, `failed` with its error, or `unknown`), Codex account authentication as `codexAuthentication` (`supplied` after `--codex-auth` is installed or applied, `healthy` after a turn completes, `failed` with its error, or `unknown`), per-Discussion sessions, work counts and up to 20 recent failures with their log kind and time, plus the latest forwarded activity and each [repository setting](docs/repository-settings.md)'s latest observation (`settings`: state, effective value and the reason it is invalid or unreadable). A session is `pending` while a native delivery attempt is in flight, or was interrupted by a stop until the next start retries it; `retrying`, with `attempts` and `retryAt`, after a failed or unacknowledged delivery (see [redelivery](#checkpoints-and-manual-recovery)); `running`, with the turn's start as `since`, while an agent turn runs; otherwise `idle`. `work` counts stored sessions, pending, retrying and waiting input, and `running` turns against `limit`, the effective [active-session limit](docs/repository-settings.md#active-session-limit). A stopped controller reports no running turns. `running` controller state without a later stop means the last recorded lifetime; an abrupt kill cannot record its own end.

### Status endpoint

A running controller also serves `GET /status` on a local port, in polling and webhook mode. `--status-port` selects it (default 8081); it listens on loopback only and must differ from `--listen-port`. The answer is `busy` while an agent turn runs or input is pending, retrying or waiting, otherwise `idle`, with the `work` counts of `status` above (`admissionBlocked` is `true` while a managed checkout refresh holds new turns, and `null` without a managed clone):

```json
{"state":"busy","work":{"sessions":1,"pending":0,"retrying":0,"waiting":0,"running":1,"limit":4,"admissionBlocked":null}}
```

It returns nothing else: no Discussion URLs, sessions, failures, logs or credentials. The controller does not act on it. A hosting environment that must not stop a busy controller, such as one that scales to zero, reads it ([ADR 0009](docs/adr/0009-keep-hosting-lifecycle-out-of-the-controller.md)); nothing reads it yet. In a container it is reachable inside the container's network, for example from a sidecar, and the container runtime publishes no port for it. The container runtime uses 8081, or 8082 when its listener port is configured as 8081. `--once`, `--check-auth` and `--disable-webhook` serve no endpoint.

The lease holder also appends every stdout line to retained logs in `PATH.logs/`, so they survive restart and container replacement. `--log-file-bytes` (default 1 MiB, 1 KiB to 1 GiB) bounds each file and `--log-files` (default 5, at most 100) bounds the count, including the active `controller.log`. Retained logs never exceed their product (5 MiB by default); rotation deletes the oldest file. At startup a lower setting removes surplus and oversized rotated files and keeps only the newest whole lines of an oversized active file. `RepoAgentController logs --state PATH` prints them oldest first. Stdout is unchanged.

Status and retained logs use the same redacted entries, so every reported failure has a log entry with the same time, kind and message (status truncates messages beyond 2000 characters), correlated by Discussion URL and session ID. Tokens, controller secrets and webhook secrets are redacted. Agent turn events are reduced to thread, turn, status and error text, so transcript items are not logged; Discussion bodies are not logged. Status (`PATH.status.json`) and logs are owner-only files beside the state.

### Discussion status dashboard

`--dashboard-category "NAME"` (container: `configure --dashboard-category "NAME"`; an empty value removes it) publishes the same status to a controller-owned Discussion in that existing category, so participants can see it without host access. Create the category first; the App needs only its existing **Discussions: read/write**. The controller creates the Discussion once and finds it again after restart; it is recognised by the App's own authorship plus the hidden `<!-- repoagent:controller-dashboard -->` marker, so a participant's copy stays an ordinary Discussion. The dashboard itself is never agent input: mentions, comments, `--enroll` of its URL and its webhook deliveries are all ignored.

The body shows the controller state with its start time, or the time of a handled graceful or failed stop; GitHub App and Codex account authentication health; session counts and running turns against the active-session limit; active and queued sessions, each with its running turn's start and why its input waits (for that turn, for a free active-session slot, for replacement Codex account credentials, or for dispatch); recent failures; and the latest forwarded Discussion or comment as a link with its time. A separate heartbeat is refreshed about every 30 seconds while the controller runs, even when idle. An abrupt kill cannot report its own end, so it leaves the last heartbeat aging rather than a stop: treat an old heartbeat as unconfirmed status. A failed authentication refresh, or Codex account credentials rejected at the model provider (`codexAuthentication` `failed`, which holds new input), changes the title to `Attention: RepoAgent controller authentication failed` while GitHub writes still work (a lost broker credential cannot publish anything); it returns to `RepoAgent controller status` on recovery. Error text is the same redacted text as status and logs.

An **Updates** section compares the controller's image with the [baseline releases](docs/ci-cd.md#baseline-releases) published in `repoagent/controller`. The controller reads them with its App credential at startup and about hourly; GitHub's **Latest** badge is ignored. `--image-inventory FILE` names the running image's inventory: the container runtime passes `/opt/repoagent/image-inventory.json`, and its SHA-256 identifies the release that published the image. When a newer release exists, the section shows one **Update available** notice for the newest release only, with the number of newer releases, links to the release and the GHCR package, the immutable image reference and its gh and Codex versions. Publication is not deployment. The controller never replaces itself and has no Docker host access, so an operator recreates the controller from that image, or rebuilds a derived image on it; external configuration, credentials and session volumes are kept. The section instead reports **Release identity uncertain**, and suggests no replacement, when:
- no inventory is given (a native or development run);
- the inventory matches none of the 100 newest published releases (a derived, local, unreleased or much older image);
- `--startup-tool-updates` is set. The runtime passes this flag for `--tool-updates latest`, because tools updated at startup may differ from every release.

An image built `FROM` a baseline image without changing its inventory still matches that release. A failed release read is shown with its time and error, and claims neither "current" nor "update available" until a later check succeeds.

Updates use the retained outbox above with one coalesced entry, so writes held back by a rate limit or outage are replaced by the latest status, which is written once when GitHub allows it. A missing category or a permission or validation error is logged once as a permanent `dashboard-error`, and dashboard updates stop until the controller restarts; the dashboard never affects Discussion work. If you delete the dashboard Discussion, restart the controller to recreate it.

## Checkpoints and manual recovery

One JSON file holds the repository/bot binding, session IDs and last accepted content/reaction versions. An adjacent `.lock` file prevents concurrent writers for that state file; keep one bridge per repository/App. A private adjacent `.github-app` directory holds the short-lived credential, isolated `gh` configuration and native command wrapper. Persist this directory with the state volume and keep it out of source control. Signing keys and tokens are never stored in the conversation checkpoint. Use a fresh state file when switching from a user identity to an App; the bridge rejects a mismatched identity instead of silently replaying or migrating old conversations. Codex retains conversation history itself.

Observed changes wait in the Discussion record's `waiting.inputs`, in order and with their authors and receipt source; recording them advances the source checkpoint. The bridge never adds input to a running turn. It dispatches only when Codex reports that Discussion's session `idle`, or `systemError` after a failed turn: pinned Codex keeps that status until the session's next turn and accepts that turn, so no restart is needed. While a turn is active, or while status is unknown, changes wait and get no EYES (`input-waiting`). A restarted native process first resumes the session and uses its reported status. Each dispatch starts one new agent turn with the next ordered batch: at most 256 KiB of envelope, or one larger change sent alone, never dropped. The rest waits for the next idle report. Dispatch also waits while the [active-session limit](docs/repository-settings.md#active-session-limit) is reached: `REPOAGENT_MAX_ACTIVE_SESSIONS`, default 4 running agent turns per controller. Idle stored sessions do not count. The first (bootstrap) envelope carries the Discussion and its existing comments once. Its context holds at most 128 KiB of existing comments, the earliest first; when a long Discussion has more, `context.laterComments` counts them and their changes carry their bodies, splitting into later batches like other input, so no envelope reaches the agent input limit. Later envelopes name the Discussion once and carry only each change's subject ID, author, new or edited body, changed Discussion fields or reaction actor, and reply target; unchanged Discussion and parent bodies are left for the agent's history or `gh`. A checkpointed comment or reply missing from a complete observation is reported once as `comment.deleted`, with its ID, author and thread but no body or EYES; any failed page fails the whole observation, so the checkpoint stays and nothing is inferred deleted.

Before creating a session or sending a batch the bridge persists `pending`, including its `inputs` count. Only native acknowledgement removes those inputs and clears the marker. A failed or unacknowledged delivery does not stop the Discussion. This covers a native error, the 60-second native request deadline, transport loss, and a stop or crash before acknowledgement. The batch stays first in line, `waiting.retry` records the attempt, and a `delivery-retry` line names the sources and the reason. The next attempt waits for an idle session and a backoff of 5 seconds, doubling to 5 minutes, with no attempt limit; a `pending` left by a stopped controller is retried at the next start. Input that a `turn/start` carried is marked `redelivery` in `waiting.inputs`, because Codex may have accepted it without acknowledging. It is sent again in a batch of its own, with `_bridge.redelivery: true` in the envelope. The agent checks its history and the target thread before repeating work. Duplicate processing is accepted: the bridge does not search transcripts or promise exactly-once input. In clone mode, an unacknowledged input keeps the managed checkout excluded until an acknowledged turn of that session completes. Failed or uncertain input receives no EYES until a delivery of it is acknowledged. After acceptance the bridge checkpoints **before** queuing or reusing EYES on every source in that batch. Controller-owned GitHub writes, currently EYES receipts and [dashboard](#discussion-status-dashboard) updates, are retained in the adjacent `.outbox` file until they succeed or fail permanently, including across restarts; retrying them never resends accepted input. Transient failures back off from 15 seconds to 15 minutes. Rate limits (`Retry-After`, an exhausted `X-RateLimit-Remaining` until `X-RateLimit-Reset`, or GraphQL `RATE_LIMITED`) pause every retained operation until GitHub's signalled time, or at least one minute. A 5xx, timeout or other unconfirmed outcome is reconciled by reading the App's actual reaction before writing again. Permissions, validation and missing subjects (HTTP 400/403/404/410/422 or GraphQL `FORBIDDEN`/`NOT_FOUND`/`UNPROCESSABLE`) are logged as permanent `receipt-error` lines with the source URL and subject ID, then removed from retry. A later operation for the same subject supersedes a still-pending one. `--once` attempts due operations once and exits nonzero while any remain retained. Receipts are excluded from wake triggers; agent replies still use the agent's own gh.

Input the native keeps refusing keeps retrying at the longest backoff and holds that Discussion's later input; other Discussions continue. Examples are a session ID that Codex no longer knows, or a single change above its input limit. Inspect the `delivery-retry` reason and the agent session (`codex resume SESSION_ID`, using the same Codex profile). To abandon such input, stop the bridge and back up the state. Then remove the offending entries from the front of `waiting.inputs`, or remove the Discussion record to enroll it again. In clone mode the refresh journal still blocks a restart after an interrupted or unacknowledged native admission; see [managed checkout recovery](docs/local-installation.md#own-app-mode-and-acceptance). Crash-proof exactly-once input or publication is outside this prototype.

See [manual verification](docs/manual-verification.md) for the acceptance gate.

## Containerized authentication checks

```sh
docker build -f tests/Containerfile -t repoagent-controller-tests .
docker run --rm repoagent-controller-tests
```

These focused xUnit tests exercise real RSA signing, private credential files and child-command dispatch with controlled HTTP responses/time. They verify renewal, expiry and failure isolation; they do not prove real App permissions or native Codex compatibility. The separate live checks in the [App guide](docs/github-app-auth.md) provide that evidence.

### Shared-App controller enrollment

PowerShell 7.4+ can create approval in one direct repository Actions variable (default `REPOAGENT_APPROVAL`) and obtain a private shared-App enrollment through `install.ps1 -Action Enroll`, using separate authenticated host `gh`. See [host setup, recovery and revoke](docs/host-enrollment.md). Use the [guided local installer](docs/local-installation.md) to compose enrollment with Docker startup. Azure setup and live broker acceptance remain separate gates.
