# Use repository Actions variables for approval

Superseded in part on 2026-10-26 by [ADR 0012](0012-use-repository-agent-variables-for-settings-and-approval.md): repository settings and fresh approval live in direct repository Agent variables (setup v4), and Actions-variable setup v3 is retired. The invariants below still apply.

Accepted on 2026-10-23. Supersedes only the repository Agent-variable location in [ADR 0006](0006-use-repository-agent-variables-for-approval.md): fresh enrollment approval is a direct repository Actions variable, next to the ordinary nonsecret `REPOAGENT_` repository settings. Everything else from ADR 0003 and 0006 stays: UI-free controller approval, writer authority that GitHub permits (no named-human or admin attestation), separate private possession, durable observed closure, and the existing token, recovery and old-authority barriers.

The host writes the marker with its own GitHub authority. The broker verifies it with a broker-only internal verifier that has exactly `actions_variables: read` (implicit metadata only), and reads the selected variable by name only from the direct `/repos/{owner}/{repo}/actions/variables` location. Organization and inherited variables never substitute. Runtime tokens get no variables, secrets, environments or workflow access, so a controller cannot write or restore its own approval. ([ADR 0008](0008-add-an-explicit-repository-settings-runtime-profile.md) adds variables read, never write, for explicitly enrolled repository-settings profiles only.) The broker-issued controller secret stays in the private host and controller files and is never stored in a repository variable.

Actions-variable approval is a new explicit kind: `repository-actions-variable`, setup version 3, policies `repository-actions-approval-v3` and `repository-actions-clone-approval-v3`, under the `/v3` setup routes. Agent-variable v2 and Environment v1 grants keep working, with their kinds unchanged. The broker never reinterprets them, and the installer never overwrites or migrates a live marker on its own. Migration is deliberate: revoke and settle the old grant, then do a fresh v3 enrollment. A repository still has one owner gate, so v3 completion is refused while a v2 owner is active. To roll back, explicitly select `-ApprovalLocation AgentVariable` for a fresh enrollment. A broker that does not know v3 fails closed on v3 rows.

[#184](https://github.com/repoagent/controller/issues/184) implements this. Still open as release gates: live installation-permission acceptance of `actions_variables: read` on the shared App, private-repository availability, and native Windows acceptance. See [the approval contract](../auth-repository-approval.md) and [the provider contract](../../service/auth/README.md#repository-actions-variable-enrollment-v3).
