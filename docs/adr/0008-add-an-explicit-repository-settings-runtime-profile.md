# Add an explicit repository-settings runtime profile

Superseded in part on 2026-10-26 by [ADR 0012](0012-use-repository-agent-variables-for-settings-and-approval.md): the repository-settings profiles grant `agent_variables: read` under setup v4, and v3 settings enrollments are retired. The explicit, separately enrolled profile family below still applies.

Accepted on 2026-10-23. Supersedes, for the explicitly selected repository-settings profiles only, the sentence in [ADR 0007](0007-use-repository-actions-variables-for-approval.md) that runtime tokens get no variables access. Everything else from ADR 0007 stays.

Broker-enrolled controllers need to read [repository settings](../repository-settings.md), which live in direct repository Actions variables. Existing broker profiles are frozen: their approvals bound exact grants, so adding `actions_variables: read` to them would silently widen authority that an approver never saw. Instead, a new family of profiles (`polling-settings`, `webhook-settings`, `polling-clone-settings`, `webhook-clone-settings`) grants exactly its frozen counterpart's permissions plus `actions_variables: read`, under the single policy `repository-actions-settings-approval-v3`. It is available only with Actions-variable approval (setup v3) and uses its own runtime protocol version 3 (file, lease, `POST /v3/devices/{id}/installation-token` and `DELETE /v3/devices/{id}`). The approval marker names the profile, so an approver sees the grant before it exists. The controller must be started with `--repository-settings` to consume a v3 file, and it refuses that flag with v1 and v2 files before contacting the broker. An existing controller moves to this family only by revocation, settlement and a fresh enrollment. Rollback is a fresh enrollment with a frozen profile.

The runtime token stays read-only for variables. The controller still cannot write, restore or forge its approval marker, and the broker's verifier remains a separate internal capability. One accepted consequence is that a settings controller, and so the agent it runs, can read every direct repository Actions variable, including the nonsecret approval marker and any unrelated variables. Operators must keep secrets out of repository variables, which ADR 0007 already requires for the marker. The considered alternatives were widening the frozen profiles (rejected: it reinterprets existing approvals), a flag on the existing v1 and v2 runtime routes (rejected: old brokers and controllers would not fail closed), and a broker-side settings proxy (rejected: more broker surface for nonsecret data).

[#196](https://github.com/repoagent/controller/issues/196) implements this. Still open as release gates: live installation acceptance of **Variables: read** on the shared App, a deployed broker that serves runtime v3, and native Windows acceptance. See [the consumer contract](../broker-protocol.md#explicit-repository-settings-consumer-v3).
