# Use repository Agent variables for settings and approval

Accepted on 2026-10-26. Supersedes the direct repository Actions-variable location of repository settings and of fresh approval in [ADR 0007](0007-use-repository-actions-variables-for-approval.md), and the `actions_variables: read` grant of the repository-settings profiles in [ADR 0008](0008-add-an-explicit-repository-settings-runtime-profile.md). Every invariant from ADR 0003, 0006, 0007 and 0008 stays: UI-free controller approval, writer authority that GitHub permits (no named-human or admin attestation), separate private possession, durable observed closure, the token, recovery and old-authority barriers, frozen profiles that never widen, runtime tokens that never write variables, and a broker-only verifier.

Every `REPOAGENT_*` repository setting and the default approval marker `REPOAGENT_APPROVAL` live in direct repository Agent variables (`/repos/{owner}/{repo}/agents/variables`, shown under **Settings > Secrets and variables > Agents**). The names keep the `REPOAGENT_` prefix. Organization and inherited Agent variables never substitute. This keeps RepoAgent configuration out of the store that CI workflows read as `vars.*`, so a settings controller no longer reads CI configuration. The shared App already declares **Agent variables: read**. It has never declared **Variables: read**, so no Actions-variable (v3) approval has ever completed on it.

## Setup v4

Setup version 4 is Agent-variable approval with every profile. It keeps the approval kind `repository-agent-variable`, because the kind names the location, which v2 already uses. Its routes are `/v4/enrollments`, `/v4/enrollments/{id}`, `/v4/enrollments/{id}/completion` and `/v4/devices/{id}/acknowledgment`, with the v2 bodies. Its marker has the v2 property order with `"version":4`. Its policies are `repository-agent-approval-v4`, `repository-agent-clone-approval-v4` and `repository-agent-settings-approval-v4`. The verifier has exactly `agent_variables: read`. The four `*-settings` profiles grant exactly their frozen counterpart plus `agent_variables: read`, and the frozen profiles grant no variables access.

The runtime versions do not change: v1 for `polling` and `webhook`, v2 for the clone profiles, v3 for the settings profiles. The v2 and v3 files and leases repeat the policy, which names the variables store. The v1 file and lease stay policy-free and unchanged, and their profiles grant no variables access. The broker binds every enrollment's policy durably and derives runtime authority from that policy and the profile together, never from the profile name alone. A broker without v4 fails closed: it has no `/v4` setup routes and denies a v4 row. An older controller refuses a v4 clone or settings file because it does not know the policy.

Fresh enrollments through the installer and `enroll-controller.ps1` use v4 with `REPOAGENT_APPROVAL`, and they no longer offer setup v2 or v3. RepoAgent is unannounced, so v3 is retired rather than kept for deployments that do not exist: the controller refuses a v3 settings enrollment file at startup and names re-enrollment, and the broker may drop the v3 setup family. Existing v2 grants keep their kind, setup version, policy and runtime authority, and they keep renewing until revoked; saved installer state still revokes them. One owner gate still serves each repository. A controller moves to v4 only by revocation, settlement and a fresh enrollment in a new state directory.

## Controller and Settings script

A controller reads settings only from Agent variables, with a v4 settings enrollment or in direct-App mode. In direct-App mode the token requests `agent_variables: read`, never write. If the installation does not grant it, the controller does not request it and reports every setting as unreadable, keeping the last effective values, instead of refusing to start. The controller never reads Actions variables, also not after a failed read or a 404.

The Settings script reads and writes Agent variables. Its move action moves each catalogue setting from Actions variables: it reads the Actions value, writes the Agent variable, reads it back, then deletes the Actions variable. It never touches names outside the catalogue or reserved names, and it refuses to overwrite a different Agent value. Because nothing falls back, upgrade a direct-App controller in this order: stop it, move the settings, then start the new version. A controller that starts before the move sees its settings as absent and applies the defaults.

## Consequences

GitHub documents that Copilot cloud agent has "its own dedicated **Agents** secrets and variables", and that "Variables and secrets that you configure are exposed to Copilot as environment variables" ([Configure secrets and variables for Copilot cloud agent](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/configure-secrets-and-variables)). Every `REPOAGENT_*` setting and Agent-variable approval marker therefore reaches any Copilot cloud agent session in the repository. They are nonsecret, so this is accepted. In turn, a settings controller and the agent it runs can read every direct repository Agent variable, including the approval marker and variables set for Copilot. Agent variables must never hold secrets; GitHub's Agent secrets are a separate store that RepoAgent never reads. An organization Agent variable with a `REPOAGENT_` name reaches Copilot but never the controller.

The shared App needs no permission change. Each installation's acceptance of **Agent variables: read**, a live probe of a v4 settings token on a selected repository, and native Windows acceptance remain release gates. A direct-App operator's own App needs **Agent variables: read** instead of **Variables: read**.

The considered alternatives were keeping Actions variables (rejected: the owner moved both), a controller that reads Actions variables when an Agent variable is missing (rejected: two sources of truth with no defined winner), keeping v3 settings controllers on Actions variables (rejected: no such deployment exists, and it keeps a second store in the controller), adding settings profiles to setup v2 (rejected: it reinterprets the v2 setup contract), and new runtime v4 routes (rejected: more broker surface, while the policy already distinguishes the store and older controllers refuse it).

[#240](https://github.com/repoagent/controller/issues/240) implements this.
