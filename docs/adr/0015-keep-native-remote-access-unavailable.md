# Keep native remote access unavailable until both safety boundaries qualify

> Superseded on 2026-10-31 by [ADR 0016](0016-trust-container-owner-for-native-remote-access.md). This records the earlier unavailable-only implementation, which does not satisfy the clarified owner-access requirement.

Accepted on 2026-10-30 for [#335](https://github.com/repoagent/controller/issues/335), implementing the unavailable alternative in [ADR 0014](0014-unify-local-commands-and-private-authorization.md). The controller refuses every native remote operation until agent-tool isolation and preexecution admission of native commands can both be established. This does not provide supported native remote access; [#332](https://github.com/repoagent/controller/issues/332) remains open for enablement and real acceptance.

## Concrete current process arrangement

`container/Containerfile` runs the controller as UID 1000. Its `Codex.Transport` starts the supervised app-server with that same identity; agent tools inherit it. The container makes `/data/state`, `/data/config`, `/data/credentials/codex`, `/data/control`, the workspace and home writable by UID 1000. `container/runtime.py` selects `approval_policy="never"`, `sandbox_mode="danger-full-access"` and file credentials. Native deployment likewise starts the runtime with the controller's identity. Neither arrangement establishes an OS boundary between tools and administration authority.

Private socket permissions and peer authentication can identify callers, but cannot make this shared identity an administrator safely. Tools can potentially reach shared configuration, account credentials, same-identity process state or an alternate runtime. Environment sanitization and the bounded GitHub credential handoff do not establish administrative isolation. No blanket same-UID administration is granted. Host root and equivalent container administration remain trusted.

## Pinned provider blocker and startup refusal

The image pins Codex 0.166.0. Its [remote client tracker](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server-transport/src/transport/remote_control/client_tracker.rs) forwards incoming requests to the provider dispatcher. The [message processor](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/src/message_processor.rs) dispatches `turn/start` and other mutations internally, bypassing RepoAgent's admission path. The provider's [connection RPC gate](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/src/connection_rpc_gate.rs) handles connection/drain admission, not the controller's active-session limit or checkout exclusion. Source inspection found no supported external preexecution veto or enforced read-only remote permission. Separate controller/runtime UIDs alone would not repair that bypass.

The provider's [runtime defaults](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/src/lib.rs) resolve persisted remote intent. Therefore every controller-owned launch sets `CODEX_INTERNAL_APP_SERVER_REMOTE_CONTROL_DISABLED=1`, overriding inherited values. The pinned [CLI startup](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/cli/src/main.rs) consumes this marker and selects `DisabledEphemeral` when `--remote-control` is absent. Our launch never supplies that flag. The single transport constructor covers initial startup, trust bootstrap and replacement/restart.

This is a startup guard for the owned process, not protection against same-identity tools launching another runtime, a rewrite of persisted provider preferences, proof of revocation or a current provider observation. The controller invokes no experimental remote APIs. Keep the existing unmatched agent lifecycle invariant in `CheckoutRefresh`: remote-originated execution must be prevented before execution, never accommodated by ignoring an unknown turn afterward.

## Application contract and remaining qualification

The core accepts only named enable, pair, status, clients, revoke and disable operations and a permission derived by a trusted adapter. Inspection-only, absent and unknown permissions are forbidden before protected state/runtime access; unknown operations are forbidden even to administrators. Recognized administrator operations return sanitized unavailability, explicitly leaving current access and revocation unconfirmed. The gate has no persistence/runtime dependencies and cannot record enabled intent, issue pairing authority or inspect client inventory. A dormant remote orchestration stack would imply behavior that cannot safely run, so it is deferred.

[Qualification evidence and remaining acceptance](../native-remote-qualification.md) distinguish core/source checks from real OS/provider acceptance. Future support requires an OS boundary protecting control channels, credentials, configuration, process state and handles from agent tools, together with provider-supported preexecution command admission, followed by the real shared Aspire and desktop journey in #332. Until then local activity inspection remains independent and native remote administration remains unavailable.
