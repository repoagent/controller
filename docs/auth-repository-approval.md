# Repository-held approval and a UI-free auth service

Approved by the maintainer on 2026-10-20. This replaces broker-hosted administrator browser approval, broker human OAuth/cookie/CSRF/PKCE flows, and continuing authorization tied to a particular approving person. The current storage decision is [ADR 0006](adr/0006-use-repository-agent-variables-for-approval.md): direct repository Agent variables replace GitHub Environments. This is a design contract. Merged [#52](https://github.com/repoagent/controller/issues/52) implements the legacy Environment provider; Agent-variable [provider #68](https://github.com/repoagent/controller/issues/68) and [host #53](https://github.com/repoagent/controller/issues/53) remain pending. Draft PR #67 is an unmerged Environment host prototype. No new setup/marker wire version has been chosen; require an explicit reviewed discriminator before implementation and never reinterpret legacy markers. Canonical delivery parents are [#30](https://github.com/repoagent/controller/issues/30) and [#31](https://github.com/repoagent/controller/issues/31).

## Authority and credentials

The GitHub App must be installed with access to the target repository before enrollment. The installer uses the operator's separately authenticated host GitHub authority to create or safely reuse the selected direct repository Agent variable. GitHub authenticates that setup authority; the broker hosts no user login, browser approval, device-login ceremony or administrator dashboard.

Approval authority means a principal GitHub permits to manage the selected variable; the marker does not attest a particular human administrator or required deployment reviewer. The approval belongs to the repository, not to the person running setup. Their later departure or personal OAuth-consent withdrawal does not revoke it. A human identity may appear in an audit record but is not a continuing grant condition. GitHub App uninstall, loss of repository/required permissions, missing or changed approval, explicit device revocation, expiry or recovery-epoch mismatch deny further issuance.

The marker is nonsecret. It binds a broker-issued pending controller ID and fresh challenge/fingerprint to the immutable GitHub host, numeric repository/App/installation IDs, exact server-defined permission profile, authorization-policy version, external restore epoch and chosen marker coordinates. Readable binding information must let the operator assess the requested grant before writing it. The controller must separately prove possession of its private pending/device credential; reading or copying a public marker is insufficient. The broker validates the marker against its stored pending request, not client-supplied authority claims.

The broker reads `/repos/{owner}/{repo}/agents/variables/{name}` directly through GitHub, with TLS, fixed GitHub host, bounded freshness and no client-supplied screenshots or cached copies as authorization. Only direct repository Agent variables authorize; organization or inherited variables cannot substitute. The host needs GitHub-authorized Agent variables write access. The internal exact-repository verifier requests Agent variables read (`agent_variables:read`), subject to live installation-scope proof. Neither GitHub Environment creation nor an Environment name, numeric identity or deployment setting is required. Controller runtime installation tokens retain the frozen v1 polling/webhook profiles; no approval-variable read/write permissions, host GitHub credentials or App PEM are delegated to them. Account for internally minted verification tokens as well as returned runtime tokens.

## Installer setup and names

The MVP targets PowerShell 7 / `install.ps1`, with planned `install`, `revoke` and `uninstall` actions and a user-selectable repository Agent-variable name. Bash parity and a .NET/native installer are deferred; the existing [exact-value revocation tool](repository-approval.md) still targets legacy Environments. `APPROVED_CONTROLLER` is the suggested variable name. Keep this input separate from Azure Container Apps environment selection and the native Discussion-enrollment option.

Arguments fill answers; interactive mode prompts for missing values and previews the exact repository, App installation, controller, profile and marker location. Noninteractive mode requires explicit apply authorization and the necessary values; it never prompts. Persist selected marker coordinates in the broker's authoritative enrollment state and the installer's nonsecret instance configuration. Preserve the frozen v1 enrollment-file/token-response schema; add a reviewed version only if wire-format changes are genuinely necessary.

The planned scripts perform Agent-variable creation through structured host `gh` API arguments, not manual copy/paste instructions. They verify the host identity's setup authority, the actual repository and App installation, and feature/plan availability. Do not assume private/internal repository availability from public documentation or a successful host read; verify the selected repository and actual installation grant. Permission denial, unsupported plans and transport failures must be actionable; none becomes an approval bypass or permission broadening. No host GitHub credential is copied into the controller or retained by the auth service.

Read before writing. Reuse only a matching selected Agent variable; preserve unrelated variables, secrets, protection rules and deployment settings. A matching pending/device binding is idempotently resumable. A marker owned by another enrollment is a conflict, not an automatic overwrite; explicit replacement must close/fence the old grant first. Validate names using GitHub's rules, encode path segments correctly, use safe process arguments, and cap data/work. Do not interpolate names into shell commands.

## Enrollment and renewal

1. Start a bounded pending enrollment at the configured broker origin. Bind the repository, installation, server-defined profile and selected marker coordinates; return a pending controller ID, nonsecret approval material and a private recovery/possession credential.
2. Preview and apply the GitHub approval through the host installer, creating the selected repository Agent variable as needed. The controller and the broker's delegated runtime tokens cannot write that approval.
3. The broker independently verifies the actual installation and exact repository marker before preparing one recoverable enrollment completion. An initiating poll secret alone cannot authorize completion.
4. Persist the private v1 enrollment file atomically with owner-only permissions before acknowledging it. Retry recovers the same device/credential. Acknowledgment activates only a still-approved, unexpired grant; missing approval, concurrent revocation or expired completion cannot reactivate it.
5. Before every issuance/renewal and release, verify the live repository-held approval under a reviewed bounded-freshness policy along with the durable gate, device, profile, installation and expiry. Reserve every mint attempt; sign an App JWT; request exactly `repository_ids: [approvedRepositoryId]` plus approved runtime permissions; validate actual scope and expiry. Internal approval-check tokens require the same durable authority accounting.

## Revocation and uninstall

`revoke` works from a trusted host using current GitHub setup authority, explicit repository/Agent-variable inputs or saved instance configuration. It does not require the lost controller's device secret or access to its machine. Verify the selected marker and binding before mutation; delete only that approval variable. If the device credential is available, the existing self-revocation route is an additional closure mechanism, not the recovery prerequisite. Ask the broker to reconcile where the API supports it; report GitHub marker removal, broker closure and outstanding-token settlement as distinct observable states. An unavailable broker never becomes a false successful remote-revocation result.

Host revocation checks an independently reviewed exact-value fingerprint and makes at most one name-addressed DELETE. GitHub has no atomic compare-delete: an independent writer may replace approval between GET and DELETE and lose that newer value, causing temporary service loss. Manual inspection/reapproval is the accepted recovery; no distributed locks, leases, blind retries, automatic restoration or replacement are required. This availability tradeoff does not relax broker closure or old-token barriers.

`uninstall` performs revocation and stops/removes only the selected managed controller runtime. Preserve persistent volumes, workspace/history, other variables/secrets, existing GitHub Environments and the GitHub App installation by default. Local teardown is not evidence that remote authority has closed; report failures and remaining access explicitly. This decision authorizes future script behavior, not a live uninstall or deletion now.

Confirmed marker absence or a changed binding permanently closes that observed enrollment in durable broker state. Restoring an old marker must not reopen it; replacement needs a new controller ID/credential and fresh approval challenge. A timeout, 403 or malformed GitHub response denies issuance but is not fabricated evidence of deletion. Marker replay, rename, version changes, stale observations and deletion/recreation between checks need concrete provider tests. GitHub state and broker transactions are not atomic: document observation latency, rechecks and the remaining check-to-release race; do not claim instantaneous or continuously observed revocation.

Already-issued bearer tokens are separate authority. Preserve known-token revocation, unknown-attempt quarantine, response-loss accounting and the #34 replacement barrier. Removal of a marker, cache deletion or a replica count cannot recall a copied token. The minimal broker ledger therefore remains necessary even though approval lives in GitHub.

## Evidence and retained constraints

Use transport-boundary tests to assert exact GitHub lookup/mint permissions and repository scope. Use real PowerShell 7 process boundaries, including native Windows acceptance for named Agent-variable setup, reuse, conflict, denied/unsupported setup, revoke with no local credential, and uninstall preservation. Verify the actual broker API, private filesystem/ACLs and real Azure Table Storage for completion, revocation, replay, restart, conditional gates and restore rejection; no in-memory substitute.

Live GitHub acceptance must prove that the operator can create/remove the chosen marker, the broker can read it, and the exact controller token cannot read, create, change or restore it. Exercise missing/changed approval and failed GitHub reads before token release, duplicate/resumed installation, a customized Agent-variable name, lost-secret recovery, and an old token surviving enrollment closure until separately settled. The independent protocol review established the GitHub-permitted-writer authority and accepted read/delete availability race. Agent-variable marker encoding, freshness and adaptation of the existing durable verifier/admission quotas and recovery need implementation evidence under #68 before affected slices become ready. Shared broker-only verifier credentials must not be minted per public poll, positive approval decisions must not be cached across operations, and disconnects cannot erase reserved mint attempts.

Preserve the existing provider ceilings during adaptation: fixed UTC minute admission/read/sign/mint limits of 120/600/20/20 globally and 12/60/2/2 per repository, 128 fixed global slots, eight combined repository attempts, and pending caps of four per repository and 64 globally. Configuration may lower the reviewed ceilings. Changing the approval surface does not refund work, expire unknown attempts or authorize per-poll verifier minting; see [the current source accounting](../service/auth/README.md).

Azure Table Storage, one repository partition/common gate, per-entity ETags, external restore epoch, bounded work/rate/size/cardinality and fail-closed readiness remain. Keep configurable 15-minute pending approval, 24-hour abandonment-cleanup target, 30-day audit and 90-day inactivity defaults. Independent cleanup must work with zero HTTP replicas. Blob Data Protection keys may still protect encrypted completion/recovery payloads; they are not evidence that browser sessions remain in scope. This documentation update itself performs no deployment, App-permission change or live approval mutation.

## Observed evidence and remaining proof

On 2026-10-20, App 5387625 metadata included both `environments:read` and `agent_variables:read`; a host-authenticated GET of `repoagent/controller/agents/variables?per_page=1` returned HTTP 200 with `total_count: 0`. A subsequent bounded host probe on immutable repository ID `1426154477` created one uniquely named nonsecret disposable Agent variable, read its exact value, received DELETE acknowledgment and confirmed absence through a complete listing; no existing variable was touched. This proves host create/read/delete access only. Published App permissions and host API availability do not prove a particular installation token's scope, a private-plan entitlement or runtime permission separation. Live acceptance must prove host write, broker read and runtime inability to read/write approval on the selected repository.

Names and timestamps do not supply an immutable variable ID or deletion history. The marker may appear in Copilot's agent environment and must remain public data, never private authority. RepoAgent's native Codex runtime does not automatically consume Agent variables. GitHub's configuration UI documentation describes repository-administrator setup; REST authorization remains whatever GitHub permits for the actual Agent-variable writer, without a broker claim about their human identity or administrator status.
