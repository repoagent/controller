# Controller approval and a UI-free credential broker

Approved by the maintainer on 2026-10-20, with the current variable location and fresh setup contract superseded by [ADR 0012](adr/0012-use-repository-agent-variables-for-settings-and-approval.md). Fresh approval uses direct repository Agent variables and [setup v4](../service/auth/README.md#repository-agent-variable-enrollment-v4): kind `repository-agent-variable`, setup version 4 and exact policies `repository-agent-approval-v4`, `repository-agent-clone-approval-v4` or `repository-agent-settings-approval-v4`. Saved v2 Agent-variable and v3 Actions-variable grants keep their original contracts; Environment v1 stays revoke-only on the host. Frozen runtime schemas/scopes stay v1 for polling/webhook and v2 for clone profiles. Settings profiles use runtime v3 and add only `agent_variables:read`. The PowerShell installer supports v4; live GitHub/Azure, assembled migration and native Windows acceptance remain separate release gates.

## Authority and credentials

The GitHub App must be installed with access to the target repository before enrollment. The installer uses the operator's separately authenticated admin authority to create or safely reuse the selected direct repository Agent variable. GitHub authenticates that setup authority; the broker hosts no user login, browser approval, device-login ceremony or administrator dashboard.

Approval authority means a principal GitHub permits to manage the selected variable; the marker does not attest a particular human administrator or required deployment reviewer. The approval belongs to the repository, not to the person running setup. Their later departure or personal OAuth-consent withdrawal does not revoke it. A human identity may appear in an audit record but is not a continuing grant condition. GitHub App uninstall, loss of repository/required permissions, missing or changed approval, explicit device revocation, expiry or recovery-epoch mismatch deny further issuance.

The marker is nonsecret. It binds a broker-issued pending controller ID and fresh challenge/fingerprint to the immutable GitHub host, numeric repository/App/installation IDs, exact server-defined permission profile, authorization-policy version, external restore epoch and chosen marker coordinates. Readable binding information must let the operator assess the requested grant before writing it. The controller must separately prove possession of its private pending/device credential; reading or copying a public marker is insufficient. The broker validates the marker against its stored pending request, not client-supplied authority claims.

For setup v4 the broker reads `/repos/{owner}/{repo}/agents/variables/{name}` and compares the exact name and value, with TLS, fixed GitHub host and bounded freshness. Organization/inherited variables and other stores never substitute. The host needs GitHub-authorized Agent-variable write access; the broker-only verifier requests exactly `agent_variables:read`. The approval sits beside the nonsecret `REPOAGENT_*` settings: generic settings tooling must never write, copy or restore it. V4 permits the `REPOAGENT_` prefix only for the reserved `REPOAGENT_APPROVAL` name. Legacy v2 keeps its original name grammar. No setup secret, controller secret, host GitHub credential or App PEM enters a variable. Runtime grants never include variables write, secrets, Environment or workflow permissions. Frozen profiles have no variables access; v4 settings profiles add only Agent variables read, so they can read the nonsecret approval but cannot change it. Account for internal verifier tokens as well as returned runtime tokens.

## Installer setup and names

The host targets PowerShell 7.4 / `install.ps1`, with `Install`, `Enroll`, `Revoke` and `Uninstall` actions and a user-selectable repository Agent-variable name. Bash parity and a .NET/native installer are deferred. Fresh setup is v4 with default `REPOAGENT_APPROVAL`; `-ApprovalLocation AgentVariable` is the same default. Saved instance state decides its exact setup version and location; v2 and v4 share a kind but not a policy. Fresh v2/v3 selection is not offered.

Arguments fill answers; interactive mode prompts for missing values and previews the exact repository, App, profile and marker location. Noninteractive mode requires explicit apply authorization and the necessary values; it never prompts. Persist marker coordinates in broker state and separate installer configuration. Use explicit setup/marker v4 while preserving runtime enrollment-file/lease versions v1, v2 for clone profiles and v3 for settings profiles.

The scripts create Agent variables through structured host `gh` API arguments. The host verifies repository intent, GitHub-authorized write access, trusted broker origin and returned App/profile/binding. The broker performs App-JWT installation lookup; a host human credential cannot perform it. Feature/plan availability and actual installation access require separate acceptance. Permission denial, unsupported plans and transport failures never authorize bypass or permission broadening. No admin authority is copied into the controller or retained by the broker.

Read before writing. Reuse only the exact matching selected variable; preserve unrelated variables and secrets. A saved request remains idempotently resumable with its original possession and deadline. Another enrollment's marker is a conflict, not an automatic overwrite. Replacement requires closure, positive settlement of all old runtime/verifier capabilities and durable owner release. Validate and encode names with safe process arguments and bounded work.

## Enrollment and renewal

1. Privately persist a fresh recovery credential and idempotency ID on the host, then start bounded v4 enrollment at the configured broker origin. The broker validates the repository/installation and binds the server-defined profile and selected variable; it returns a pending controller ID and nonsecret approval material.
2. Apply the exact GitHub approval through the host installer, creating the selected direct repository Agent variable as needed. Runtime tokens cannot write it.
3. The broker independently verifies the actual installation and exact repository marker before preparing one recoverable enrollment completion. A setup secret alone cannot authorize completion.
4. Persist the private controller enrollment file (v1, v2 for clone profiles or v3 for settings profiles) atomically with owner-only permissions before acknowledging it. Retry recovers the same device/credential. Missing approval, concurrent revocation or expired completion cannot reactivate it.
5. Before every issuance/renewal and release, verify the live approval under bounded freshness with the durable gate, device, profile, installation and expiry. Reserve every mint, sign an App JWT, request exactly the approved repository and runtime permissions, then validate actual scope and expiry. Internal approval-check tokens require the same durable authority accounting.

## Revocation and uninstall

`revoke` works from a trusted host using current GitHub setup authority, explicit repository/variable inputs or saved approval state. Without saved state it defaults to Agent variables and `REPOAGENT_APPROVAL`; use the original v2 name, or `-ApprovalLocation ActionsVariable` for v3. It does not require the lost controller's secret or machine. Verify the selected exact value/binding before one deletion. A matching private enrollment may additionally self-revoke using its original runtime route and policy, including retired v3 files. Report marker removal, broker closure and outstanding-token settlement separately; an unavailable broker never becomes confirmed remote closure.

Host revocation checks an independently reviewed exact-value fingerprint and makes at most one name-addressed DELETE. GitHub has no atomic compare-delete: an independent writer may replace approval between GET and DELETE and lose that newer value, causing temporary service loss. Manual inspection/reapproval is the accepted recovery; no distributed locks, leases, blind retries, automatic restoration or replacement are required. This availability tradeoff does not relax broker closure or old-token barriers.

`uninstall` performs revocation and stops/removes only the selected managed controller runtime. Preserve persistent volumes, workspace/history, other variables/secrets, existing GitHub Environments and the GitHub App installation by default. Local teardown is not evidence that remote authority has closed; report failures and remaining access explicitly. This decision authorizes future script behavior, not a live uninstall or deletion now.

Fresh, well-formed confirmed marker absence or a changed binding permanently closes that observed enrollment in durable broker state. Restoring an old marker must not reopen it; replacement needs a new controller ID/credential and fresh approval challenge. A timeout, 403, malformed response or stale observation denies access without irreversible closure. A lone 404 can also mean lost access, so a 404 for the bound name establishes absence only when a well-formed listing page of the same location, read afterwards with the same verifier token, proves that the location was readable. That page is only an access proof: the number of repository variables, including CI and settings variables, never limits verification. A selected value read by name remains subject to oldest-read freshness. GitHub state and broker transactions are not atomic: document observation latency, rechecks and the remaining check-to-release race; do not claim instantaneous or continuously observed revocation.

Already-issued bearer tokens are separate authority. Preserve known-token revocation, unknown-attempt quarantine, response-loss accounting and the #34 replacement barrier. Removal of a marker, cache deletion or a replica count cannot recall a copied token. The minimal broker ledger therefore remains necessary even though approval lives in GitHub.

## Legacy approvals, migration and rollback

Each grant keeps its approval kind, setup version and policy. The broker selects authority from durable state, never a client hint. V2/v4 use Agent variables and v3 uses Actions variables; setup routes reject a different version before provider work. Existing v2 grants keep renewing unchanged until revoked. Nothing copies, moves, rewrites or deletes a live marker automatically.

The installer validates the saved `approval.json` version/setupVersion and kind together. V2/v4 share the Agent kind but remain distinct. Conflicting explicit locations stop before remote work. Original v2/v3 recovery journals retain their exact request and secret; saved approval metadata without its original journal cannot create replacement authority. Revoke/uninstall use the saved original store, marker version and policy. No-state revocation defaults to Agent variables or follows explicit ActionsVariable/Environment coordinates.

Migration from any older setup to v4 is deliberate:

1. Revoke the old grant using its saved approval file and, if available, matching private enrollment. Credential-free revocation remains available.
2. Establish broker closure, positive settlement of every old runtime/verifier capability and durable owner release. DELETE204 is closure only. Avoid starting replacement discovery while waiting; it can add another verifier before completion blocks. [#249](https://github.com/repoagent/controller/issues/249) owns the missing early settlement preflight.
3. Enroll in a new state directory with setup v4. It gets a new controller ID, challenge and Agent-variable marker, including when moving from v2 in the same store.

Restoring the old marker cannot reopen a closed grant. The new controller refuses retired Actions-v3 clone/settings policies; retain those files for revocation rather than rewriting them.

Rollback to a frozen profile also requires revoke, settlement, owner release and fresh setup v4 in a new directory. A broker without v4 fails closed; the host never falls back to v2/v3. Environment v1 stays revoke-only legacy.

## Evidence and retained constraints

Broker core unit tests assert exact GitHub lookup/mint permissions and repository scope against in-memory ports (ADR 0010). Installer verification is manual: use the AppHost/selected repository for real v4 setup, reuse, conflict, denial, credential-free revoke and retained-data checks. Native Windows DACL/atomic-file execution and actual provider/storage/recovery behavior remain separate evidence.

Live GitHub acceptance must prove host marker write/removal, broker read and exact runtime permissions: frozen tokens cannot read/write variables; settings tokens may read approval but cannot create, change or restore it. Exercise approval withdrawal, failed reads, resumed setup, custom names and unknown outcomes without changing immutable deadlines. The [v4 provider contract](../service/auth/README.md#repository-agent-variable-enrollment-v4) retains durable verifier/admission quotas and recovery. Core tests and golden rows do not replace live GitHub/Azure or host/Windows acceptance. Broker-only verifier credentials must not be minted per public poll, approval decisions must not be cached across operations, and disconnects cannot erase reserved mint attempts.

Preserve the existing provider ceilings during adaptation: fixed UTC minute admission/read/sign/mint limits of 120/600/20/20 globally and 12/60/2/2 per repository, 128 fixed global slots, eight combined repository attempts, and pending caps of four per repository and 64 globally. Configuration may lower the reviewed ceilings. Changing the approval surface does not refund work, expire unknown attempts or authorize per-poll verifier minting; see [the current source accounting](../service/auth/README.md).

Azure Table Storage, one repository partition/common gate, per-entity ETags, external restore epoch, bounded work/rate/size/cardinality and fail-closed readiness remain. Keep configurable 15-minute pending approval, 24-hour abandonment-cleanup target, 30-day audit and 90-day inactivity defaults. Independent cleanup must work with zero HTTP replicas. Blob Data Protection keys may still protect encrypted completion/recovery payloads; they are not evidence that browser sessions remain in scope. This documentation update itself performs no deployment, App-permission change or live approval mutation.

## Observed evidence and remaining proof

On 2026-10-20, App 5387625 metadata included both `environments:read` and `agent_variables:read`; a host-authenticated GET of `repoagent/controller/agents/variables?per_page=1` returned HTTP 200 with `total_count: 0`. A subsequent bounded host probe on immutable repository ID `1426154477` created one uniquely named nonsecret disposable GitHub Agent variable, read its exact value, received DELETE acknowledgment and confirmed absence through a complete listing; no existing variable was touched. This proves host create/read/delete access only. Published App permissions and host API availability do not prove a particular GitHub token's scope, a private-plan entitlement or runtime permission separation. Live acceptance must prove host write, broker read and runtime inability to read/write approval on the selected repository.

On 2026-10-23, for #184, a read-only host-authenticated GET of `repoagent/controller/actions/variables?per_page=1&page=1` returned the `total_count` and `variables[]` (`name`, `value`, `created_at`, `updated_at`) shape that the v3 provider parses. This only shows API shape compatibility for the host identity. It does not prove that the shared App or any installation has `actions_variables: read`. On 2026-10-24, for the code review of #171, a read-only host GET of `repoagent/controller/actions/variables/{name}` for an existing deployment variable returned `name`, `value`, `created_at` and `updated_at`; a lowercase request returned the stored uppercase name, and a missing name returned 404. A GET of a missing `agents/variables/{name}` returned 404 that documents the Agent "get a repository variable" operation. The broker's named read relies on these shapes. Before the installer default reaches operators, the App permission change, each installation's acceptance of it, and live host-write, broker-read and runtime-denial acceptance remain release gates.

Names and timestamps do not supply an immutable variable ID or deletion history. Actions variables are visible to the repository's workflows as `vars.*` and may appear in workflow logs. The marker must therefore remain public data, never private authority. RepoAgent's agent runtime does not consume the approval variable. REST authorization remains whatever GitHub permits for the actual Actions-variable writer, without a broker claim about their human identity or administrator status. Legacy Agent-variable markers may also appear in Copilot's agent environment.
