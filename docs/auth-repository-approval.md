# Controller approval and a UI-free credential broker

Approved by the maintainer on 2026-10-20. This replaces broker-hosted administrator browser approval, broker human OAuth/cookie/CSRF/PKCE flows, and continuing authorization tied to a particular approving person. The current storage decision is [ADR 0007](adr/0007-use-repository-actions-variables-for-approval.md): direct repository Actions variables replace the Agent-variable location chosen by [ADR 0006](adr/0006-use-repository-agent-variables-for-approval.md), which had replaced GitHub Environments. The [provider source contract](../service/auth/README.md#repository-actions-variable-enrollment-v3), from [#184](https://github.com/repoagent/controller/issues/184), implements explicit v3 setup and markers with immutable approval kind `repository-actions-variable`, setup version 3 and policy `repository-actions-approval-v3` (`repository-actions-clone-approval-v3` for clone profiles). Agent-variable v2 setup ([#68](https://github.com/repoagent/controller/issues/68)) and Environment setup v1 stay as explicit legacy kinds; see [legacy approvals, migration and rollback](#legacy-approvals-migration-and-rollback). Markers never change kind implicitly. Frozen profiles keep their controller enrollment file and runtime schemas/scopes: v1 for `polling`/`webhook` and v2 for explicit clone profiles. Only the explicitly enrolled repository-settings profiles use runtime v3, which adds `actions_variables:read` ([ADR 0008](adr/0008-add-an-explicit-repository-settings-runtime-profile.md)). Guided installer and host integration remain [#53](https://github.com/repoagent/controller/issues/53) work; live GitHub/Azure and native Windows acceptance remain separate release gates. Canonical delivery parents are [#30](https://github.com/repoagent/controller/issues/30) and [#31](https://github.com/repoagent/controller/issues/31).

## Authority and credentials

The GitHub App must be installed with access to the target repository before enrollment. The installer uses the operator's separately authenticated admin authority to create or safely reuse the selected direct repository Actions variable. GitHub authenticates that setup authority; the broker hosts no user login, browser approval, device-login ceremony or administrator dashboard.

Approval authority means a principal GitHub permits to manage the selected variable; the marker does not attest a particular human administrator or required deployment reviewer. The approval belongs to the repository, not to the person running setup. Their later departure or personal OAuth-consent withdrawal does not revoke it. A human identity may appear in an audit record but is not a continuing grant condition. GitHub App uninstall, loss of repository/required permissions, missing or changed approval, explicit device revocation, expiry or recovery-epoch mismatch deny further issuance.

The marker is nonsecret. It binds a broker-issued pending controller ID and fresh challenge/fingerprint to the immutable GitHub host, numeric repository/App/installation IDs, exact server-defined permission profile, authorization-policy version, external restore epoch and chosen marker coordinates. Readable binding information must let the operator assess the requested grant before writing it. The controller must separately prove possession of its private pending/device credential; reading or copying a public marker is insufficient. The broker validates the marker against its stored pending request, not client-supplied authority claims.

The broker reads the bound name from the direct repository location `/repos/{owner}/{repo}/actions/variables/{name}` and compares its exact name and value, with TLS, fixed GitHub host, bounded freshness and no client-supplied screenshots or cached copies as authorization. Only direct repository Actions variables authorize. Organization or inherited variables, GitHub Agent variables and Environment variables cannot substitute. The host needs GitHub-authorized Actions-variables write access. The internal exact-repository verifier requests Actions variables read (`actions_variables:read`), subject to live installation-scope proof. The approval variable sits next to the ordinary nonsecret `REPOAGENT_` repository settings. Generic settings tooling must treat it as approval-owned and never write, copy or restore it. An Actions-variable approval may therefore use the `REPOAGENT_` prefix only as the name the settings catalogue reserves (`REPOAGENT_APPROVAL`); the installer and the v3 setup routes refuse any other `REPOAGENT_` approval name before GitHub work. The broker-issued controller secret is never placed in any repository variable. Neither GitHub Environment creation nor an Environment name, numeric identity or deployment setting is required. Controller runtime GitHub tokens keep their exact polling/webhook (and explicit clone) profiles. No variables write, secrets, Environment or workflow permissions, host GitHub credentials or App PEM are delegated to them, so a controller cannot write or restore its own approval. Only the explicitly enrolled repository-settings profiles ([ADR 0008](adr/0008-add-an-explicit-repository-settings-runtime-profile.md)) add `actions_variables:read`, which lets that controller read the nonsecret marker but not change it. Account for internally minted verification tokens as well as returned runtime tokens.

## Installer setup and names

The MVP targets PowerShell 7 / `install.ps1`, with `install`, `enroll`, `revoke` and `uninstall` actions and a user-selectable repository Actions-variable name. Bash parity and a .NET/native installer are deferred. `REPOAGENT_APPROVAL` is the default variable name for fresh Actions-variable approval. `-ApprovalLocation AgentVariable` explicitly selects legacy Agent-variable setup v2, whose default name stays `APPROVED_CONTROLLER`. Saved instance state always decides the location of an existing enrollment. Keep this input separate from Azure Container Apps environment selection and the native Discussion-enrollment option.

Arguments fill answers; interactive mode prompts for missing values and previews the exact repository, App installation, controller, profile and marker location. Noninteractive mode requires explicit apply authorization and the necessary values; it never prompts. Persist selected marker coordinates in the broker's authoritative enrollment state and the installer's nonsecret instance configuration. Use the provider's explicit v3 setup/marker contract while preserving the existing controller enrollment-file/token-response schemas (v1, v2 for explicit clone profiles, or v3 for explicit repository-settings profiles).

The scripts perform Actions-variable creation through structured host `gh` API arguments, not manual copy/paste instructions. The host verifies repository intent, its GitHub-authorized write access, trusted broker origin and returned App/profile/binding. The broker performs App-JWT installation lookup; a host human credential cannot perform that lookup. Feature/plan availability and actual installation access require separate acceptance. Do not assume private/internal repository availability from public documentation or a successful host read; verify the selected repository and actual installation grant. Permission denial, unsupported plans and transport failures must be actionable; none becomes an approval bypass or permission broadening. No admin authority is copied into the controller or retained by the broker.

Read before writing. Reuse only a matching selected Actions variable; preserve unrelated variables, secrets, protection rules and deployment settings. A matching pending/device binding is idempotently resumable. A marker owned by another enrollment is a conflict, not an automatic overwrite; explicit replacement must close/fence the old grant first. Validate names using GitHub's rules, encode path segments correctly, use safe process arguments, and cap data/work. Do not interpolate names into shell commands.

## Enrollment and renewal

1. Privately persist a fresh recovery credential and idempotency ID on the host, then start bounded v3 enrollment at the configured broker origin. The broker validates the repository/installation and binds the server-defined profile and selected variable; it returns a pending controller ID and nonsecret approval material.
2. Preview and apply the GitHub approval through the host installer, creating the selected repository Actions variable as needed. The controller and the broker's delegated runtime tokens cannot write that approval.
3. The broker independently verifies the actual installation and exact repository marker before preparing one recoverable enrollment completion. An setup secret alone cannot authorize completion.
4. Persist the private controller enrollment file (v1, v2 for clone profiles or v3 for repository-settings profiles) atomically with owner-only permissions before acknowledging it. Retry recovers the same device/credential. Acknowledgment activates only a still-approved, unexpired grant; missing approval, concurrent revocation or expired completion cannot reactivate it.
5. Before every issuance/renewal and release, verify the live controller approval under a reviewed bounded-freshness policy along with the durable gate, device, profile, installation and expiry. Reserve every mint attempt; sign an App JWT; request exactly `repository_ids: [approvedRepositoryId]` plus approved runtime permissions; validate actual scope and expiry. Internal approval-check tokens require the same durable authority accounting.

## Revocation and uninstall

`revoke` works from a trusted host using current GitHub setup authority, explicit repository/Actions-variable inputs (or `-ApprovalLocation AgentVariable` for a legacy grant) or saved instance configuration. It does not require the lost controller's controller secret or access to its machine. Verify the selected marker and binding before mutation; delete only that approval variable. If the device credential is available, the existing self-revocation route is an additional closure mechanism, not the recovery prerequisite. Ask the broker to reconcile where the API supports it; report GitHub marker removal, broker closure and outstanding-token settlement as distinct observable states. An unavailable broker never becomes a false successful remote-revocation result.

Host revocation checks an independently reviewed exact-value fingerprint and makes at most one name-addressed DELETE. GitHub has no atomic compare-delete: an independent writer may replace approval between GET and DELETE and lose that newer value, causing temporary service loss. Manual inspection/reapproval is the accepted recovery; no distributed locks, leases, blind retries, automatic restoration or replacement are required. This availability tradeoff does not relax broker closure or old-token barriers.

`uninstall` performs revocation and stops/removes only the selected managed controller runtime. Preserve persistent volumes, workspace/history, other variables/secrets, existing GitHub Environments and the GitHub App installation by default. Local teardown is not evidence that remote authority has closed; report failures and remaining access explicitly. This decision authorizes future script behavior, not a live uninstall or deletion now.

Fresh, well-formed confirmed marker absence or a changed binding permanently closes that observed enrollment in durable broker state. Restoring an old marker must not reopen it; replacement needs a new controller ID/credential and fresh approval challenge. A timeout, 403, malformed response or stale observation denies access without irreversible closure. A lone 404 can also mean lost access, so a 404 for the bound name establishes absence only when a well-formed listing page of the same location, read afterwards with the same verifier token, proves that the location was readable. That page is only an access proof: the number of repository variables, including CI and settings variables, never limits verification. A selected value read by name remains subject to oldest-read freshness. GitHub state and broker transactions are not atomic: document observation latency, rechecks and the remaining check-to-release race; do not claim instantaneous or continuously observed revocation.

Already-issued bearer tokens are separate authority. Preserve known-token revocation, unknown-attempt quarantine, response-loss accounting and the #34 replacement barrier. Removal of a marker, cache deletion or a replica count cannot recall a copied token. The minimal broker ledger therefore remains necessary even though approval lives in GitHub.

## Legacy approvals, migration and rollback

Each grant keeps the approval kind, setup version and policy it was enrolled with. The broker resolves the provider from authenticated durable grant state, never from the route or a client claim. It reads Actions variables only for `repository-actions-variable` grants and GitHub Agent variables only for `repository-agent-variable` grants. The `/v2` and `/v3` setup, status, completion and acknowledgment routes reject a pending grant of the other kind before provider work. Existing v2 Agent-variable grants keep renewing against their GitHub Agent variable until deliberately revoked. Nothing copies, moves, rewrites or deletes a live marker automatically.

The installer treats the saved `approval.json` kind as authoritative. If the saved kind differs from an explicit `-ApprovalLocation`, the installer stops before broker or GitHub work instead of reinterpreting the enrollment. Revoke and uninstall use the saved kind's variable location and marker version. With no saved state, they follow explicit `-ApprovalLocation` or `-GitHubEnvironment` input and otherwise default to Actions variables.

Migration from GitHub Agent variables is deliberate:

1. Revoke the v2 grant with the installer (`Revoke` or `Uninstall` with the saved state, or `-ApprovalLocation AgentVariable` with explicit coordinates). This removes only the exact Agent marker and adds device self-revocation when the private device file is available.
2. Wait until broker closure and outstanding-token settlement are observed. One repository owner gate serves all approval kinds, so v3 completion is refused (`409`) while the v2 owner remains active or unsettled.
3. Enroll afresh in a new state directory. The new enrollment gets a new controller ID, a fresh challenge and a new Actions-variable marker.

Restoring the old Agent marker cannot reopen the closed v2 grant.

Rollback stays explicit. With the current broker, a fresh enrollment that passes `-ApprovalLocation AgentVariable` uses setup v2. A broker build that predates v3 fails closed on `repository-actions-variable` rows and `/v3` routes: issuance is denied, not reinterpreted. After such a rollback, revoke the v3 grants and enroll again with the legacy location. Environment v1 stays revoke-only legacy.

## Evidence and retained constraints

Use transport-boundary tests to assert exact GitHub lookup/mint permissions and repository scope. Use real PowerShell 7 process boundaries, including native Windows acceptance for named Actions-variable setup, reuse, conflict, denied/unsupported setup, revoke with no local credential, and uninstall preservation. Verify the actual broker API, private filesystem/ACLs and real Azure Table Storage for completion, revocation, replay, restart, conditional gates and restore rejection; no in-memory substitute.

Live GitHub acceptance must prove that the operator can create/remove the chosen marker, the broker can read it, and the exact controller token cannot read, create, change or restore it. Exercise missing/changed approval and failed GitHub reads before token release, duplicate/resumed installation, a customized Actions-variable name, lost-secret recovery, and an old token surviving enrollment closure until separately settled. The independent protocol review established the GitHub-permitted-writer authority and accepted read/delete availability race. The [v3 provider contract](../service/auth/README.md#repository-actions-variable-enrollment-v3), with the retained [#68 v2 contract](../service/auth/README.md#repository-agent-variable-enrollment-v2), defines marker encoding, freshness, durable verifier/admission quotas and recovery. Its real HTTP/pinned-Azurite/Data Protection tests provide application evidence; they do not replace live GitHub/Azure or host/Windows acceptance. Shared broker-only verifier credentials must not be minted per public poll, positive approval decisions must not be cached across operations, and disconnects cannot erase reserved mint attempts.

Preserve the existing provider ceilings during adaptation: fixed UTC minute admission/read/sign/mint limits of 120/600/20/20 globally and 12/60/2/2 per repository, 128 fixed global slots, eight combined repository attempts, and pending caps of four per repository and 64 globally. Configuration may lower the reviewed ceilings. Changing the approval surface does not refund work, expire unknown attempts or authorize per-poll verifier minting; see [the current source accounting](../service/auth/README.md).

Azure Table Storage, one repository partition/common gate, per-entity ETags, external restore epoch, bounded work/rate/size/cardinality and fail-closed readiness remain. Keep configurable 15-minute pending approval, 24-hour abandonment-cleanup target, 30-day audit and 90-day inactivity defaults. Independent cleanup must work with zero HTTP replicas. Blob Data Protection keys may still protect encrypted completion/recovery payloads; they are not evidence that browser sessions remain in scope. This documentation update itself performs no deployment, App-permission change or live approval mutation.

## Observed evidence and remaining proof

On 2026-10-20, App 5387625 metadata included both `environments:read` and `agent_variables:read`; a host-authenticated GET of `repoagent/controller/agents/variables?per_page=1` returned HTTP 200 with `total_count: 0`. A subsequent bounded host probe on immutable repository ID `1426154477` created one uniquely named nonsecret disposable GitHub Agent variable, read its exact value, received DELETE acknowledgment and confirmed absence through a complete listing; no existing variable was touched. This proves host create/read/delete access only. Published App permissions and host API availability do not prove a particular GitHub token's scope, a private-plan entitlement or runtime permission separation. Live acceptance must prove host write, broker read and runtime inability to read/write approval on the selected repository.

On 2026-10-23, for #184, a read-only host-authenticated GET of `repoagent/controller/actions/variables?per_page=1&page=1` returned the `total_count` and `variables[]` (`name`, `value`, `created_at`, `updated_at`) shape that the v3 provider parses. This only shows API shape compatibility for the host identity. It does not prove that the shared App or any installation has `actions_variables: read`. On 2026-10-24, for the code review of #171, a read-only host GET of `repoagent/controller/actions/variables/{name}` for an existing deployment variable returned `name`, `value`, `created_at` and `updated_at`; a lowercase request returned the stored uppercase name, and a missing name returned 404. A GET of a missing `agents/variables/{name}` returned 404 that documents the Agent "get a repository variable" operation. The broker's named read relies on these shapes. Before the installer default reaches operators, the App permission change, each installation's acceptance of it, and live host-write, broker-read and runtime-denial acceptance remain release gates.

Names and timestamps do not supply an immutable variable ID or deletion history. Actions variables are visible to the repository's workflows as `vars.*` and may appear in workflow logs. The marker must therefore remain public data, never private authority. RepoAgent's native Codex runtime does not consume the approval variable. REST authorization remains whatever GitHub permits for the actual Actions-variable writer, without a broker claim about their human identity or administrator status. Legacy Agent-variable markers may also appear in Copilot's agent environment.
