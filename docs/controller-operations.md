# Controller operations

Use this reference when running or troubleshooting an installed controller. For installation, start with the [guided local installer](local-installation.md) or [container setup](container-setup.md). For supported features and everyday use, see the [README](../README.md).

## Run the controller directly

The following example uses your own GitHub App in a configured Linux container containing `gh` and `codex`. The packaged controller is Native AOT compiled and needs no installed .NET runtime. Codex uses its normal sign-in. GitHub access uses an installed GitHub App with **Discussions: read/write** and a read-only mounted PEM signing key. An agent GitHub-user login is unnecessary. For shared-App credentials instead, see [external controller credentials](container-setup.md#external-controller-credentials).

Pass these arguments to the bridge **inside the configured container**:

```text
RepoAgentController --repo repoagent/controller --app-id APP_ID_OR_CLIENT_ID --mention-user repoagent \
--private-key /run/secrets/github-app.pem --workspace /workspace \
--state /data/bridge-state.json
```

The bridge discovers the App's installation for the configured repository; `--installation-id` optionally checks a specific expected installation. It verifies the token's actual `viewer.login` matches the App bot before starting Codex. Use `--check-auth` to check App credentials and prepare its `gh` wrapper without starting an agent session. See [App setup, token renewal and verification](github-app-auth.md).

Mention the bot's actual login, such as `@repo-agent-connector[bot]`, in a Discussion body/comment/reply, or add `--enroll https://github.com/OWNER/REPO/discussions/123` (repeatable). Discussion enrollment uses literal polled text and does not require GitHub mention notifications or autocomplete. An explicitly enrolled URL persists in the state file and need not be repeated. With [repository settings](repository-settings.md) enabled, `REPOAGENT_ENROLLMENT_CATEGORIES` also enrolls Discussions created in selected categories without a mention; see [category enrollment](repository-settings.md#category-enrollment) for how preexisting Discussions are treated. Each Discussion gets one agent session across all comment threads. The default polling interval is ten seconds after each completed poll; every connection is paginated, so large repositories may take longer. Only observed versions are forwarded; changes reverted between polls can be missed.

Each turn states its Codex model and reasoning effort explicitly. A Discussion label `repoagent:<model>:<reasoning>`, such as `repoagent:sol6.1:xhigh`, selects them for that Discussion's next turn. Without such a label, the repository defaults `REPOAGENT_MODEL` and `REPOAGENT_REASONING` apply, then the Codex configuration, then the model catalogue's default. Adding, changing or removing a label never starts a turn and never steers active work. Conflicting labels, malformed labels and values the Codex account does not offer are never substituted: the input waits and a `selection-error` names the problem. See [model and reasoning selection](repository-settings.md#model-and-reasoning-selection).

Add `--mention-user repoagent` to enroll through the dedicated `@repoagent` account. Startup verifies that the configured user exists; Discussion enrollment recognizes GitHub-rendered mentions, including emphasized mentions, while profile links, code examples and email addresses stay inactive. The App still authors replies and EYES; the mention account needs no runtime login or token. See [mention-account setup](github-app-auth.md#dedicated-mention-account) for repository access and autocomplete eligibility. Native agent registration remains a separate integration.

The response skill is copied beside the executable and injected through Codex's native skill input. Additional skills and workspace guidance load normally. Agent sessions receive the absolute path to an authenticated `gh` wrapper, which reads renewed credentials for every command. The agent runtime process inherits neither a static GitHub token nor the operator's GitHub-user token/configuration. Choose a Codex configuration whose normal tool permissions allow the agent's intended work and network access for `gh` publication. The bridge preserves those permissions and has no approval UI: interactive approval/input requests are logged and rejected for operator attention. Participant clarification questions should be published to GitHub by the response skill.

Logs go to timestamped stdout. Keep the process running for agent work and future activity. Ctrl+C stops the process. `--once` is an observation/acceptance check, **not a complete conversation run**: it exits after one poll and can interrupt unfinished agent work. Agent acceptance means the input reached Codex, not that the answer finished. On normal restart, reuse the same state file and Codex sign-in/storage; the next change resumes the recorded session and its agent session history.

### Supplied Codex credentials

`--codex-auth FILE` supplies the Codex account credentials (an `auth.json` holding an API key or ChatGPT sign-in tokens), separately from the GitHub App credentials. It requires an explicit private `CODEX_HOME`. Startup validates the file before any GitHub or Codex use and installs it as the native home's `auth.json` only when its content differs from the last supply, so a restart keeps tokens Codex itself refreshed. The owned app-server then uses file credential storage.

Replace the file to change credentials while the controller runs; replace it atomically (write beside it, then rename). The Codex integration does not rely on reloading a replaced `auth.json`: a running app-server keeps its loaded account. `account/read` with `refreshToken` adopts only a same-account ChatGPT file, `account/login/start` covers API keys only, and external `chatgptAuthTokens` are marked internal. The controller therefore checks the file every five seconds and, when no accepted turn is running (and in clone mode, no repository refresh is in progress), installs the replacement and restarts only its owned app-server. A running turn is never interrupted; the replacement applies before the next input. Each session resumes its recorded agent session and history on its next input. An unusable replacement is logged and the current credentials stay in use. If the restart itself fails, the controller stops.

A turn whose credentials are rejected (`401`/`unauthorized`) logs `codex-auth-failed` with what to do. New Discussion input then stays in the controller's waiting queue (`input-held`), without a turn or EYES receipt, and is dispatched once replacement credentials are applied. The rejected turn's own input goes back to the front of that queue (`input-requeued`) and is sent again, marked as a [redelivery](#checkpoints-and-manual-recovery), with the replacement credentials. Held input never counts as processed work.

## Status and retained logs

`RepoAgentController status --state PATH` prints the controller's current status as JSON, for a running or stopped controller, without taking its lease or requiring you to read checkpoint files. It reports the repository and App actor, controller lifetime (`starting`, `running`, `stopped` or `failed`, with mode and timestamps), authentication health (`healthy`, `degraded` with automatic retry details during broker throttling, `failed` with its error, or `unknown`), Codex account authentication as `codexAuthentication` (`supplied` after `--codex-auth` is installed or applied, `healthy` after a turn completes, `failed` with its error, or `unknown`), per-Discussion sessions, work counts and up to 20 recent failures with their log kind and time, plus the latest forwarded activity and each [repository setting](repository-settings.md)'s latest observation (`settings`: state, effective value and the reason it is invalid or unreadable). A session is `pending` while an agent delivery attempt is in flight, or was interrupted by a stop until the next start retries it; `retrying`, with `attempts` and `retryAt`, after a failed or unacknowledged delivery (see [redelivery](#checkpoints-and-manual-recovery)); `running`, with the turn's start as `since`, while an agent turn runs; otherwise `idle`. `work` counts stored sessions, pending, retrying and waiting input, and `running` turns against `limit`, the effective [active-session limit](repository-settings.md#active-session-limit). A stopped controller reports no running turns. `running` controller state without a later stop means the last recorded lifetime; an abrupt kill cannot record its own end.

### Private session activity

Run `activity` as the controller's operating-system user, inside its container or native Linux/macOS environment. The controller must already be running in polling or webhook mode; stopped controllers and `--once` have no activity endpoint. The command lists only the controller's unambiguous Discussion-to-session mappings. Mapping reads use a consistent local snapshot, so repository scans and slow GitHub reads do not block selection or live-update revalidation. New sessions and confirmed deletions update that snapshot. Select a mapped Discussion number or its exact URL in the configured repository; foreign, dashboard and unmapped selections are refused. There is no arbitrary session ID, runtime-method forwarding or transcript HTTP endpoint.

```sh
RepoAgentController activity --state /data/bridge-state.json
RepoAgentController activity --state /data/bridge-state.json --discussion 42 --limit 100
RepoAgentController activity --state /data/bridge-state.json --discussion 42 --follow
RepoAgentController activity --state /data/bridge-state.json --discussion 42 --format json
```

History is newest first. Use the printed `--cursor` with the same Discussion to request an older page; a first page does not establish complete history. The default and maximum page size is 100 items. Continuations are private, opaque and bound to this controller/runtime lifetime and the selected mapping. Start a new snapshot after a restart, changed mapping, unsupported history or invalid continuation. The pinned runtime's efficient item pagination is preferred; legacy stores use its read-only full-turn history API and page one turn's items locally. That compatibility path bounds the returned page, but the runtime may reconstruct a larger retained turn or history internally. No second runtime, resume or turn is started for inspection.

Text and deliberate JSON-lines output retain session, turn and item IDs, item status and supported text arguments/results. Provider-classified file reads appear as read evidence with their path and associated operation status/result. This is best-effort evidence of an operation, not proof that a file was fully read or its instructions followed; missing evidence does not establish noncompliance. Unsupported item families, intentionally suppressed source items, truncation and incomplete history are marked. Reasoning, raw provider responses, image/binary bodies and runtime credential/configuration operations are excluded.

`--follow` subscribes before reading its initial history page and reconciles racing updates by stable item identity. Subsequent `UPDATE`/`upsert` records replace that item's displayed state. Each watcher holds at most 256 queued updates and 1 MiB; the runtime's shared live baseline is also bounded. A slow viewer, missing baseline, changed mapping or runtime restart produces an explicit gap and ends the subscription. Re-select the Discussion for a fresh snapshot; there is no durable event replay promise. Ctrl+C or a disconnected viewer cancels inspection without changing agent work. History reads have a five-second deadline, with at most two outstanding reads and four simultaneous followers. Individual text is limited to 32 KiB, reduced for large pages so responses stay below 1 MiB. There is no unbounded full-history export.

The local Unix socket has mode `0600` in a private `0700` directory. Its descriptor is beside `--state` under `PATH.activity/endpoint.json`, with the same private modes and the repository, state-path and lifetime binding. The endpoint is removed on orderly controller shutdown; stale descriptors never start a runtime. Filesystems that cannot enforce these permissions disable inspection while ordinary controller operation continues. This boundary excludes other operating-system users; processes sharing the same UID, including the controller's agent tools, are not isolated from one another.

Known controller secrets are redacted and terminal control characters are escaped. Running output retains a protected suffix until completion so split updates cannot reveal a known secret prefix. Tool output can still contain secrets the controller does not know; private operator access is not a complete secret detector. Output is not copied into controller logs, status, dashboard or exception messages. Treat terminal output and any explicitly redirected JSON as private operator data.

### Status endpoint

A running controller also serves `GET /status` on a local port, in polling and webhook mode. `--status-port` selects it (default 8081); it listens on loopback only and must differ from `--listen-port`. The answer is `busy` while an agent turn runs, input is pending, retrying or waiting, or managed checkout admission is blocked by uncertainty; otherwise `idle`, with the `work` counts of `status` above (`admissionBlocked` is `true` while uncertainty holds new turns, and `null` without a managed clone). A known block remains busy even when no Discussion remains, without claiming an uncertain turn is running:

```json
{"state":"busy","work":{"sessions":1,"pending":0,"retrying":0,"waiting":0,"running":1,"limit":4,"admissionBlocked":null}}
```

It returns nothing else: no Discussion URLs, sessions, failures, logs or credentials. The controller does not act on it. A hosting environment that must not stop a busy controller, such as one that scales to zero, reads it ([ADR 0009](adr/0009-keep-hosting-lifecycle-out-of-the-controller.md)); nothing reads it yet. In a container it is reachable inside the container's network, for example from a sidecar, and the container runtime publishes no port for it. The container runtime uses 8081, or 8082 when its listener port is configured as 8081. `--once`, `--check-auth` and `--disable-webhook` serve no endpoint.

The lease holder also appends every stdout line to retained logs in `PATH.logs/`, so they survive restart and container replacement. `--log-file-bytes` (default 1 MiB, 1 KiB to 1 GiB) bounds each file and `--log-files` (default 5, at most 100) bounds the count, including the active `controller.log`. Retained logs never exceed their product (5 MiB by default); rotation deletes the oldest file. At startup a lower setting removes surplus and oversized rotated files and keeps only the newest whole lines of an oversized active file. `RepoAgentController logs --state PATH` prints them oldest first. Stdout is unchanged.

Status and retained logs use the same redacted entries, so every reported failure has a log entry with the same time, kind and message (status truncates messages beyond 2000 characters), correlated by Discussion URL and session ID. Tokens, controller secrets and webhook secrets are redacted. Agent turn events are reduced to thread, turn, status and error text, so transcript items are not logged; Discussion bodies are not logged. Status (`PATH.status.json`) and logs are owner-only files beside the state.

### Discussion status dashboard

`--dashboard-category "NAME"` (installer: `-DashboardCategory 'NAME'`; container: `configure --dashboard-category "NAME"`; an empty value removes it) publishes the same status to a controller-owned Discussion in that existing category, so participants can see it without host access. The installer saves this choice for retries; older saved installations without it remain supported. Create the category first; the App needs only its existing **Discussions: read/write**. The controller creates the Discussion once and finds it again after restart; it is recognised by the App's own authorship plus the hidden `<!-- repoagent:controller-dashboard -->` marker, so a participant's copy stays an ordinary Discussion. The dashboard itself is never agent input: mentions, comments, `--enroll` of its URL and its webhook deliveries are all ignored.

The body leads with **Last heartbeat**, a full UTC timestamp refreshed about every 30 seconds, including when idle. Treat more than two minutes without a heartbeat as offline and investigate: failure to publish can look the same as an offline controller. An abrupt kill cannot report its own end, and GitHub cannot change a frozen title or body automatically. A handled graceful or failed stop publishes its stop time explicitly.

The compact overview shows work capacity first: running agent turns against the active-session limit, waiting inputs, pending acknowledgements and stored sessions as separate counts. GitHub and Codex authentication, repository-setting problems, image update information, tracked Discussions including idle entries and retained failures follow. Supplied Codex credentials remain unverified until a turn completes; an unknown credential state is never shown as healthy. Latest activity links to its exact Discussion or comment.

Each update also publishes a concise title, for example `💓 28 Oct 2026 09:07 UTC · 0/4 active · 0 queued — RepoAgent`. Active counts running turns and queued counts waiting inputs; neither counts idle stored sessions or pending acknowledgements. Known stops take priority over current GitHub authentication failure, Codex authentication failure, then checkout admission blocking (`Dispatch blocked`), then fresh confirmed account usage exhaustion (`Usage exhausted`, with a reported reset when available). The body retains simultaneous problems. Historical errors alone never change the title; recovery restores the ordinary work summary. Titles include the year so an old heartbeat remains unambiguous at year boundaries. Lost GitHub authority can prevent even a failure or stop publication. Error text remains the same redacted text as status and logs.

The **Agent account usage** section reads `account/rateLimits/read` from this controller's owned Codex runtime, never the desktop chat account or GitHub API quota. Codex 0.165.0 defines this protocol, but availability depends on the deployed account/provider; unsupported methods and unavailable or malformed responses are reported explicitly. Schema support alone is not evidence that a deployed account has supplied live measurements. Account allowances can span repositories and are independent of the active-session limit. No turns are started to measure usage, and collection never changes work admission or authentication state.

A full read runs at dashboard startup and then one minute after each read completes, with a ten-second budget per read. Successful observations are fresh for less than two minutes. A failed or unsupported refresh, a disconnected/replaced runtime or an account-change notification immediately marks last-known values stale; superseded in-flight reads cannot restore them. A new controller lifetime starts with unknown usage. Stale values retain their original observation time and never contribute an exhaustion title. The next successful full read replaces them.

Each supplied allowance keeps its meter/name, model and plan scope, primary/secondary windows and individual spend control when reported. Used percentages are converted to remaining percentages; missing windows and resets stay unknown. Explicit permission for ordinary usage or available additional credits prevents a depleted included window alone from claiming account exhaustion; provider spend-control evidence remains visible. This does not promise that a model call will succeed or that a past reset restored capacity. Private account identifiers and credit balances are not published. To bound output, the dashboard shows at most 20 metered buckets (with an exact omitted count) and the pinned protocol's three possible windows per bucket; metadata uses the same redaction, literal text and 300-character bounds as other dashboard text.
The **Tracked Discussions** section comes from the saved Discussion inventory, without extra title lookups. Running turns come first, then pending acknowledgements, retries, queued input and idle Discussions; each group is ordered by its stored URL using ordinal comparison. At most 20 entries are shown, with the exact omitted count. Stored session totals remain separate from running turns and waiting inputs. Idle means no current work is recorded; it does not establish checkout recovery. Latest activity keeps its exact comment anchor when one was recorded. Invalid stored links are shown as unlinked Discussions.

**Historical failures** groups equivalent retained redacted events by kind, message and Discussion association, with occurrence counts and latest timestamps. It shows the newest 10 groups; an omitted-group count points to expandable details containing every retained event, up to the status limit of 20. Each detail keeps its timestamp, kind and currently publishable redacted message. Messages remain limited to 300 characters in the dashboard, with explicit truncation notices; status truncation is identified too. Only complete valid Discussion links within that publishable text, or a valid recorded event link, become clickable references. Older discarded events and truncated text cannot be reconstructed here; private logs and transcripts are not added.

Events whose timestamps precede this controller lifetime are marked explicitly. This is historical evidence: restart, healthy authentication and idle sessions do not establish recovery of a checkout or any earlier failure. Historical groups never create a current blocker title; current authentication and admission evidence remains in the overview. Empty history is shown as “None recorded.”

An **Updates** section compares the controller's image with the [baseline releases](ci-cd.md#baseline-releases) published in `repoagent/controller`. The controller reads them with its App credential at startup and about hourly; GitHub's **Latest** badge is ignored. `--image-inventory FILE` names the running image's inventory: the container runtime passes `/opt/repoagent/image-inventory.json`, and its SHA-256 identifies the release that published the image. When a newer release exists, the section shows one **Update available** notice for the newest release only, with the number of newer releases, links to the release and the GHCR package, the immutable image reference and its gh and Codex versions. Publication is not deployment. The controller never replaces itself and has no Docker host access, so an operator recreates the controller from that image, or rebuilds a derived image on it; external configuration, credentials and session volumes are kept. The section instead reports **Release identity uncertain**, and suggests no replacement, when:

- no inventory is given (a native or development run);
- the inventory matches none of the 100 newest published releases (a derived, local, unreleased or much older image).

An image built `FROM` a baseline image without changing its inventory still matches that release. A failed release read is shown with its time and error, and claims neither "current" nor "update available" until a later check succeeds.

Updates use the retained outbox above with one coalesced entry, so writes held back by a rate limit or outage are replaced by the latest status, which is written once when GitHub allows it. A missing category or a permission or validation error is logged once as a permanent `dashboard-error`, and dashboard updates stop until the controller restarts; the dashboard never affects Discussion work. If you delete the dashboard Discussion, restart the controller to recreate it.

## Checkpoints and manual recovery

### Model capacity recovery

After an accepted turn completes with Codex's structured `serverOverloaded` category, the controller saves a recovery intent with the failed turn, exact selected model and reasoning effort, attempt count and next due time. It waits 120 seconds before starting a continuation in that same session. A restart during the wait preserves the due time and selection. Repository defaults or Discussion label changes do not substitute a model for this continuation. Intermediate Codex errors with `willRetry: true` leave retries to Codex; they never start a competing controller turn.

The continuation instructs the agent to inspect its conversation history, current workspace and external effects, including replies, commits and pull requests, then finish only what remains. It does not resend the accepted request. Partial work can already have happened before the capacity failure: this inspection reduces duplicate effects but cannot provide exactly-once external actions. Keep the controller's session data so history remains available.

Each further confirmed terminal capacity failure schedules another full two-minute wait, without an attempt limit or a promise that capacity returns within any deadline. Later Discussion input stays ordered behind the recovery and gets no EYES until accepted. Recovery itself creates no new EYES receipt for the original input. Waiting recovery releases the active-session slot so other Discussions can progress, but keeps `/status` busy. Status and the dashboard show `recovering`, reason `model-capacity`, attempts and next retry time; an active continuation also reports `running: true` and counts against the active-session limit. The dashboard title identifies current model capacity recovery until a successful turn clears it; historical failure evidence remains.

Recovery uses normal session, credential, active-session-limit and managed-checkout admission. Graceful shutdown starts no recovery turn and preserves a scheduled wait for restart. Account quota exhaustion, rate limits, cancellation, unrelated terminal failures, runtime loss and uncorrelated completions do not schedule capacity recovery. There is no automatic model fallback.

If a recovery turn encounters an unrelated failure, loses its runtime, or has an uncertain request acknowledgement, the intent remains visible as held rather than automatically repeating work. Inspect the failure and prior work, restore credentials or establish checkout safety as required, then use an explicit Discussion follow-up to finish remaining work. An uncertain managed checkout continues to require the existing offline recovery procedure; a follow-up cannot bypass that fence. GitHub receipt failures alone never cause accepted input to be replayed.

The typed mapping is verified against the pinned [Codex 0.165.0 error schema](https://github.com/openai/codex/blob/rust-v0.165.0/codex-rs/app-server-protocol/schema/typescript/v2/CodexErrorInfo.ts) and [event mapping](https://github.com/openai/codex/blob/rust-v0.165.0/codex-rs/app-server/src/bespoke_event_handling.rs). The existing Aspire/pinned-tool smoke path owns live adapter and history compatibility; source inspection and core tests do not establish an observed production overload or live recovery.

### Broker token throttling

A broker HTTP 429 is temporary throttling, not confirmed credential rejection. Token acquisition shares one retry schedule across controller callers. A valid `Retry-After` delta or UTC HTTP date sets the earliest retry; absent, invalid or elapsed values use a 30-second exponential backoff up to five minutes, with zero to five seconds of jitter. Retries do not bypass broker issuance or settlement limits.

While renewal is throttled, an existing token remains available only until 30 seconds before its expiry, and a token rejected by GitHub is never used as fallback. A timer ends broker authority at that safety cutoff even if the retry time is later or no new token request arrives. Owned agent work then stops through the existing authority-loss path; retained recovery evidence stays intact. Invalid leases, definitive denials and other broker acquisition failures retain their existing fail-closed behavior.

Startup has no token to fall back to: it waits and retries on the same paced schedule until acquisition succeeds or the operator cancels. It does not initialize the receiver or admit agent work without credentials. This avoids turning a temporary 429 into rapid controller/tunnel restarts. Authentication status reports `degraded` with the next retry time during throttling and returns to `healthy` after successful acquisition; the dashboard describes automatic retries without claiming that credentials were rejected.

The broker also attempts [bounded pressure relief](../service/auth/retained-state.md#renewal-pressure-relief-and-rejection-diagnostics) for known expired issuance attempts before normal renewal reaches its outstanding-token ceiling. Unknown attempts remain charged; increasing limits is not a recovery procedure. Optional broker monitoring distinguishes request throttles, minute budgets and retained/outstanding capacity denials without publishing caller identities. These changes mitigate reproducible failure mechanisms from issue #269; they do not identify the historical production rejection or establish deployed recovery.

### Managed checkout startup recovery

An interrupted native admission or pending delivery can leave the shared managed checkout unsafe to refresh. The controller retains that evidence, serves `GET /status` as busy with `admissionBlocked: true`, and reports `refresh-blocked` in status and the dashboard. Discussion observation and controller-owned GitHub writes continue; new agent turns and credential-driven runtime restarts wait. Deleting a Discussion does not prove its agent tools have stopped and cannot remove the block.

For a readable, exactly bound journal with no interrupted checkout apply, including legacy generic blocks from an earlier crash loop, stop the controller, its agent runtime **and every agent-launched tool or process that can still access the checkout**. Then run the controller executable offline against the same mounted state and workspace:

```sh
RepoAgentController recover-checkout --state /state/bridge.json --workspace /workspace --confirm-runtime-stopped
```

The flag is your explicit attestation that all that activity has stopped. The command takes both normal leases and verifies the retained checkout binding using local Git; it starts no agent runtime and uses no network. It preserves the original Discussion state and refresh journal, including unknown fields, privately under `PATH.checkout-evidence/`, marks interrupted input for the existing ordered retry/redelivery, then clears the fence. This settles current quiescence; it does not prove the original block's cause or that past work completed. It does not mark input processed or add EYES receipts. Restart with the existing configuration; a normal authoritative checkout refresh still precedes admission. Input may already have executed or a stopped turn's output may have been lost; duplicate work remains possible.

Recovery refuses missing journals, unreadable or foreign evidence, interrupted checkout applies/reloads, unsafe paths and active lease holders. Retain the old workspace, ownership records, state, evidence snapshots and agent session history together; use an isolated fresh approved instance when recovery is refused. Do not edit private files or delete the journal to force admission. Evidence snapshots are retained until the operator deliberately disposes of them with the associated old state; ordinary log rotation does not remove them.

One JSON file holds the repository/bot binding, session IDs and last accepted content/reaction versions. An adjacent `.lock` file prevents concurrent writers for that state file; keep one bridge per repository/App. A private adjacent `.github-app` directory holds isolated `gh` configuration and command wrappers. Short-lived GitHub tokens stay in process memory and reach authenticated child commands through a local credential handoff; they are not written to this directory. Persist this directory with the state volume and keep it out of source control. Signing keys and tokens are never stored in the conversation checkpoint. Use a fresh state file when switching from a user identity to an App; the bridge rejects a mismatched identity instead of silently replaying or migrating old conversations. Codex retains conversation history itself.

Observed changes wait in the Discussion record's `waiting.inputs`, in order and with their authors and receipt source; recording them advances the source checkpoint. The bridge never adds input to a running turn. It dispatches only when Codex reports that Discussion's session `idle`, or `systemError` after a failed turn: pinned Codex keeps that status until the session's next turn and accepts that turn, so no restart is needed. While a turn is active, or while status is unknown, changes wait and get no EYES (`input-waiting`). A restarted agent runtime process first resumes the session and uses its reported status. Each dispatch starts one new agent turn with the next ordered batch: at most 256 KiB of envelope, or one larger change sent alone, never dropped. The rest waits for the next idle report. Dispatch also waits while the [active-session limit](repository-settings.md#active-session-limit) is reached: `REPOAGENT_MAX_ACTIVE_SESSIONS`, default 4 running agent turns per controller. Idle stored sessions do not count. The first (bootstrap) envelope carries the Discussion and its existing comments once. Its context holds at most 128 KiB of existing comments, the earliest first; when a long Discussion has more, `context.laterComments` counts them and their changes carry their bodies, splitting into later batches like other input, so no envelope reaches the agent input limit. Later envelopes name the Discussion once and carry only each change's subject ID, author, new or edited body, changed Discussion fields or reaction actor, and reply target; unchanged Discussion and parent bodies are left for the agent's history or `gh`. A checkpointed comment or reply missing from a complete observation is reported once as `comment.deleted`, with its ID, author and thread but no body or EYES; any failed page fails the whole observation, so the checkpoint stays and nothing is inferred deleted.

Before creating a session or sending a batch the bridge persists `pending`, including its `inputs` count. Only native acknowledgement removes those inputs and clears the marker. A failed or unacknowledged delivery does not stop the Discussion. This covers a native error, the 60-second native request deadline, transport loss, and a stop or crash before acknowledgement. The batch stays first in line, `waiting.retry` records the attempt, and a `delivery-retry` line names the sources and the reason. The next attempt waits for an idle session and a backoff of 5 seconds, doubling to 5 minutes, with no attempt limit; a `pending` left by a stopped controller is retried at the next start. Input that a `turn/start` carried is marked `redelivery` in `waiting.inputs`, because Codex may have accepted it without acknowledging. It is sent again in a batch of its own, with `_bridge.redelivery: true` in the envelope. The agent checks its history and the target thread before repeating work. Duplicate processing is accepted: the bridge does not search transcripts or promise exactly-once input. In clone mode, an unacknowledged input keeps the managed checkout excluded until an acknowledged turn of that session completes. Failed or uncertain input receives no EYES until a delivery of it is acknowledged. After acceptance the bridge checkpoints **before** queuing or reusing EYES on every source in that batch. Controller-owned GitHub writes, currently EYES receipts and [dashboard](#discussion-status-dashboard) updates, are retained in the adjacent `.outbox` file until they succeed or fail permanently, including across restarts; retrying them never resends accepted input. Transient failures back off from 15 seconds to 15 minutes. Rate limits (`Retry-After`, an exhausted `X-RateLimit-Remaining` until `X-RateLimit-Reset`, or GraphQL `RATE_LIMITED`) pause every retained operation until GitHub's signalled time, or at least one minute. A 5xx, timeout or other unconfirmed outcome is reconciled by reading the App's actual reaction before writing again. Permissions, validation and missing subjects (HTTP 400/403/404/410/422 or GraphQL `FORBIDDEN`/`NOT_FOUND`/`UNPROCESSABLE`) are logged as permanent `receipt-error` lines with the source URL and subject ID, then removed from retry. A later operation for the same subject supersedes a still-pending one. `--once` attempts due operations once and exits nonzero while any remain retained. Receipts are excluded from wake triggers; agent replies still use the authenticated `gh` wrapper.

Input the native keeps refusing keeps retrying at the longest backoff and holds that Discussion's later input; other Discussions continue. Examples are a session ID that Codex no longer knows, or a single change above its input limit. Inspect the `delivery-retry` reason and the agent session (`codex resume SESSION_ID`, using the same Codex profile). To abandon such input, stop the bridge and back up the state. Then remove the offending entries from the front of `waiting.inputs`, or remove the Discussion record to enroll it again. In clone mode the refresh journal still blocks a restart after an interrupted or unacknowledged native admission; see [managed checkout recovery](local-installation.md#own-app-mode-and-acceptance). Exactly-once input or publication is not guaranteed.

See [manual verification](manual-verification.md) for the acceptance gate.

## Containerized authentication checks

```sh
docker build -f tests/Containerfile -t repoagent-controller-tests .

```

These focused xUnit tests exercise real RSA signing, private credential files and child-command dispatch with controlled HTTP responses/time.
