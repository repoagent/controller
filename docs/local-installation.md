# Guided PowerShell local installation

Use PowerShell 7.4 or later and Docker Desktop with Linux containers (or Docker on Linux). The supported controller image uses Ubuntu 26.04, linux/amd64. Host `gh` must already be authenticated for direct repository Agent-variable writes. Supply a trusted broker HTTPS origin and an existing Codex `auth.json`, or explicitly request container device sign-in. This workflow does not install or approve the shared GitHub App on your behalf; the selected repository must already have a compatible App installation.

Preview first, then run the same selection with `-Apply`:

```powershell
.\install.ps1 -Repository owner/repo -BrokerOrigin https://broker.example.org `
    -Instance repo-one -Clone -CodexAuthPath "$HOME/.codex/auth.json" -NonInteractive

.\install.ps1 -Repository owner/repo -BrokerOrigin https://broker.example.org `
    -Instance repo-one -Clone -CodexAuthPath "$HOME/.codex/auth.json" -NonInteractive -Apply
```

Without `-Apply`, the command only reads inputs and inspects available Docker metadata. It creates no host files, volumes, containers, approval markers or enrollments, and pulls/builds no images. It shows the repository, trusted broker, App/profile/approval-variable location and name, image and tool choices, instance mounts and retained data. A fresh installation/device is explicitly pending until enrollment. Download/build time and size depend on caches and selected tools/base; the preview cannot estimate them reliably. Source and ABI build validation still run through the existing image composer during Apply.

Complete inputs never prompt or open a browser. Interactive runs prompt for missing required values; `-NonInteractive` fails with the missing option. `-NoStart` still configures and checks the runtime, then leaves it stopped. With `-Clone`, guided shared-App setup derives `polling-clone` for polling or `webhook-clone` for `fixed-url`/`quick-tunnel`; an explicit profile must match. Fixed URL requires `-PublicUrl https://your-listener.example`. Omit `-Clone` for ordinary polling without repository context. During a fresh interactive run that already prompts for missing required inputs, one optional context question defaults to No. Complete inputs, explicit Clone choices, noninteractive runs and saved instances never receive that question.

## Saved choices and recovery

`-Instance` selects `repoagent-INSTANCE` and its named volumes. Its default comes from `REPOAGENT_INSTANCE`, then `default`; use separate names for separate controllers. The host state defaults to `$HOME/.repoagent/instances/INSTANCE`. Override that exact directory with `-StateDirectory`; keep using the same directory to resume. Paths must be local and privately owned; links and unsafe access are refused rather than repaired. Missing directories are created privately only on Apply.

The separate `launch.json` contains nonsecret choices: instance/repository, broker/variable/profile, selected input paths and hashes, immutable runtime image ID, model and runtime options. It contains no token, credential contents, approval marker or recovery secret. The existing enrollment client owns `approval.json`, `recovery.json` and the frozen private `enrollment.json`; retain them together. Only the frozen enrollment is imported privately into the runtime; the launch record and recovery journal stay on the host.

Explicit arguments override saved launch choices, then defaults apply. Changing an existing repository, broker, authentication mode, App binding or image inputs requires a fresh instance. A conflicting enrollment coordinate is refused, never replaced or automatically approved. Fresh installs use setup v4 and `REPOAGENT_APPROVAL` in a direct repository Agent variable; `-ApprovalVariable NAME` changes the name. Saved v2/v3 state keeps its original setup version, custom name and location for recovery and revocation. `-ApprovalLocation AgentVariable` selects fresh v4; ActionsVariable is only for saved v3 recovery or revocation. No GitHub Environment or inherited organization variable is involved.

Apply delegates creation/recovery to the [controller enrollment client](host-enrollment.md), then uses the [private runtime commands](local-runtime.md) to configure, import, check and start. A pending/failed enrollment stops before runtime setup. A later build/import/login/check/start failure retains the same enrollment and instance data. Retry the original command, or use the printed instance/state resume command; do not delete recovery files to force a new identity. Matching retries reuse the saved approval and immutable image, without new approval writes. Expired, withdrawn, conflicting or unverifiable authority requires inspection; the installer does not restore it.

Stop a running instance before applying configuration. The installer never stops/removes it automatically. Config, credentials, workspace, history, state and retained tools storage persist in selected named volumes; broker enrollment is a seventh volume, mounted read-only for runtime authorization. No host home or Docker socket is mounted. Runtime tokens never receive the host's approval authority.

## Codex sign-in and image choices

The installer detects `CODEX_HOME/auth.json`, then `$HOME/.codex/auth.json`; `-CodexAuthPath` overrides detection and saved paths. It imports only that file, leaving host config/history/sign-in unchanged. Existing container credentials are retained on reruns unless an explicit `-CodexAuthPath` requests a new import. `-DeviceLogin -Apply` explicitly enables interactive device sign-in using the existing runtime login flow; it cannot be combined with `-NonInteractive`. A host OS-keyring-only sign-in cannot be copied as `auth.json`.

The default `image/default.json` selects reviewed Codex, gh and optional tools on the maintained base. Use `-ImageManifest PATH` for a custom digest-pinned `baseImage.reference` or other supported manifest choices; explicit selection wins over defaults. Custom bases must satisfy the existing Ubuntu 26.04/linux-amd64 compatibility checks. Named OpenAI universal/.NET presets remain gated by issue #46. No host Python installation is required.

`-DerivedDockerfile` and `-BuildArg` retain the existing image builder API. Build argument values are forwarded explicitly but not stored in launch state or printed by the installer; resupply them if a failed build must be retried. Keep credentials out of image/build inputs. To reuse an already-built controller image, set `REPOAGENT_IMAGE` and pass `-SkipBuild`. Once resolved, the immutable SHA256 image ID is saved and reused even if a tag moves. Local setup performs no registry write. Publishing uses `scripts/publish-image.ps1`. Hosting lifecycle is outside the controller ([ADR 0009](adr/0009-keep-hosting-lifecycle-out-of-the-controller.md)); hosted operation will be redesigned around the status endpoint.

## Own-App mode and acceptance

Existing PEM users can select `-Authentication OwnApp`; explicit `-AppId`/`-KeyPath` also select it on a fresh instance. Own-App setup now follows the same preview/Apply gate. It keeps existing polling, fixed-URL and quick-tunnel options, PEM readability checks and image customization API. It needs no host `gh`. For example:

```powershell
.\install.ps1 -Authentication OwnApp -Repository owner/repo -AppId 123 `
    -KeyPath C:\Private\app.pem -CodexAuthPath "$HOME/.codex/auth.json" `
    -Instance own-app -NonInteractive -Apply
```

`-Clone` adds Contents read alongside Discussions write and, for webhook modes, repository hooks write. Broker setup uses fresh clone approval and enrollment; ordinary/v1 approval and older launch records cannot be upgraded by changing a flag. Choose a new instance and state directory for new approval. The selection persists across retries in both Broker and Own-App modes.

`-RepositorySettings` lets the controller read [repository settings](repository-settings.md). In Broker mode it selects the matching repository-settings profile (for example `polling-clone-settings` with `-Clone -Mode polling`), which adds only `agent_variables: read` under policy `repository-agent-settings-approval-v4` and fresh setup-v4 Agent-variable approval. In Own-App mode the runtime token also requests Agent variables read, which the App installation must grant. Like `-Clone`, the choice is fixed for an instance: adding or removing it on a saved instance stops before any change. To switch, revoke, establish settlement and owner release, then enroll a new instance; see [migration and rollback](repository-settings.md#broker-enrollments).

> [!WARNING]
> Repository Agent variables must never hold secrets. A controller that reads repository settings, and so the agent it runs, can read every direct repository Agent variable, including approval. GitHub also gives Agent variables to Copilot cloud agent sessions ([ADR 0012](adr/0012-use-repository-agent-variables-for-settings-and-approval.md)).

The controller authenticates repository identity and its actual default branch, then clones into the persistent `/workspace/repository` root before starting native Codex. It trusts exactly that root in its private Codex configuration, allowing repository instructions, project configuration and local skills to load. Other settings, trust entries, sign-in and history are preserved. Review the repository context before approving this choice. Startup and periodic polling check the approved default branch. At an idle boundary, the controller fetches through its renewable App identity and forces the checkout to the verified commit, including rewritten or force-pushed history, then restarts native Codex and reloads project instructions and skills. Existing Discussion sessions resume with their native history on their next input. No-context installations retain their existing workspace behavior.

The refresh journal sits beside the bridge state as `<state-path>.refresh.json`. Admission is recorded before creating or resuming a session and remains active until both the bridge checkpoint and the correlated agent turn completion are recorded. Refresh waits for all sessions to be idle; acceptance, timeout and process exit do not count as completion. A busy repository is checked again after completion. Clone webhook mode also requests refresh on signed pushes to the recorded default branch; HTTP202 confirms a durable request, not that the checkout has advanced. Polling supplies the fallback.

The managed checkout is disposable. The idle refresh discards local edits, untracked files, local commits, branch switches, hidden index flags and interrupted merges inside `/workspace/repository`, then checks out the verified commit on the default branch. It does so when the default branch moves, and also when it has not moved but the checkout no longer matches it (`checkout-refreshed ... restored=local-changes`). The refresh runs at startup and at each idle poll or reconcile interval; durable webhook mode refreshes on startup and push deliveries. Ignored files that do not collide with tracked paths, nested repositories, other local branches and separate worktrees are kept. Put historical checkouts, bisects, edits and temporary artifacts in separate worktrees or directories outside the managed checkout. An interrupted rebase, `am`, cherry-pick or revert sequence, bisect, or a Git lock file leaves refresh pending and stops a restart until inspected. Assistance can continue while the checkout identity and native activity remain known. Restart accepts local state in the owned checkout, which the startup refresh then discards, but still refuses unrelated, replaced or incomplete checkouts under the ownership checks.

A native delivery the running controller cannot confirm does not block: it is redelivered, and refresh waits until an acknowledged turn of that session completes. Interrupted admission, ambiguous native events, journal failure or an interrupted apply/reload block new admissions. Stop the controller and its native process before manual recovery. Preserve the checkout, ownership record, bridge state, refresh journal and private native history together; inspect the recorded operation and commit before deciding how to recover. Do not delete the journal to force idle or retry an uncertain input. If completion or applied state cannot be established, retain those files and configure a fresh approved instance. Older instances with sessions but no lifecycle journal also require this inspection.

Choose a fresh instance when changing credential mode; existing storage is not silently adopted or relabeled. Existing Own-App Docker settings without a host launch record require explicit inputs for the first guided run, because preview does not launch a container to retrieve settings. `-Action Enroll` and `-Action Revoke` retain their independent host command behavior.

A successful command reports either verified/stopped or local runtime readiness. Native Windows PowerShell with actual Docker Desktop, a real authenticated Codex turn/history, live Agent-variable host-write/broker-read/exact-runtime-permissions (including the installation's accepted `agent_variables: read`), private-repository availability and hosted/Azure/signing recovery remain separate acceptance gates. Settings tokens can read approval but cannot write it; frozen tokens have no variables access. See [installation acceptance and the #249 settlement-preflight limitation](host-enrollment.md#verification-boundary). Process fixtures and source merge do not establish those outcomes.
