# GitHub identity options for the Discussion–agent bridge

Checked against current primary documentation on 2026-10-19. This is research and a proposed integration approach: no App was registered, credentials changed, or authenticated App smoke test run.

A **GitHub App installation identity** is the strongest alternative to a machine user: it provides a separate bot actor without another licensed user seat, while preserving `gh api graphql` as the agent’s interface. The added work is token refresh at the boundary where each `gh` process starts. This recommendation is an inference from the documented authentication mechanisms and the current PoC architecture.

## Current implementation baseline

The [completed PoC's acceptance record](https://github.com/egil/gh-discussion-agent-bridge/issues/2#issuecomment-6277950749) reports a working journey using human GitHub identities. It does not establish App-token compatibility. This research recommends a follow-up identity change; it does not rewrite the completed ticket's acceptance contract.

Code was inspected at commit `f42c85913f1c75af89cd2f8f6be188c6f51b0206`: [GitHub.cs](https://github.com/egil/gh-discussion-agent-bridge/blob/f42c85913f1c75af89cd2f8f6be188c6f51b0206/src/DiscussionBridge/GitHub.cs) launches `gh` through `PATH` for each GraphQL request, verifies `viewer.login` against the configured agent login, and checks `viewerHasReacted` before adding EYES. [Bridge.cs](https://github.com/egil/gh-discussion-agent-bridge/blob/f42c85913f1c75af89cd2f8f6be188c6f51b0206/src/DiscussionBridge/Bridge.cs) uses that login for own-activity filtering and a literal mention pattern. [Codex.cs](https://github.com/egil/gh-discussion-agent-bridge/blob/f42c85913f1c75af89cd2f8f6be188c6f51b0206/src/DiscussionBridge/Codex.cs) launches a persistent native app-server process. These existing seams support the wrapper proposal without adding another agent framework; configure the App's actual bot login and verify the native shell resolves the same wrapper.

## Identity and seat comparison

| Option | Actor and access | Fit for this bridge |
| --- | --- | --- |
| GitHub App installation token | App bot, conventionally `<slug>[bot]`; installation-scoped permissions and repositories. | Recommended separate automation identity. GitHub explicitly documents that installation tokens do not consume licensed seats. [App/OAuth comparison](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps), [installation token advantages](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys#github-app-installation-access-tokens). |
| GitHub App **user** token | Acts on behalf of an authorizing person, with activity attributed to that person. | Suitable when human attribution is intentional; using an existing person requires no new account, but does not provide a separate bot actor. It is a different authentication mode from installation identity. [App/OAuth comparison](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps). |
| Dedicated machine user + PAT | A normal personal account reserved for automation. | Simple long-lived credential and familiar user identity, but account access can consume a paid organization seat. GitHub treats machine users as personal accounts, not App bots. [App/OAuth comparison](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps). |
| Existing human PAT or OAuth login | The existing user; token access depends on that user’s access and granted scopes/permissions. | Fastest experiment without another account. Replies and reactions carry human attribution, and access remains tied to that human. GitHub recommends Apps for long-lived integrations. [PAT documentation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [OAuth comparison](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps). |
| Actions `GITHUB_TOKEN` | GitHub Actions’ repository installation identity. | Useful inside a workflow, where GitHub supplies the token. Repository-scoped and job-bound, with a runner-dependent maximum lifetime; it is not a general credential service for the existing external daemon. Adopting it would change the runtime architecture. [GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token). |
| SSH deploy key | SSH access attached directly to one repository. | Can support Git checkout/push, but cannot authenticate Discussions GraphQL requests. It does not replace the bridge’s API identity. [Deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys#deploy-keys). |

Do not state that every machine-user account necessarily adds a charge. For GitHub Team, organization members and outside collaborators on private repositories consume seats. Enterprise Cloud also counts outside collaborators on internal repositories, while public-repository outside collaborators are excluded. Consequently, changing a bot from member to outside collaborator does not avoid the private-repository seat requirement. A new PAT on an already licensed person does not itself create another user. [License accounting](https://docs.github.com/en/billing/reference/github-license-users).

Fine-grained PATs target one resource owner. GitHub currently lists outside-collaborator repository access among their limitations, so a machine-user outside-collaborator design may require a classic PAT rather than the expected fine-grained token. [PAT limitations](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens-limitations).

These are **seat** conclusions. They do not establish that all Apps, hosting, Actions usage, or Marketplace products are free. A public App registration can optionally have a Marketplace listing; neither public visibility nor installation-token authentication implies a paid Marketplace subscription. No undocumented App registration fee or complete operating-cost claim is assumed here. [App visibility](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private).

## Ownership and minimum installation setup

An App registration’s visibility is independent of repository visibility. A private App owned by a personal account can only be installed on that personal account; a private organization-owned App can only be installed on that organization. Personal membership or ownership of an organization does not merge these accounts. To use **one registration** on both a personal account and an organization, make that App public and install it separately on each account, choosing repositories at installation. Public registration does not make installed private repositories public, and does not require publishing to Marketplace. Alternatively, keep separate private registrations for each owner. [Visibility and installation rules](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private).

For the documented installation flow, keep the App ID, its PEM private key, and the target installation ID. The App signs a JWT and exchanges it at `POST /app/installations/{installation_id}/access_tokens`; the installation ID can also be discovered using App-authenticated API calls. A private key alone is insufficient. No user PAT or OAuth client-secret flow is required for this path. Tokens expire after one hour, support REST and GraphQL, and can be narrowed to installed repositories and granted permissions. [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

For the next identity step, propose **Discussions: read/write**, plus implicit Metadata read, on the chosen repository; this is a starting permission set, not a verified result. GitHub’s Discussions guide explicitly supports GitHub Apps. Its classic `repo`/`public_repo` scope wording should not be read as requiring those scopes on an installation token. GitHub instructs developers to test the exact GraphQL queries and mutations against App permissions. [Discussions guide](https://docs.github.com/en/graphql/guides/using-the-graphql-api-for-discussions), [choosing permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).

An App does **not** require switching the bridge to webhooks or hosting an inbound endpoint: registration explicitly allows webhooks to be inactive for an authentication-only App. Keep the current polling approach. [App registration](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app).

GitHub's separate “agent apps” preview is Copilot-powered delegation from issues, pull requests and the Agents UI. It is not required to use an ordinary GitHub App as this bridge's API identity. [Agent apps overview](https://docs.github.com/en/apps/using-github-apps/about-using-github-apps#agent-apps).

## Refresh without a custom agent framework

**Documented:** `gh` accepts `GH_TOKEN`, ahead of `GITHUB_TOKEN` and stored credentials. The value is a credential, not a token-provider command. Updating stored login credentials will not override a still-set `GH_TOKEN`. [CLI environment](https://cli.github.com/manual/gh_help_environment).

**Process-model consequence:** a native agent started with `GH_TOKEN=token_A` retains that environment value. Replacing the bridge’s token later does not rewrite the running agent’s environment. Its future shell children can therefore inherit expired `token_A`. Starting with a fresh token only postpones this failure.

Two lightweight integration designs follow; neither has been tested in this runtime:

1. **Bridge-owned refresh and a small `gh` wrapper.** The bridge caches a token and its returned expiry, refreshes with a safety margin, and passes the current token explicitly whenever it launches `gh`. For agent-launched commands, put a wrapper named `gh` first on the agent’s `PATH`. On every invocation, it reads the current token from an access-restricted file, overrides inherited `GH_TOKEN`, and executes the real CLI by absolute path. Replace the file atomically, keep the App private key with the bridge, and fail closed if no usable token exists. In a container, mount the credential directory so file replacement is visible.
2. **On-demand credential helper.** The wrapper requests a current token from a small local helper/socket owned by the bridge. The helper caches and refreshes tokens; agents receive installation tokens rather than the signing key. GitHub’s Octokit SDK already handles token generation and regeneration for its own requests; an exported token still needs this handoff to each separate `gh` process. [Octokit installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation#using-the-octokitjs-sdk-to-authenticate-as-an-app-installation).

The file-and-wrapper design is the smaller PoC change. Polling, native sessions, and `gh api graphql` can remain. Ensure the agent actually resolves the wrapper; a direct call to the underlying CLI bypasses refresh. Refresh failures must not silently fall back to a developer’s stored login.

## Remaining compatibility check

With configuration authorized, verify one Discussion post, top-level comment and reply; EYES reactions on both Discussion and comment; actor filtering and `viewerHasReacted`; then leave the same native session idle beyond one hour and publish again through refreshed credentials. Exercise a refresh failure and verify there is no human-credential fallback.

The reviewed official sources establish App bot identity, but do not settle custom-App `@mention` autocomplete or notification behavior. Do not claim Apps categorically cannot be mentioned. The existing bridge matches a literal mention of the configured agent login in fetched text and accepts a supplied Discussion URL; it does not need a native mention notification. For an App, first test that exact bot-login spelling. A shorter independent alias would be an optional future change. Both native mention UX and the exact permission/refresh integration remain unverified.
