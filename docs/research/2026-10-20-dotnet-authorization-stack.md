# Minimal .NET credential-broker stack

Research date: 2026-10-20. Research only: production implementation remains paused. This note proposes a stack; it does not amend the [ADR](../adr/0001-keep-the-shared-app-key-out-of-controller-installations.md) or [frozen v1 consumer contract](../broker-protocol.md). No service has been deployed or acceptance-tested.

## Recommendation

Use one small ASP.NET Core service: built-in OAuth client middleware, cookies, antiforgery, authorization policies, a durable enrollment store, a typed GitHub HTTP client, and Microsoft's JWT and Azure Key Vault libraries. The broker is an OAuth **client** of GitHub; it need not become a general OAuth/OIDC authorization server. The controller receives a repository-bound installation token and keeps the shared App bot identity. The application-specific work is enrollment authorization, binding, persistence, and revocation.

Target the separate service at **.NET 10 LTS**, independently of the controller's .NET 11 RC target. Microsoft's current support-policy table lists 10.0.13, released 2026-10-13, with .NET 10 support through November 2028. Use the current serviced patch when implementation resumes; do not pin a research snapshot indefinitely. [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

## Browser login and explicit approval

ASP.NET Core's generic `AddOAuth` can use GitHub's authorization and token endpoints, with `AddCookie` for the broker's browser session. No Identity user/password database is necessary just to use cookies. Enable `UsePkce = true` explicitly: its default is false. GitHub App web authorization supports S256 PKCE. Keep the OAuth client secret in the broker. [Cookie authentication without Identity](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0), [UsePkce](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.oauth.oauthoptions.usepkce?view=aspnetcore-10.0), [GitHub App user authorization](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)

Generic OAuth middleware handles correlation, protected state, code exchange and PKCE, but its default ticket creation starts with an empty user object. Configure `OnCreatingTicket` to fetch `https://api.github.com/user` with the returned access token and map stable numeric `id` and display `login` claims; set GitHub's required request headers. Merely setting `UserInformationEndpoint` does not implement that fetch. The first-party generic handler is sufficient with this small provider-specific integration. `SaveTokens` is unnecessary if human credentials are needed only during enrollment; avoid putting them in the browser ticket. [OAuthHandler source](https://raw.githubusercontent.com/dotnet/aspnetcore/main/src/Security/Authentication/OAuth/src/OAuthHandler.cs)

Recommended application flow, derived from the repository's contract:

1. Installer creates a pending enrollment and receives an expiring poll credential plus browser URL.
2. Browser authenticates directly with the trusted broker and GitHub. Broker loads the pending request and independently resolves repository, installation, App and requested fixed permission profile.
3. Broker verifies the authenticated human's repository-admin authority with GitHub. Its approval page displays the exact device, immutable repository ID, installation, and permissions. Explicit approval is an antiforgery-protected POST. OAuth callback success or possession of the poll credential cannot approve it.
4. Broker commits approval atomically, issues the random device credential, and permits only the bound installer to collect it. Expired unacknowledged completion revokes the unclaimed device.

ASP.NET authorization policies and antiforgery supply mechanisms for these checks; the GitHub-specific requirements and the pending-enrollment state machine are application code. This preserves the trusted-browser approval gate (R3). OAuth middleware does not provide machine pairing or repository authorization. [Policy authorization](https://learn.microsoft.com/en-us/aspnet/core/security/authorization/policies?view=aspnetcore-10.0), [Antiforgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0), [local provider gates](../broker-protocol.md#provider-and-hosted-release-gates)

## Scope checks and human credential retention

For issuance, request exactly the enrolled `repository_ids` and explicit `permissions` from `POST /app/installations/{installation_id}/access_tokens`. Omitting either broadens the default grant. GitHub limits these grants to what the installation/App already holds, but that is not a substitute for the broker's own approved binding. Validate actual returned scope and installation state before releasing credentials. Tokens expire after one hour. Treat them as opaque: GitHub documents a newer variable-length format rolling out in 2026. [GitHub App endpoints](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)

**Human refresh credentials are not inherently required for continuous admin checks.** GitHub's collaborator-permission endpoint accepts installation tokens with `metadata:read` and returns both `permission` and the user's numeric ID. The broker can query the enrolled approver using a strictly repository-scoped installation credential, require `permission == admin`, and compare returned `user.id` to the stored approving ID. Never trust a reused login alone. Missing access, mismatched IDs and unavailable checks fail closed. This is a proposed composition of the documented endpoint, not a tested end-to-end result. [Get repository permissions for a user](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user)

Define the grant's lifetime deliberately. Recommended starting policy: active enrollment plus current installation/repository/permission grants and current approving-admin authority are required on renewal. This supports discarding the human token after approval. It **does not** detect withdrawal of that human's OAuth authorization, and an alternative policy where enrollment survives the approving person's departure would need an explicitly recorded administrator-managed grant. These are product decisions; middleware cannot choose them.

If ongoing user-token authorization is required instead, retain encrypted human access/refresh credentials only at the broker and implement refresh/revocation handling. GitHub's expiring user access token lasts eight hours and refresh token six months; refresh replaces both. Passing the documented `repository_id` further narrows eligible user tokens, but GitHub can ignore an inaccessible selector, so inspect actual access. Generic `AddOAuth` does not automatically maintain this durable refresh lifecycle. [Refreshing GitHub user tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens), [User token parameters](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)

## Device API authentication

Preserve v1's random `deviceSecret` bearer credential. A small `AuthenticationHandler<TOptions>` can parse it, find the device, compare a stored digest, and establish the device principal; authorization separately checks active status and immutable binding. Generate at least 32 cryptographically random bytes, store a SHA-256 digest rather than plaintext, and compare fixed-length digests with `CryptographicOperations.FixedTimeEquals`. This proposal uses framework primitives for a high-entropy API credential, not password hashing or a custom OAuth server. [AuthenticationHandler](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.authenticationhandler-1?view=aspnetcore-10.0), [RandomNumberGenerator](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator.getbytes?view=net-10.0), [FixedTimeEquals](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.cryptographicoperations.fixedtimeequals?view=net-10.0)

`AddBearerToken`/Identity API tokens are a different protected-ticket format, with an access/refresh lifecycle. They do not directly validate the existing random enrollment secret or supply repository policy. Adding Identity endpoints would change the contract without eliminating its authorization work. [Microsoft Identity API documentation](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/security/authentication/identity-api-authorization.md)

## JWT signing without exporting the App PEM at runtime

Use Microsoft's `Microsoft.IdentityModel.JsonWebTokens` and `Microsoft.IdentityModel.Tokens`, rather than handwritten JWT encoding/signatures. `JsonWebTokenHandler.CreateToken` accepts signing credentials. GitHub requires RS256, an App/client issuer ID, issued-at time, and an expiration no more than ten minutes ahead; it recommends backdating issued-at by 60 seconds for clock drift. [Microsoft IdentityModel](https://raw.githubusercontent.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/dev/README.md), [CreateToken source](https://raw.githubusercontent.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/dev/src/Microsoft.IdentityModel.JsonWebTokens/JsonWebTokenHandler.CreateToken.cs), [GitHub JWT requirements](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)

The existing Azure SDK provides the desired RSA adapter:

```csharp
// Proposed composition; not executed or production-validated in this research.
using RSA rsa = await cryptographyClient.CreateRSAAsync(cancellationToken);
var key = new RsaSecurityKey(rsa);
var signing = new SigningCredentials(key, SecurityAlgorithms.RsaSha256);
```

`CreateRSA`/`CreateRSAAsync` obtains the public key. `RSAKeyVault.SignHash` calls `CryptographyClient.Sign`, allowing remote signing while keeping private material in Key Vault. Use a versioned key identifier and managed identity with key-read and sign authorization; deployment/import permissions belong to provisioning, not the broker runtime. The needed operations are public-key retrieval and remote signing, not reading the PEM as a secret. [CreateRSA API](https://azuresdkdocs.z19.web.core.windows.net/dotnet/Azure.Security.KeyVault.Keys/4.7.0/api/Azure.Security.KeyVault.Keys.Cryptography/Azure.Security.KeyVault.Keys.Cryptography.CryptographyClient.html), [RSAKeyVault source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/main/sdk/keyvault/Azure.Security.KeyVault.Keys/src/Cryptography/RSAKeyVault.cs), [Key operations](https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys-details)

Source inspection supports compatibility: IdentityModel uses the supplied RSA instance; its modern span path calls `TrySignData`. The base RSA implementation reaches the overridden `SignHash`. A failed private-key export yields `PrivateKeyStatus.Unknown`, which the signature provider accepts (it rejects `DoesNotExist`). Thus a handwritten `KeyVaultSignatureProvider` is not justified at this point. [IdentityModel RSA adapter](https://raw.githubusercontent.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/dev/src/Microsoft.IdentityModel.Tokens/AsymmetricAdapter.cs), [RSA base implementation](https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/RSA.cs), [RsaSecurityKey](https://raw.githubusercontent.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/dev/src/Microsoft.IdentityModel.Tokens/RsaSecurityKey.cs), [Signature provider](https://raw.githubusercontent.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/dev/src/Microsoft.IdentityModel.Tokens/AsymmetricSignatureProvider.cs)

**Local compatibility check completed:** .NET 10.0.13, Azure.Security.KeyVault.Keys 4.10.2 and Microsoft.IdentityModel.JsonWebTokens 8.23.0 successfully composed the real SDK RSA wrapper and JWT library against a fixture Key Vault HTTP transport. Two RS256 tokens validated with a separate public key; private export failed; one public-key read and two remote-sign requests were observed. See the [exact versions, method and limits](2026-10-20-dotnet-key-vault-signing-check.md).

**Remaining live gates:** real Key Vault managed identity/minimum permissions, real signing and GitHub acceptance, version rotation, production timeout behavior, and provider disposal/cache lifetime. Signing through `RSA` is synchronous even after asynchronous initialization. The local check establishes library compatibility, not deployed compatibility.

## API client and remaining release gates

A typed `HttpClient` with `System.Text.Json` is a reasonable small dependency surface for identity, permission/install checks and token issuance. Do not sell the entire broker as only three HTTP endpoints: approval, lookup, scope validation and revocation add calls. Official Octokit.NET is also suitable if its typed API coverage is useful; it does not replace application authorization or prove remote-Key-Vault signing integration. [Official GitHub libraries](https://docs.github.com/en/rest/using-the-rest-api/libraries-for-the-rest-api), [Octokit.NET](https://github.com/octokit/octokit.net)

Durable transactional storage remains necessary for pending approvals, approved bindings, secret hashes, revoked state, and issued-token accounting. Revoking a device stops future renewal; it does not invalidate a copied GitHub token. GitHub exposes `DELETE /installation/token` using the token being revoked. Every token issued for internal checks also belongs in the accounting. Mint/response-loss races can leave tokens unknown to the broker; ownership transfer must wait for expiry plus uncertainty unless revocation is confirmed. Cached-token fencing (R4), draining old controller children, and hosted acceptance remain separate release gates. [GitHub token revocation](https://docs.github.com/en/rest/apps/installations#revoke-an-installation-access-token), [local lifecycle contract](../broker-protocol.md#provider-and-hosted-release-gates)
