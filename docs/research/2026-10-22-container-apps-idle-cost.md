# Azure Container Apps controller: idle-cost research

Research date: 2026-10-22. Scope is vendor documentation and the public Azure Retail Prices API only. It does **not** inspect, modify, or recommend deleting the deployed resources. Prices below are public pay-as-you-go **USD** retail rates returned for `swedencentral` on that date, not a quote, invoice, negotiated rate, tax-inclusive price, or EUR conversion.

## Decision summary

A one-container-app controller can have near-zero **Container Apps compute** cost when it truly reaches zero replicas, but it is not correct to describe the whole deployment as free while unused. The present persistent costs are most likely the provisioned Azure Files NFS share and, if separately billable/user-owned, static public IP and load-balancing configuration. A `minReplicas: 1` controller also never reaches zero: it is billed at least at the idle replica rate when it meets the service's tight idle criteria.

The cost-minimal viable shape is:

| Count | Resource | Why it is the minimum |
|---:|---|---|
| 1 | ACA workload-profiles environment using its Consumption profile, default managed network | One public HTTP endpoint and a scale-to-zero host; no dedicated profile, private endpoint, custom ingress, user VNet, NSG, public IP, or user load balancer solely for this shape. |
| 1 | External HTTP Container App, `minReplicas: 0`, `maxReplicas: 1` | One controller process, awakened by an HTTP webhook. `max: 1` limits desired replicas within a revision; rollout/maintenance can still overlap replicas, so the state lease remains required. |
| 0 or 1 | Storage | Prefer none if controller state can be rebuilt from the authoritative remote system. If a shared filesystem is genuinely required, choose the least expensive storage that satisfies the actual POSIX/locking test; NFS deliberately changes the networking and cost floor. |
| 0 | Log Analytics workspace | ACA can use `none` as its log destination. This trades away retained diagnostic evidence; it does not remove live log streaming. |
| 0 | Key Vault and user-assigned managed identity | Omit only if there is no long-lived secret to distribute. Container Apps native secrets can hold an app-level secret, but Microsoft advises Key Vault references rather than literal production secret values. |
| 0 | Smoke job when it has no actual idle work | A manual ACA job has no running replica between executions; a scheduled/always-running alternative does not share that property. |

This is an architecture inference from the facts cited below, not a statement that every controller can safely be stateless. It is deliberately a *single* app rather than a platform of always-on supporting resources.

## ACA consumption, zero replicas, and long-lived work

### What is free at zero—and what is not

* Consumption bills allocated replica vCPU-seconds and GiB-seconds, plus external HTTP requests. The subscription monthly grants are 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million requests. When a revision is at zero replicas, it incurs **no resource-consumption charge**. [Azure Container Apps billing](https://learn.microsoft.com/en-us/azure/container-apps/billing#consumption-plan)
* A public HTTP price meter is still a possible usage cost: only requests from outside the ACA environment are billable, though health-probe requests are not. Therefore “zero replicas” is not synonymous with “no request charges” after the grant. [Billing](https://learn.microsoft.com/en-us/azure/container-apps/billing#request-charges)
* The public Retail Prices API returned, for Sweden Central and USD on the research date, active vCPU `$0.000024/second`, active memory `$0.000003/GiB-second`, idle vCPU `$0.000003/second`, idle memory `$0.000003/GiB-second`, and `$0.40/million` standard requests. These are reproducible public observations from [the Azure Retail Prices API query](https://prices.azure.com/api/retail/prices?%24filter=serviceName%20eq%20%27Azure%20Container%20Apps%27%20and%20armRegionName%20eq%20%27swedencentral%27&currencyCode=%27USD%27), not a promise of what a particular subscription pays. [Retail Prices API overview](https://learn.microsoft.com/en-us/rest/api/cost-management/retail-prices/azure-retail-prices)
* A revision with `minReplicas > 0` is eligible for reduced idle charging only when it is at its minimum, every container is running, it processes no HTTP requests, uses under 0.01 vCPU, and receives under 1,000 bytes/sec network traffic. Otherwise active charges apply. Thus a controller holding a connection, polling, sending heartbeats, or doing background work must not be budgeted as idle. [Billing: minimum replicas](https://learn.microsoft.com/en-us/azure/container-apps/billing#minimum-number-of-replicas-are-running)
* Consumption supports scale-to-zero; Dedicated billing is by allocated workload-profile instances and an environment with one or more Dedicated profiles has a Dedicated plan-management fee. A Consumption-only environment/app should not acquire such a fee merely because the environment exists, but private endpoints and planned maintenance are separately subject to the documented Dedicated Plan Management charge. [Billing: Dedicated plan](https://learn.microsoft.com/en-us/azure/container-apps/billing#dedicated-plan); [compute structure](https://learn.microsoft.com/en-us/azure/container-apps/structure#plans)

### HTTP webhook controller: practical limits

* HTTP scaling evaluates concurrency every 15 seconds and can use `minReplicas: 0`; without ingress and without either a minimum or custom scale rule, an app can scale to zero with no mechanism to wake again. [ACA scaling](https://learn.microsoft.com/en-us/azure/container-apps/scale-app#http); [default scale rule](https://learn.microsoft.com/en-us/azure/container-apps/scale-app#default-scale-rule)
* The first request after scale-to-zero triggers a cold start, which includes image pull, resource provisioning, and application startup. Webhook callers must tolerate this with an acknowledgement/retry/idempotency design; do not treat a synchronous response as guaranteed rapid delivery. [Cold starts](https://learn.microsoft.com/en-us/azure/container-apps/cold-start)
* Default HTTP ingress supports WebSocket and gRPC but documents a 240-second request timeout. It is unsuitable as the sole mechanism for an unbounded synchronous coding session. Persist work/lease state and return promptly, then resume through a later webhook or an explicitly designed event source. [ACA ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview#http)
* An open/active session also defeats the premise of a zero-idle controller: it needs a running replica and can keep it in the active billing category. A background daemon that must continuously poll or retain an interactive connection needs `minReplicas: 1` (or another wake mechanism), and is a deliberate recurring cost.
* A manual ACA job is appropriate only as a smoke operation: Consumption jobs are billed at active rates while an execution runs; idle rates do not apply because completed executions stop consuming resources. [Billing: jobs](https://learn.microsoft.com/en-us/azure/container-apps/billing#jobs)

## Storage: the current NFS floor versus SMB standard

### Current NFS design

The supplied deployed state is a 32-GiB SSD LRS Provisioned v2 NFS Azure Files share with 3,000 IOPS and 100 MiB/s. Those are exactly the documented SSD Provisioned v2 minima: 32 GiB, 3,000 IOPS, and 100 MiB/s. [Understand Azure Files billing](https://learn.microsoft.com/en-us/azure/storage/files/understanding-billing#provisioned-v2-model)

Provisioned v2 charges the **provisioned** storage, IOPS, and throughput meters hourly, regardless of whether the controller is active. That makes it a true idle cost floor. [Provisioned v2 billing meters](https://learn.microsoft.com/en-us/azure/storage/files/understanding-billing#provisioned-v2-billing-meters)

The public Sweden Central USD API returned SSD LRS Provisioned v2 storage `$0.000196/GiB-hour`, with separate free SSD LRS provisioned-IOPS and provisioned-throughput meters. The [official Azure Files pricing table](https://azure.microsoft.com/en-us/pricing/details/storage/files/) explicitly includes the first3,000IOPS and100MiB/s at no additional charge; the meter names alone would not establish the free allowance. At 32 GiB and 730 hours this makes the observable storage-meter estimate `$4.58/month`; it excludes snapshots, soft-deleted usage, transactions/data transfer where applicable, tax, and any commercial discount. This is arithmetic over the API observation, not an Azure quote. [Retail query for Azure Files](https://prices.azure.com/api/retail/prices?%24filter=serviceName%20eq%20%27Storage%27%20and%20armRegionName%20eq%20%27swedencentral%27%20and%20contains%28productName%2C%20%27Files%27%29&currencyCode=%27USD%27); [Azure Files billing model](https://learn.microsoft.com/en-us/azure/storage/files/understanding-billing#provisioned-v2-billing-meters)

NFS is not a zero-networking-cost convenience option:

* Azure Files NFS requires SSD; its authentication is host/network based rather than identity based, and it provides POSIX permissions. NFS cannot use an HDD standard share. [Azure Files planning](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning#available-protocols)
* For an ACA NFS mount, the environment **must** use a custom VNet and the storage account must allow that VNet; the NFS mount needs unencrypted NFS and ACA documents NSG allowance for port 2049 (and port 445 if a custom-VNet environment is used). [ACA storage mounts](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts#azure-files-storage)
* NFS has important semantic/security caveats: no user-based authentication or Kerberos/ACLs, and access is controlled with a private endpoint or VNet service endpoint/network rules. Treat the VNet boundary, UID/GID, root-squash choice, and share exposure as security-critical. [NFS security and networking](https://learn.microsoft.com/en-us/azure/storage/files/files-nfs-protocol#authentication-and-network-access)

### Potential cheaper alternative, contingent on tests

An ACA Azure Files mount supports SMB or NFS. SMB can use the standard HDD tier and its pay-as-you-go model, while NFS is SSD-only. The public API observed `Files v2 / Hot LRS / Data Stored` at `$0.0271/GB-month`; 32 GB is about `$0.87/month` before operations and other meters. That is a useful *order-of-magnitude comparison*, not a recommendation or a complete SMB bill. [ACA storage mounts](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts#azure-files-storage); [Azure Files planning: storage tiers](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning#storage-tiers); [Retail query for Azure Files](https://prices.azure.com/api/retail/prices?%24filter=serviceName%20eq%20%27Storage%27%20and%20armRegionName%20eq%20%27swedencentral%27%20and%20contains%28productName%2C%20%27Files%27%29&currencyCode=%27USD%27)

Do **not** substitute SMB merely because it is cheaper without a workload test. Azure describes SMB as Win32 semantics and NFS as POSIX semantics, and a file share cannot be mounted by both protocols. Test the controller's required symlink behaviour, atomic replace/rename, file-locking, UID/GID/permission expectations, concurrent access, and failure/retry behavior from the actual Linux ACA image. [Azure Files protocol comparison](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning#available-protocols); [SMB shares](https://learn.microsoft.com/en-us/azure/storage/files/files-smb-protocol)

## Networking and standalone resources

* ACA’s **default managed network** is public and can communicate with internet-accessible endpoints; an existing/custom VNet is only needed for features such as NSGs, private endpoints, outbound control, or private resources. An external environment itself gets a public-facing virtual IP. Therefore NFS, not basic external HTTP ingress, is the documented reason this controller needs the custom VNet and NSG. [ACA networking](https://learn.microsoft.com/en-us/azure/container-apps/networking#virtual-network-type); [accessibility](https://learn.microsoft.com/en-us/azure/container-apps/networking#accessibility-level)
* No first-party instruction above says an NFS mount requires a separately created public IP or a user-managed Azure Load Balancer. NFS requires the custom VNet/subnet, storage network access, and suitable NSG rules. Whether the existing `managedLB`/PIP are service-managed dependencies, independently billable user resources, or both cannot be determined from documentation alone; use the Cost Management meter/resource dimensions before attributing a bill.
* Public prices still show why this matters: the Retail API observed a Sweden Central `Standard IPv4 Static Public IP` at `$0.005/hour` (about `$3.65` at 730 h) and a Basic static IPv4 at `$0.0036/hour` (about `$2.63`). A public IP can therefore cost while no controller replica runs. [Retail query for Virtual Network meters](https://prices.azure.com/api/retail/prices?%24filter=serviceName%20eq%20%27Virtual%20Network%27%20and%20armRegionName%20eq%20%27swedencentral%27&currencyCode=%27USD%27)
* Standard Load Balancer has no hourly charge when it has no rules; with rules, it has rule-hour and data-processed charges. Do not assume that fact applies to an ACA-managed load balancer or that its rules are absent. [Azure Load Balancer pricing FAQ](https://azure.microsoft.com/en-us/pricing/details/load-balancer/)

## Secrets, identity, and observability

* ACA application secrets can be literal values or Key Vault references. Microsoft explicitly advises against literal production secret values and says a Key Vault reference needs a managed identity and `Key Vault Secrets User` permission. A user-assigned identity is reusable and survives the app lifecycle. [ACA secrets](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets#defining-secrets); [Key Vault reference](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets#reference-secret-from-key-vault)
* A controller does not receive the shared GitHub App private key, but this controller **does** retain a repository-bound enrollment credential and coding-agent sign-in. Those must survive scale-to-zero privately. Native ACA secrets can distribute an enrollment credential without a separate vault/UAMI resource, but replacing the currently approved versioned Key Vault reference is a deliberate secret-lifecycle change, not something to remove simply because the current setup-only app has no identity. Key Vault changes access control and cost. Standard/Premium Key Vault are transaction-billed; do not call either “free when idle” without checking its operation meters. [Azure key management pricing model](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management#pricing)
* Log Analytics is not required by ACA. Environment logs can use `log-analytics`, `azure-monitor`, or `none`; with `none`, log storage is disabled but real-time log streaming remains available. The saving is real, with an operational trade-off during cold-start/mount/webhook failures. [ACA log options](https://learn.microsoft.com/en-us/azure/container-apps/log-options)

## Minimum counts and cost drivers to validate before change

The minimum *persistent* count for the proposed stateless, HTTP-woken controller is one Consumption environment and one app; all of VNet, NSG, NFS FileStorage/Provisioned v2 share, PIP, user LB, Key Vault, UAMI, Log Analytics, and smoke job are conditional rather than inherent requirements. The currently supplied eight-resource set has several valid reasons it could need those resources—especially POSIX NFS—but those reasons should be evidenced before paying for them continuously.

Before any architecture change, answer these non-destructive questions:

1. Is any state irrebuildable and does it truly require a shared POSIX filesystem (rather than the remote system of record)?
2. Does the controller need a continuously held connection, background poller, or synchronous run longer than HTTP's documented timeout? If yes, zero replicas is incompatible with that behavior.
3. Can the GitHub integration use an installation/access token obtained at request time without persisting a private key? If no, retain a proper secret distribution design, preferably Key Vault + managed identity for production as Microsoft advises.
4. Does the storage workload pass explicit symlink, atomic rename, locking, permission, concurrency, and restart tests on a candidate SMB mount? If not, retain NFS and treat its VNet plus provisioned SSD minimum as intentional cost.
5. In Cost Management, which resource/meter actually records the PIP/LB charge? Do not remove service-managed dependencies based on a name alone.

The resource count is conditional, not an instruction to delete:

- A plain stateless public ACA application needs two top-level resources: environment and app.
- This controller needs durable private state/history/account credentials, so a realistic cheaper target includes storage: roughly three top-level resources if standard-network compatible storage and native secret distribution meet the real requirements. Retaining the existing vault/identity makes five but need not create a large fixed idle cost. Storage/share/queue/role child resources are additional declarations, not separate always-on machines.
- Keeping the current POSIX NFS approach means five core resources (app, environment, storage account, VNet, NSG), plus its two Azure-managed network resources; vault/identity add two and the temporary smoke Job adds one. Removing only the last three does not remove the main idle-cost floor.
- VNet/NSG/managed identity are configuration/control resources rather than always-on compute; the expensive dependency is the separately billed managed networking and provisioned storage they enable. A dormant manual Job consumes no replica compute. Key Vault requests are transaction-metered. Do not equate icon count with recurring spend.

Code evidence makes a `minReplicas:0` edit insufficient: `DiscussionWebhooks.Accept` queues the observation in an in-memory Channel and returns202; native Codex work runs after the request ends. `DiscussionWebhooks.Run` finally calls `Registration.Deactivate`, setting the repository webhook inactive during normal shutdown. Scaling down could therefore interrupt a turn and remove the next wake-up trigger. A saved conversation/thread is not a currently executing turn and should not keep compute allocated forever.

The next bounded design must provide durable admission/recovery, a scale signal that remains nonzero while an agent turn is executing, and a distinction between idle scale-down (leave webhook active) and explicit stop/revoke (disable it). It also needs cold-start delivery handling and real Azure acceptance. None of these behaviors are currently claimed. Cheap SMB is a candidate, not a drop-in replacement for NFS: current code validates0700/0600 ownership, symlinks, atomic publication and process leases. An alternative is local ephemeral POSIX working files plus carefully synchronized durable object/state storage, which requires deliberate code changes. No Azure simulator or manual owner reset is appropriate.
