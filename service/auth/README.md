For native C# debugging with Aspire, Azurite and a Key Vault emulator, see [local development](local-development.md).

The [v3 Actions-variable contract](#repository-actions-variable-enrollment-v3) from [#184](https://github.com/repoagent/controller/issues/184) ([ADR 0007](../../docs/adr/0007-use-repository-actions-variables-for-approval.md)) is retired: no shipped installer offers it, and the broker still serves it only so that any v3 row keeps its exact contract until it expires or is revoked. The [v2 Agent-variable contract](#repository-agent-variable-enrollment-v2) from [provider #68](https://github.com/repoagent/controller/issues/68) ([ADR 0006](../../docs/adr/0006-use-repository-agent-variables-for-approval.md)) and legacy v1 GitHub Environment setup stay as explicit kinds. A marker never becomes another approval kind implicitly. Frozen profiles keep their controller enrollment files and runtime routes: v1 for polling/webhook, v2 for explicit clone profiles. Only the explicit [repository-settings profiles](#repository-settings-profiles) use runtime v3 ([ADR 0008](../../docs/adr/0008-add-an-explicit-repository-settings-runtime-profile.md)). Live GitHub/Azure acceptance remains under [#35](https://github.com/repoagent/controller/issues/35) and [#28](https://github.com/repoagent/controller/issues/28).

The repository-variable providers read the selected variable by name, only from the direct location for their kind. Actions grants read `/repos/{owner}/{repo}/actions/variables/{name}` with broker-only `actions_variables:read`. Agent grants read `/repos/{owner}/{repo}/agents/variables/{name}` with `agent_variables:read`. A 404 establishes absence only when a listing page of the same location, read afterwards with the same verifier token, proves access. The number of variables in the repository never limits verification. Organization/inherited fallback, cross-kind fallback and Environment creation/identity are excluded. The host needs GitHub-authorized write access to the selected variable; controller tokens get no approval access. Published App permissions and host CRUD do not prove installation-token scope, private-plan availability or runtime permission separation. Existing quotas, private possession, receipt-before-ack, durable closure, known/unknown accounting and restore/replacement gates remain; see [the approval contract](../../docs/auth-repository-approval.md).

This partial credential broker implements `DELETE /v1/devices/{deviceId}`. A valid enrolled controller secret closes its grant and records a durable receipt without deleting outstanding-token evidence. `204` means future broker issuance is closed; it does not invalidate already issued GitHub tokens. The empty-body `POST /v1/devices/{deviceId}/installation-token` implements the frozen v1 token contract for acknowledged active grants. The enrollment routes below create those grants after independently verifying controller approval. `/health/live` reports process liveness; `/health/ready` returns `200` when valid local startup configuration registers enrollment and issuance, otherwise `503`. Its empty, noncacheable response checks registrations without resolving services or contacting providers. Revoke-only and missing-origin compositions remain live but unready; malformed supplied settings fail startup. Normal Data Protection startup may preload the key ring independently of probes. Readiness does not prove runtime permissions, quotas, upstream availability or recovery.

## HTTP behavior and limits

Send `Authorization: Bearer <deviceSecret>` without a request body or client-selected scope. The frozen v1 grammar permits 43–128 base64url secret characters generated from at least 256 random bits, and 1–128 ASCII base64url device-ID characters. Only SHA-256 hashes of the UTF-8 secret text are persisted; comparison is constant-time.

- `204`: authenticated committed revocation, or a valid authenticated retry with matching closed gate/device and receipt.
- `401`: missing/invalid secret, missing grant, wrong binding/epoch, or expired device (including an expired retry).
- `503`: unavailable, malformed or unresolved durable state, exhausted conflicts, or request timeout. Retry safely with the same controller secret; an ambiguous response may follow a committed revoke.
- `429` with `Retry-After`: request or concurrency budget exhausted before storage access.
- `400`: a DELETE with a body.

Built-in global limits use one fixed partition, without attacker-controlled per-IP/device state or a request queue. They apply to all non-health routes, including future routes. These per-process limits reduce resource/spending risk; they are not a distributed DDoS defense or guaranteed spend cap. Replica, CPU/memory, log-budget and Azure spending controls remain infrastructure acceptance work. Arbitrary forwarded headers are not trusted.

| Variable | Default | Allowed range |
| --- | --- | --- |
| `Broker__RequestLimitPerMinute` | 120 | 1–10,000 |
| `Broker__ConcurrentRequestLimit` | 8 | 1–128 |
| `Broker__RequestTimeoutSeconds` | 15 | 1–60 |

Kestrel caps request bodies at 64 KiB, headers at 16 KiB/64 fields, connections at 128, header arrival at 10 seconds and idle keep-alive at 30 seconds; default minimum data-rate protections remain enabled. Health paths perform no remote work and bypass application budgets. SDK automatic retries are disabled; conflicts get at most four complete authorization evaluations within the request deadline. Cancellation propagates to every SDK call. Request info logs and Azure info logs are suppressed; the service does not log secrets, entities or SDK response/error bodies, nor write audit records for invalid/throttled traffic.

## Durable shape

One dedicated table contains routing hints in `locator:<deviceId>` partitions (row `locator`) and authority under `repository:<immutableNumericGitHubRepositoryId>` partitions. A locator supplies `RepositoryId` and `DeviceId` but never authorizes a request.

| Row | Required properties |
| --- | --- |
| `gate` | `RepositoryId`, `Epoch`, `OwnerDeviceId`, `State` (`active`/`closed`), `Sequence` (nonnegative Int64) |
| `device:<deviceId>` | `RepositoryId`, `DeviceId`, `Epoch`, `SecretHash` (64 hex digits), `ExpiresAt` (DateTimeOffset), `State` (`active`/`revoked`) |
| `revocation:<deviceId>` | `RepositoryId`, `DeviceId`, `Epoch`, `RevokedAt` (DateTimeOffset) |

Revocation conditionally replaces gate and device using both observed ETags, creates one receipt in the same entity-group transaction, and preserves all other properties and attempt rows. A conflict rereads and reevaluates the whole decision. No wildcard updates, upserts, grants recreated on missing data, partition scans or production seed endpoint exist. All writes and reads are capped at 128 properties and 64 KiB of JSON; broker transactions are limited to 32 operations and 1 MiB including a framing allowance. Admission requires preinitialized retained-state metadata and preserves these accounting and partition rules.

## Issuance configuration and boundaries

Issuance is registered when `Auth__SigningKeyUri` is configured. It additionally requires `Auth__DataProtectionKeyUri` (both version-pinned HTTPS Key Vault key IDs), `Auth__DataProtectionBlobUri` (HTTPS key-ring blob, no SAS), and `Auth__DataProtectionApplicationName` (the shared key-ring application discriminator). These are the existing infrastructure outputs. Without signing configuration, token requests return 503 and self-revocation remains available. The server owns App ID 5387625, slug `repo-agent-connector`, and fixed `github.com`/`api.github.com` origins. Neither an App private key nor a human GitHub credential is loaded into this service.

`ManagedIdentityCredential`, `CryptographyClient`, Azure Blob Data Protection storage and Key Vault key wrapping provide the production boundaries. Signing, Table, Blob and wrapping SDK clients disable retries and use three-second network timeouts. GitHub redirects, cookies and automatic POST retries are disabled. GitHub bodies are bounded at 64 KiB and calls at three seconds. Signing uses a persisted reservation's fixed `iat=reserved−60s` and `exp=reserved+120s`; a delayed worker never refreshes either claim.

The request has a 15-second issuance deadline and eight GitHub reads. Each of the two fresh observations uses the repository's App installation lookup and the verifier's exact accessible-repository listing. Legacy grants then verify Environment identity and its variable; v3 grants read the selected direct Actions variable and v2 grants the selected direct GitHub Agent variable by name, both described below. Release checks both observations from their oldest read start against ten seconds. No positive observation is cached. Before any GitHub observation, a definite global or repository admission ETag conflict permits a full fresh authority/quota evaluation, with at most four admission evaluations shared by verifier and runtime acquisition. The original operation ID and JWT timestamps remain fixed; a committed global precharge is reused, while a definitively rolled-back global charge is freshly evaluated. Changed binding/state, exhausted budgets and unknown outcomes deny. Post-observation conflicts deny rather than reusing stale observations; no mint is replayed. These checks do not make GitHub and Table atomic or establish continuous approval history. An isolated 404 denies without declaring withdrawal. A successfully read changed identity/value closes the grant monotonically.

The legacy verifier profile is exactly `environments:read` and `actions:read`; the v2 and v4 Agent-variable verifier is exactly `agent_variables:read`; the v3 Actions-variable verifier is exactly `actions_variables:read`. Each allows only implicit `metadata:read`. A verifier token is never returned, never renews device activity and can be acquired internally without an active runtime grant. Its encrypted durable credential is reused until five minutes before actual expiry. A reserved/sending/unverifiable acquisition blocks subsequent acquisition indefinitely. Runtime profiles remain exactly polling `discussions:write` or webhook plus `repository_hooks:write`; actual returned permissions and repository scope must match.

A successful runtime release also records a bounded device pointer to that protected lease and its original expiry. A fresh authenticated request can reuse it until the five-minute expiry margin, after two fresh approval observations and conditional gate/device/attempt/verifier checks. Reuse charges admission, eight reads and one signing operation, but no mint, outstanding capability, retained row or global slot. It never extends the token or payload clocks; ambiguous or unpublished authority denies. Historical devices without the pointer use ordinary issuance and cleanup.

A single `global:issuance-v1` partition precharges fixed UTC minute counters and one of 128 fixed slot keys before the repository transaction. Per-minute admission/read/sign/mint limits are 120/600/20/20 globally and 12/60/2/2 per repository. Optional `Broker__Issuance__{Repository|Global}{Admissions|Reads|Signs|Mints|Attempts}` settings may only lower the corresponding reviewed ceiling; no new setting is required. A runtime reservation conservatively precharges all eight reads; a verifier reservation charges its own admission/sign/mint. Repository capacity is eight combined attempts, including existing gate accounting. The global precharge and repository commit are separate transactions; failed or unknown second commits retain global slot and work charges until explicit fenced settlement; no timeout compensation exists. Enrollment applies the same work budgets plus 4 pending/repository, 64/global, and an absolute 15-minute deadline.

Every repository authority change conditions the common gate, device and relevant attempt ETags. A persisted send claim precedes exactly one POST; restart never replays it. Known tokens are protected under repository, epoch, operation and purpose before release. Revoke-first prevents release; release-first remains accounted even if its response is delayed. Client disconnect after the send claim does not cancel server-owned completion. Failed known-token operations conditionally fence unpublished runtime authority before attempting one DELETE; an already committed runtime release is preserved. Other failed known-token operations attempt one DELETE and durable settlement under an additional bounded six-second finalization allowance; failed finalization preserves evidence. Only a committed authorized runtime release advances 90-day inactivity.

The per-allocation capacity reclamation facade releases proved outstanding and pending occupancy using repository settlement obligations followed by exact global charge release; see [retained state](retained-state.md#outstanding-and-pending-capacity-release). A later invocation physically retires eligible resolved issuance and new never-minted, never-completed enrollments using durable deletion proof before refunding retained credits. Completed, mint-started and unversioned enrollment publication credits remain charged for manual recovery. Fixed-window charges are never refunded. An unresolved mint, lost commit response or orphan global slot does not age out. At saturation the service denies; explicit operator reconciliation may be required. Neither JWT expiry nor changing the restore epoch settles a previously unknown token. Public enrollment remains a source-level integration surface; sustained hosted availability requires cleanup and live provider acceptance.

## Legacy Environment approval marker encoding

`ApprovalMarker.Create` defines the compact canonical JSON v1 marker, in this property order:

```json
{"version":1,"githubHost":"github.com","appId":5387625,"appSlug":"repo-agent-connector","repositoryId":123456,"repository":"owner/project","installationId":789,"deviceId":"DEVICE_ID","challenge":"43_CHARACTER_BASE64URL_CHALLENGE_FROM_32_BYTES","profile":"polling","policyVersion":"repository-approval-v1","epoch":"DEPLOYMENT_EPOCH","environment":"approval/environment","environmentId":987,"variable":"APPROVAL"}
```

The example identifiers/challenge are explanatory placeholders. Enrollment must generate a fresh 32-byte challenge, use unpadded base64url (43 characters), and generate the marker with this canonical serializer. The pending identity becomes the enrollment ID; both the environment name and numeric ID are bound. The controller secret is separate and never included. The operator preview may pretty-print these fields, but the written variable value is the exact compact string. This encoding does not change the frozen consumer enrollment or token-response schemas.

Before any issuance, the service recomputes the marker from authoritative durable fields and rejects a stored marker that disagrees. It then compares the independently fetched GitHub value exactly. Copying either the public marker or enrollment ID cannot authenticate a caller. The host revoke tool continues to fingerprint the exact decoded value; it need not parse the marker.

## Legacy Environment repository-held enrollment API

Enrollment is registered only with issuance configured and an explicit `Broker__BrokerOrigin`, a canonical HTTPS DNS origin without path, credentials, query or fragment. This origin is written into the frozen v1 enrollment file; request Host and forwarded headers never select a secret destination. Missing origin leaves enrollment unavailable. Readiness remains 503. The installer integration and live provider acceptance remain separately owned.

The host first creates/reuses the selected GitHub Environment through its own authority, then privately persists a random 32-byte recovery credential and a GUID idempotency ID (32 hexadecimal characters, no separators). Host GitHub credentials never reach this service. All four operations use bearer authorization and no-store responses:

| Operation | Body and success response |
| --- | --- |
| `POST /v1/enrollments` | `idempotencyId`, positive numeric `repositoryId` hint, `repository`, `environment`, `variable`, and `profile` (`polling` or `webhook`); returns `pendingId`, `state`, exact `marker`, `deadline` |
| `GET /v1/enrollments/{pendingId}` | Empty body; recovery bearer; own status only, without provider work |
| `POST /v1/enrollments/{pendingId}/completion` | Empty body; recovery bearer; returns `completionId` and `enrollment` containing precisely the frozen v1 fields |
| `POST /v1/devices/{deviceId}/acknowledgment` | `{ "completionId": "..." }`; bearer is the separate delivered controller secret; returns `{ "state": "active" }` |

Start may return `discovering` after a recovered interrupted operation; only a non-null marker permits host approval. The host writes the exact returned marker, polls completion at intervals of at least five seconds, and atomically persists the owner-only enrollment file before acknowledgment. Pending marker coordinates belong in separate host configuration. Completion may instead return pending status while awaiting approval. Responses never include a verifier credential or an observed third-party variable value. `401` denies possession, `409` denies conflicting binding/ownership, `410` denies expiry/terminal transitions, `429` denies admission, and `503` denies unavailable/unverifiable work. Retry the identical start after response loss; never generate a new idempotency ID to recover it.

The immutable candidate repository ID routes admission but is not authority. The broker reserves cost before App-JWT installation discovery, persists the discovered installation, and claims one exact-ID/read-only verifier POST before sending. Its returned sole numeric ID and original requested repository name must both agree, and an independent authenticated repository listing and Environment numeric identity must agree, before any marker is returned. Name/ID substitution cannot redirect the binding. The marker uses canonical returned repository/Environment names and uppercase variable name. No device or incumbent owner is fabricated for bootstrap.

Global admission atomically records idempotency/body/recovery-digest binding and reserves the candidate's share of both caps. Repository admission then records its gate and pending row. Staged and uncertain starts retain capacity; no cross-partition rollback is claimed. Repeated observations reuse the pending row and share a durable work interval across discovery, completion and acknowledgment. Each provider operation reserves eight reads and a signing call; mint attempts additionally reserve mint and outstanding capacity. A sending/unknown mint never retries automatically. A definitely unsent reservation can resume only within its original signing deadline. No expiry timer erases unresolved authority.

If cleanup positively settles a verifier as unsent before its send claim, the same live authenticated enrollment can allocate a new charged operation. Conditional gate/pending/attempt updates unlink only that proved settlement; the old attempt, audit and JWT clocks stay intact. The pending device/challenge and original 15-minute deadline do not change. Missing capacity/settlement proof, any send claim, other settlement reasons and expired enrollment cannot use this path.

Completion conditions the common gate, pending and verifier attempt plus any existing device; it admits only its exact known, validated internal verifier continuation, never an incumbent, another pending attempt or unknown authority. It stores one encrypted completion and unacknowledged device atomically, then publishes a routing-only locator. Lost responses recover the same identity and envelope only after fresh checks. Runtime authentication rejects unacknowledged devices. Ack freshly checks approval and all original deadlines/barriers, activates once, starts 90-day inactivity and retires recovery authority. Duplicate active ack performs no activity extension. Revocation can close an unacknowledged device, and an expired pending deadline cannot be revived.

Approval reads prove absence through a complete bounded variable listing on the verified Environment; isolated 404, denied access, malformed responses or exhausted page/read bounds deny without claiming absence. Before first positive approval, absence/mismatch stays pending; afterward verified withdrawal closes permanently. Conflicts after observation discard that decision. GitHub/Table atomicity and identical delete/recreate history are not claimed.


## Repository Agent-variable enrollment v2

V2 implements [ADR 0006](../../docs/adr/0006-use-repository-agent-variables-for-approval.md) with a direct repository GitHub Agent variable. The Environment routes above remain legacy v1. The host installer adaptation, independent conformance review and live provider acceptance remain separate gates; readiness remains 503.

Use `POST /v2/enrollments` with exactly `idempotencyId`, positive numeric `repositoryId`, `repository`, `variable` and `profile` (`polling` or `webhook`). Environment fields, arbitrary permissions, duplicate and unknown properties are rejected. `GET /v2/enrollments/{pendingId}`, `POST /v2/enrollments/{pendingId}/completion` and `POST /v2/devices/{deviceId}/acknowledgment` retain the corresponding legacy bodies, credentials, responses and deadlines. Setup/status/completion/ack routes reject a pending grant of the other setup version before provider work. The shared v1 token/revoke routes and the frozen v1 controller enrollment file remain unchanged; runtime provider selection comes from authenticated durable grant state.

New rows persist approval kind, setup version and policy together. Agent grants use `repository-agent-variable`, `2`, `repository-agent-approval-v2`; new legacy rows use `environment-variable`, `1`, `repository-approval-v1`. Historical rows without discriminators remain subject to their complete legacy binding. Partial, unknown or inconsistent discriminators deny access. Pending/device/verifier relationships must agree. V2 request digests and protected payload purposes are domain-separated; legacy digests and protection purposes remain compatible. Both kinds share one admission/idempotency namespace, all quotas and one repository owner gate. Switching versions cannot bypass an incumbent or unresolved authority.

The canonical compact v2 marker has this property order:

```json
{"version":2,"approvalKind":"repository-agent-variable","githubHost":"github.com","appId":5387625,"appSlug":"repo-agent-connector","repositoryId":123456,"repository":"owner/project","installationId":789,"deviceId":"DEVICE_ID","challenge":"43_CHARACTER_BASE64URL_CHALLENGE_FROM_32_BYTES","profile":"polling","policyVersion":"repository-agent-approval-v2","epoch":"DEPLOYMENT_EPOCH","variable":"APPROVAL"}
```

The example is explanatory. The marker contains no secret, Environment identity or invented immutable variable identity. Setup generates a fresh challenge and uppercases the selected variable name. Private recovery is persisted by the host before start; the private device receipt is persisted before fresh acknowledgment. The broker validates the App installation using its App JWT, then verifies the exact numeric repository and original requested name using both the internal mint response and an independent authenticated repository listing before returning approval material. Human host credentials cannot perform the App-JWT lookup and never enter the broker. The host validates repository intent, trusted broker origin, App/profile and returned binding.

The broker requests only `agent_variables:read` for its exact-repository internal verifier; returned scope must match, allowing only implicit metadata read. Known token material is durably protected/accounted before rejection or revocation. Controller polling/webhook scopes exclude approval access. Names or timestamps are not immutable variable identity; no organization or inherited-variable fallback exists.

Each Agent observation reads the selected variable by name from the direct `/repos/{owner}/{repo}/agents/variables/{name}`. GitHub answers with the stored uppercase name; name and value must match exactly. GitHub also answers 404 when the verifier cannot read the location, so a 404 establishes absence only when a well-formed listing page (`?per_page=1`) read afterwards with the same token proves access. Reading that proof after the 404 also catches access lost before or during the named read. The page is only an access proof: its total never matters, and a page that shows the selected name contradicts the 404 and is unverifiable. Installation and repository validation plus at most two variable reads consume at most four reads however many unrelated variables exist, so both runtime observations fit the existing eight-read budget. Freshness starts at the first contributing read. Denied, malformed or contradictory results, a different returned name and an isolated 404 are unverifiable.

A fresh confirmed 404 establishes absence. A selected value read by name establishes presence or mismatch. No retry or snapshot guarantee is inferred. Before first positive approval, confirmed absence/mismatch leaves setup pending; afterward, confirmed withdrawal closes permanently. Restoration cannot reopen a grant. Identical delete/recreate entirely between observations has no continuous-history proof.

Host marker deletion, broker closure and outstanding-token settlement remain distinct outcomes. The accepted host GET/DELETE race may require manual reapproval. All existing accounting, deadlines, ETag gates, exact known-verifier continuation and old-authority barriers remain in force. This slice adds no cleanup, locks, automatic repair or takeover. Live host write/App-installation read/runtime denial and private-repository availability remain acceptance gates; public App metadata and host CRUD alone do not prove them.

## Repository Actions-variable enrollment v3

V3 implements [ADR 0007](../../docs/adr/0007-use-repository-actions-variables-for-approval.md) with a direct repository Actions variable. It reuses the v2 request, response, deadline, recovery, quota, owner-gate and closure rules above and changes only these parts:

- **Routes.** `POST /v3/enrollments`, `GET /v3/enrollments/{pendingId}`, `POST /v3/enrollments/{pendingId}/completion` and `POST /v3/devices/{deviceId}/acknowledgment` take the v2 bodies exactly. Runtime token and self-revocation routes do not change: v1 for `polling`/`webhook`, v2 for `polling-clone`/`webhook-clone`. The repository-settings profiles below use v3.
- **Discriminators.** Rows persist `repository-actions-variable`, setup version `3` and policy `repository-actions-approval-v3`, `repository-actions-clone-approval-v3` or `repository-actions-settings-approval-v3`. Request digests use the separate `repository-actions-variable/setup-v3` domain. The v1, v2 and v3 setup routes each reject the other kinds' pending grants before provider work.
- **Marker.** The compact marker has the v2 property order with `"version":3`, `"approvalKind":"repository-actions-variable"` and the v3 policy. A v2-shaped rendering of the same challenge, or an earlier challenge's marker, is a mismatch.
- **Verifier.** The broker mints its exact-repository internal verifier with only `actions_variables:read`, and returned scope must match. Frozen runtime profiles and their returned runtime tokens carry no `actions_variables`, `agent_variables`, `variables`, `secrets`, `environments` or workflow permission. Repository-settings runtime tokens add only `actions_variables:read`.
- **Observation.** Each observation reads only `/repos/{owner}/{repo}/actions/variables/{name}`, plus the `/repos/{owner}/{repo}/actions/variables?per_page=1` access proof after a 404. Presence, mismatch, confirmed absence, isolated 404/403/malformed denial without closure, and permanent closure after confirmed change or removal follow the Agent rules above. CI workflow and repository-settings variables share this location and never affect verification. GitHub Agent variables, organization variables and Environment variables are never consulted for a v3 grant, and a v2 grant never reads Actions variables.

Agent-variable v2 grants and setup routes stay supported for existing and explicitly selected legacy enrollments. All kinds share one repository owner gate, so a v3 completion returns `409` while another kind's owner is still active or unsettled. Migrate with revoke, settlement and release, then a fresh v3 enrollment; see [the approval contract](../../docs/auth-repository-approval.md#legacy-approvals-migration-and-rollback). The shared App needs Repository permission **Variables: Read** (`actions_variables`), and each installation must accept it before v3 verifier mints can succeed. Until then, completion stays pending or denied and nothing falls back to GitHub Agent variables.

`ActionsVariableEnrollmentTests` and `ActionsVariableMigrationTests.Agent_owner_migrates_to_Actions_approval_only_after_revocation_settlement_and_release` exercise this contract in the core over the in-memory broker state, with GitHub and secret protection replaced at their ports.

### Repository-settings profiles

[ADR 0008](../../docs/adr/0008-add-an-explicit-repository-settings-runtime-profile.md) adds `polling-settings`, `webhook-settings`, `polling-clone-settings` and `webhook-clone-settings` to the v3 setup request. Each issues exactly its frozen counterpart's permissions plus `actions_variables:read`, under the immutable policy `repository-actions-settings-approval-v3`. Setup v4 offers the same profiles with `agent_variables:read` instead (below). The v1 and v2 setup routes refuse these profiles with `400` before provider work.

These grants issue strict controller file/lease v3, which adds the required `profile` and `policyVersion` fields, and use `POST /v3/devices/{deviceId}/installation-token` and `DELETE /v3/devices/{deviceId}`. The route must match the stored family before reservation or mint, and a durable row whose policy, profile or runtime version disagree is denied rather than reinterpreted. The internal verifier stays separate and still requests only `actions_variables:read`. Frozen profiles never request `actions_variables`, and a GitHub response that adds it to their scope is rejected as an invalid scope. Moving a controller to or from these repository-settings profiles follows the revoke, settle, release and fresh enrollment path above. See [the consumer contract](../../docs/broker-protocol.md#explicit-repository-settings-consumer-v3).

`RepositorySettingsProfileTests` and `ActionsVariableMigrationTests.Frozen_Actions_owner_moves_to_the_settings_profile_only_through_revocation_and_fresh_enrollment` exercise these profiles the same way.

## Repository Agent-variable enrollment v4

V4 implements [ADR 0012](../../docs/adr/0012-use-repository-agent-variables-for-settings-and-approval.md): approval in a direct repository Agent variable, by default `REPOAGENT_APPROVAL`, with every profile. It reuses the v2 request, response, deadline, recovery, quota, owner-gate and closure rules and changes only these parts:

- **Routes.** `POST /v4/enrollments`, `GET /v4/enrollments/{pendingId}`, `POST /v4/enrollments/{pendingId}/completion` and `POST /v4/devices/{deviceId}/acknowledgment` take the v2 bodies exactly. There are no v4 runtime routes: `polling`/`webhook` use v1, the clone profiles v2 and the repository-settings profiles v3.
- **Discriminators.** Rows persist `repository-agent-variable`, setup version `4` and policy `repository-agent-approval-v4`, `repository-agent-clone-approval-v4` or `repository-agent-settings-approval-v4`. Request digests use the separate `repository-agent-variable/setup-v4` domain. The v1 to v4 setup routes each reject another setup version's pending grant with `409` before provider work. A broker without v4 denies a v4 row.
- **Names.** A v2 or v4 approval variable may start with `REPOAGENT_` only as `REPOAGENT_APPROVAL`, the name the settings catalogue reserves, because the repository settings share the Agent store. Existing grants are unaffected; this is a setup-time check.
- **Marker.** The compact marker has the v2 property order with `"version":4` and the v4 policy. A v2-shaped rendering of the same challenge is a mismatch.
- **Authority.** The broker derives runtime authority from the durable policy and the profile together, never from the profile name alone. The verifier has exactly `agent_variables:read`. Frozen and clone profiles carry no variables permission. Each repository-settings profile adds exactly `agent_variables:read` to its frozen counterpart, and a GitHub response that adds `actions_variables` is an invalid scope.
- **Observation.** Each observation reads only `/repos/{owner}/{repo}/agents/variables/{name}`, plus its listing access proof after a 404, by the Agent rules above. Actions, organization and Environment variables are never consulted.

Existing v2 grants keep their kind, setup version, policy and runtime authority, and they keep renewing until revoked. All kinds share one repository owner gate, so a v4 completion returns `409` while another owner is active or unsettled. Move with revoke, settlement and release, then a fresh v4 enrollment. The shared App already declares **Agent variables: Read**, so v4 needs no App permission change.

`AgentVariableV4EnrollmentTests`, the setup v4 rows of `RepositorySettingsProfileTests` and `ActionsVariableEnrollmentTests`, and `ActionsVariableMigrationTests.Agent_v2_clone_owner_keeps_renewing_unchanged_and_moves_to_v4_only_after_revocation_settlement_and_release` exercise this contract in the core. `BrokerEndpointsTests` pins the route table.

## Independent cleanup

Run the built service as `dotnet RepoAgent.Auth.dll cleanup --once`. This command branches before HTTP, signing and Data Protection composition. It requires only the existing `Broker__TableEndpoint`, `Broker__TableName`, `Broker__DeploymentEpoch` and optional `Broker__ManagedIdentityClientId`; the table must already have valid retained-state schema. Production uses explicit managed identity, zero SDK retries and a three-second network timeout. It never initializes quotas or repairs accounting.

An expired enrollment that was never acknowledged can recover through this same cleanup lifecycle. After pending capacity and every old token capability are positively settled, cleanup permanently revokes that device and releases its repository ownership under conditional gate/device/pending updates. A fresh enrollment can then use new credentials and approval; the old credential stays denied. Unknown token outcomes, missing proof, epoch conflicts and acknowledged owners still block this recovery. Retained publication/audit credits are preserved. See [the exact recovery and work bounds](retained-state.md#expired-unacknowledged-owner-recovery); active-controller handover remains #34.

An acknowledged owner has a separate release rule: its gate must already be closed, its device revoked, and its matching revocation receipt committed. Cleanup may then release ownership after the same positive pending/capability settlement and full binding checks. Expiry alone or an active gate never qualifies. Original revocation/activity/expiry clocks and audit remain; a fresh enrollment cannot reuse the old credential. [Revoked-owner release](retained-state.md#revoked-acknowledged-owner-release) supplies the broker transition only; native-child shutdown and actual hosted handover remain #34.

For local development only, set `DOTNET_ENVIRONMENT=Development` and explicitly provide `Broker__Cleanup__DevelopmentConnectionString` with standard SDK/Azurite credentials. Set `Broker__TableEndpoint` to the matching HTTP loopback account endpoint, such as `http://127.0.0.1:10002/devstoreaccount1`, and choose the existing table name. The SDK destination must match and contain no user information, query or fragment. Other environments, nonloopback destinations and mismatches reject before requests. Keep the connection string in environment configuration, not command arguments. Ordinary HTTP service startup remains HTTPS/managed-identity only; it never enables this development storage path.

Each invocation has a cooperative 60-second deadline, at most 16 logical query-page calls with 32 entities/page, 128 Azure SDK Table transport dispatches and 32 SDK batch dispatches. SDK failures and bearer-auth reissues count at that boundary; these are not exact HTTP wire-send counts. A conservative 40-dispatch/8-batch allowance is required before each allocation turn, including observations and cursor writes; insufficient remainder stops normally. The SDK retry setting remains zero, but .NET can internally replay a bodyless GET below the SDK counter. Cancellation can leave existing durable proof for the next run; unconfirmed selected cursor/cycle ages are null and no repair I/O occurs after the deadline.

Cleanup Table connectivity is direct only. Its owned standard SocketsHttpHandler disables proxies, redirects, cookies, origin/default proxy credentials and preauthentication. Proxy-required cleanup deployments are unsupported; ensure direct access to the configured Table endpoint. This does not change ordinary HTTP-service transport or globally edit proxy settings. Managed-identity token acquisition retains the credential client's implementation and is outside Table-send accounting.

The summary names are `sdkTableDispatches`, `sdkBatchDispatches` and `logicalQueryPages`. `reviewedHttp11Envelope` reports the explicit reference scope `Azure.Core1.62.0/.NET10.0.13/direct HTTP1.x/no handler authentication`, `maxSendsPerSdkDispatch=4`, and calculated `tableRequestUpperBound`/`batchRequestUpperBound` equal to four times the corresponding SDK dispatch counts. Within that reviewed scope, fixed maxima allow at most 512 Table request sends and a deliberately coarse 128 batch request sends, with batches included in the Table total. These are conservative source-based calculations, never measured wire traffic or runtime-version detection. There is no separate 64-query-wire limit or version-independent, DNS/TCP/TLS, identity or intermediary-work bound. Future SDK/runtime/configuration changes require revalidation; hosted image/runtime acceptance must establish the reviewed scope before using this envelope for cost planning.

One JSON summary reports observed lifecycle counts, SDK dispatch/batch and logical-page usage, incomplete coverage, stop reason and cursor/cycle ages. Exit0 includes a normal budget stop; it does not promise complete traversal or resolution. Exit1 reports storage/protocol failures, exit2 command/configuration errors. `deletedRowsObserved` covers only before-present/after-absent ledger, target and device rows read by this invocation, not every release/receipt/slot deletion. Concurrent observations are not exclusive causal attribution. `oldestObservedOverduePayloadAt` includes observed payload before its attempted cleanup; it is neither a remaining backlog maximum nor a global maximum. Missing trustworthy deadlines are counted separately and empty samples are null.

Schedule successive invocations separately. Temporary auth recovery payloads follow the selected 24-hour eligibility policy, with physical removal on a successful bounded visit afterward and no promised maximum deletion lag. Original clocks and immediate expiry/authorization denial remain unchanged; failures/backlog require monitoring and operator follow-up. See [retained-state cleanup](retained-state.md#independent-bounded-traversal) for continuation/failure behavior and the remaining #35/#28 hosted acceptance.


## Optional aggregate monitoring
