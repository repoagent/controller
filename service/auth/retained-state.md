# Retained broker state

Admission bounds total retained state even when cleanup stops. These limits are separate from per-minute work and outstanding-token limits. Only successful initial acknowledgment or authorized token release extends activity; pending expiry and inactive-device denial still operate before physical cleanup.

## Renewal pressure relief and rejection diagnostics

Before runtime token issuance, an authenticated controller approaching its repository outstanding-attempt ceiling (six of the default eight slots), or encountering full global occupancy, gets one bounded pressure visit. It considers only its repository and current deployment epoch, reading at most eight pages and the 128 fixed global slot records, at most 128 matching attempt records, and reclaiming at most eight positively known expired attempts. The visit shares the original issuance operation's 15-second deadline. Empty continuation pages count against the page budget. An incomplete or conflicting visit may return unavailable; it does not bypass admission or restart its deadline. The controller authenticates its grant again after the visit before continuing.

An exact-scope known token is eligible only at its actual expiry **plus five minutes**. The existing reclamation operation rechecks generation, binding, versions and settlement, commits repository proof before global release, and never compensates an uncertain transaction. A later visit can complete global release from an already committed expiry-settlement proof. Live tokens, unknown outcomes, unpublished reservations and unsent attempts are left for the existing cleanup/recovery paths. Other repositories and historical epochs are not reclaimed by this authenticated request. Scheduled cleanup remains necessary for those allocations, retained-ledger retirement and payload removal; pressure relief neither guarantees provider latency nor prevents retained-capacity exhaustion.

When optional Application Insights monitoring is configured, the HTTP service exports the `repoagent.broker.rejections` counter from meter `RepoAgent.Auth.Rejections`. These metric counts are independent of the one-percent HTTP trace sampling. Its only custom dimension is `reason`, selected from a fixed allowlist: `request_concurrency`, `request_minute`, `repository_attempts`, `global_attempts`, `retained_issuance`, `repository_minute_budget`, `global_minute_budget`, `retained_enrollments`, `candidate_repositories`, `repository_pending`, `global_pending`, `enrollment_backoff`, or `other`. No repository/enrollment identifiers, request URLs, credentials, payloads or provider messages become labels. HTTP response bodies and permission requirements do not change. A monitoring/export failure cannot authorize a request or change a denial; absent telemetry is not proof of no rejection.

Request protection and route denials are counted separately without double-counting: a request rejected by the HTTP limiter never enters a route. In the fixed concurrency/minute chain, only the replenishing minute limiter supplies a `Retry-After` estimate; concurrency rejection has no predictable release time. Core issuance and enrollment decisions retain their typed nonsecret category until the HTTP adapter records it. Counts do not identify individual callers or reconstruct historical sampled-out events.

The controlled in-process renewal and failure tests establish these code paths. Actual Azure metric ingestion, deployed limiter translation, production latency and the initiating StoryBeam rejection in issue #269 remain operational evidence to gather after a separately authorized deployment. Do not hammer the production broker to reproduce exhaustion or infer a historical cause from this mitigation.

| Configuration | Default and maximum | Minimum |
|---|---:|---:|
| `Broker:CandidateRepositoryLimit` | 128 | 1 |
| `Broker:RetainedEnrollmentLimit` | 256 | 1 |
| `Broker:RetainedIssuanceLimit` | 4096 | 1 |

Environment variables replace `:` with `__`. Invalid values fail startup. Lowering a limit does not delete rows or reset accounting; new allocations deny with 429 when their retained capacity is unavailable. Identical enrollment retries use their original reservation. Per-minute and outstanding limits can stop admissions earlier: the current global pending limit is 64 and outstanding-attempt limit is 128.

Candidates include anonymous false repository hints. The lifetime 128-candidate directory can be exhausted without repository authority. This is an explicit pilot availability tradeoff. Candidate directories never retire automatically; eligible allocation retirement below does not provide unlimited enrollment. Manual recovery requires stopping admissions, stopping/fencing old writers, positively settling authority and completing publication/release obligations. JWT expiry, timeout, age and a new deployment epoch do not settle unknown authority.

## Activation

Admission requires `RetentionSchemaVersion` equal to Int64 `1` on **both** existing global quota rows, with complete nonnegative accounting. Missing, malformed or inconsistent metadata denies new admission with 503. Runtime never creates these quota rows, scans a table to infer freshness, resets counters, or enables a legacy admission fallback.

For first deployment, provision a new dedicated table while broker traffic is disabled. A successful table creation, rather than absent metadata in an arbitrary table, establishes freshness. Using administrative Table access, Add these two entities before enabling traffic; every listed numeric value is an Int64:

| PartitionKey | RowKey | Properties |
|---|---|---|
| `global:enrollment-v1` | `quota` | `RetentionSchemaVersion=1`, `CandidateCount=0`, `RetainedEnrollmentCount=0`, `Count=0` |
| `global:issuance-v1` | `quota` | `RetentionSchemaVersion=1`, `RetainedIssuanceCount=0`, `Window=0`, `Admissions=0`, `Reads=0`, `Signs=0`, `Mints=0`, `Slots=0` |

Verify both rows before enabling admissions. Partial initialization remains denied; no cross-partition initialization transaction is needed while traffic is disabled. Service deployment does not itself provision the table or seed entities. No public initialization endpoint exists.

An existing nonempty table requires a complete **offline** inventory with all writers stopped/fenced. Every existing operation and its routing, receipt, gate, quota and outstanding-token rows must be represented by the directory, retained ledgers and counters below before activation. Merely adding zero-valued metadata over old rows is unsupported. This slice provides no migration utility; a newly provisioned table is the simple supported activation path. Existing unactivated revoke-only use is outside this activated-table allocation proof. Table restore, backup retention and Data Protection key-ring retention remain separate operational concerns; restore must stay disabled until old workers and authority are safely handled.

## Allocation proof and writer inventory

| Allocation | Rows per allocation | Covered keys and writers |
|---|---:|---|
| Enrollment, maximum 256 | 8 | Global `pending:<idempotencyId>` ledger and repository pending (`EnrollmentStore.AdmitAsync`); device (`EnrollmentService.CompleteAsync`); `locator:<deviceId>/locator` (`EnrollmentStore.PublishLocatorAsync`); repository `revocation:<deviceId>` (enrollment closure, issuance closure, self-revocation); reserved release, audit and publication-obligation rows. |
| Issuance, maximum 4096 | 4 | Global `operation:<operationId>` ledger and repository `attempt:<operationId>`, created by **both** `EnrollmentStore.ReserveWorkAsync` and `IssuanceStore.ReserveAsync`; reserved release and audit rows. All subsequent send/known/release/revoke observations replace the same attempt. |
| Fixed metadata | 514 currently | 128 global enrollment `repository:<repositoryId>` directory entries; 128 repository gates; 128 repository quotas; 128 global issuance slots; two global quota rows. |
| Fixed cleanup cursors | 2 reserved | Two singleton payload/audit cursors created by the independent cleanup command when absent. |

Total allocation is `256 × 8 + 4096 × 4 + 516 = 18,948` rows. Unused credits remain reserved; they do not permit arbitrary additional row types. A future redaction tombstone occupies its original pending/attempt key, not an extra row. No append-only diagnostic or retry log exists. Non-mint observations update the existing pending row and quota; their transient observation entity is never persisted.

The directory's `PendingCount` replaces dynamically named repository properties on the global enrollment quota. Enrollment admission conditionally updates global quota, directory and new ledger in one EGT. The existing reservation becomes the immutable retained enrollment ledger: its `Generation`, `RowCredits=8`, `CreatedAt`, original `Deadline=CreatedAt+15m`, `PayloadPurgeAt=Deadline+24h`, `PendingId` and `DeviceId` name its allocation. Repository pending copies these values. Device/locator/receipt keys are fixed by that enrollment ID.

Both mint paths generate an operation ID and generation **before** charging. Their global EGT updates rate/outstanding/retained counters and Adds the slot and immutable `operation:<operationId>` ledger. Ledger properties are `OperationId`, `Generation`, `RepositoryId`, `DeviceId`, `Purpose`, `Epoch`, `ReservedAt`, `PayloadPurgeAt=ReservedAt+24h`, `GlobalSlot`, `AttemptRowKey`, `RowCredits=4`, and approval discriminator fields. Enrollment verification additionally includes `PendingId`. Slot and repository attempt carry the same operation/generation, reservation clock and global slot. Definite conflicts can retry within the existing operation budget; ambiguous outcomes remain charged. No work-minute or retained credit is refunded on publication failure or token settlement. Outstanding and pending occupancy can be released only by the protocol below.

All production Table writes go through `BrokerTable`: at most 128 properties and 64 KiB of JSON per entity, at most 32 distinct same-partition actions, at most 1 MiB using twice the serialized row size plus an 8 KiB per-action allowance for OData annotations and multipart framing. Updates require explicit ETags; upserts and wildcard writes are unavailable; conditional Deletes require explicit observed ETags. Existing authorizing transitions still condition the common repository gate and every independently read authority entity. `EnrollmentStore`, `IssuanceStore` and `DeviceRevocation` are the only durable writer modules; `EnrollmentService` creates records committed through `EnrollmentStore`, and all three write through the `IBrokerState` Table adapter, which also goes through `BrokerTable`.

Immutable directory membership and ledger charges retained until fenced physical deletion make the count bound independent of cleanup progress. The bound assumes the dedicated table is written only by these broker paths or an explicitly stopped, complete offline inventory procedure. Administrative arbitrary writes cannot be inferred or repaired by admission.

## Payload redaction

`PayloadRedaction(IBrokerState, TimeProvider)`, in the broker core, operates without signing, Data Protection, provider access or an HTTP host. `RedactEnrollmentAsync(idempotencyId, generation, cancellationToken)` and `RedactIssuanceAsync(operationId, generation, cancellationToken)` process one charged ledger identity. Missing ledgers are no-ops; invalid identities/bindings fail closed. Callers own scheduling, cancellation and later retry of conflicts. There is no scan, route, scheduler or automatic repair in this facade.

Each enrollment redaction call uses at most twelve point reads and two EGTs; issuance uses at most ten point reads and one EGT. Both capture the repository gate before re-reading the current global ledger; retiring or missing ledgers admit no redaction write. The enrollment repository EGT has at most four actions (gate, pending, device, receipt), at most 544 KiB under BrokerTable's conservative maximum-size calculation. The separate global-ledger replacement has one action. Issuance uses two actions, at most 272 KiB. Every independently read repository entity contributing to a write is conditioned on its observed ETag, including unchanged receipt/device observations. Existing gate ownership, epoch, counters and barriers are preserved. Old-epoch payloads are still redacted when due; epoch mismatch with current configuration never settles authority or resets a gate.

The selected policy is 24-hour eligibility, then bounded cleanup of temporary auth recovery payloads. Physical removal occurs on a successful bounded visit after eligibility; no maximum deletion lag is promised. Expiry and authorization denial remain immediate under their existing clocks. Payload clocks never start at a cleanup visit:

* Enrollment global and repository RecoveryHash and repository ProtectedCompletion become eligible for removal at the original pending Deadline+24h, or earlier first-terminal+24h. Successful acknowledgment still removes repository recovery payload immediately. FirstTerminalAt is written once on active acknowledgment/closure; an expired row without it records its original deadline, not cleanup time.
* Attempt ProtectedToken becomes eligible for removal at original ReservedAt+24h / PayloadPurgeAt. First-terminal/provider-expiry clocks can only advance that eligibility. Missing, invalid or sentinel provider expiry uses the reservation fallback; invalid/missing fallback on the ledger or attempt causes immediate redaction on visit and authorization fails closed when the attempt fallback is absent. MaxValue does not gain a new grace interval. FirstTerminalAt is written once on release or positive settlement; SettledAt is written only on positive settlement and is never refreshed by duplicate finalization.
* Active, acknowledged, unexpired device SecretHash is preserved. Expired/revoked hashes become eligible for removal at original committed inactivity expiry+24h or first revocation+24h. Missing expiry, or revoked state without a trustworthy terminal/receipt clock, causes conservative removal on visit. Cleanup never advances LastActivityAt or ExpiresAt. A concurrent authorized release changes the conditioned device/gate ETags and invalidates a stale cleanup decision.

A PayloadRedacted flag records payload retirement without changing existing reserved/sending/known/released/settled authority state. Fresh payload-consuming or payload-creating transitions reject redacted state. A known expired verifier can still be conditionally observed for replacement without restoring its payload. Stale payload writers fail entity/gate ETags. An absent pending/attempt gets a charged redacted tombstone at its exact original charged key; a paused Add then conflicts. Device creation already conditions pending and gate in the same EGT, so it cannot recreate a device after that fence. A missing gate can be added within its existing fixed credit only for an unpublished target; missing gates for existing target state are not repaired.

Enrollment repository fencing commits before global recovery redaction. A cross-partition failure can leave a due global copy for the next invocation, but no credit is released. Repeated completed calls do not write when nothing changes. Scheduling failures and backlog require monitoring and operator follow-up; this module supplies no hosted deletion deadline guarantee.

All allocation identities/generations/credits, routing, original clocks, scope/expiry/settlement evidence, gate barriers/counters, marker reconstruction fields and active duplicate-ack identity survive. In particular Challenge is public marker material; active pending/device CompletionId and all legacy Environment bindings remain. Duplicate active ack still performs no write or inactivity extension. Unknown authority remains charged indefinitely.

Resolved audit history is compacted in place after 30 days: enrollment NextWorkAt, WorkStartedAt and Observation* timestamps, plus global BodyHash after recovery retirement; positively settled attempt SendClaimedAt and ReleasedAt. Resolution uses first enrollment terminal/original expiration or positive SettledAt for attempts. Release alone is not audit resolution. Allocation/JWT/settlement and unresolved safety evidence remain for later reclamation proofs. No audit row is allocated and no safety row is deleted.

Locator publication is still an outstanding charged obligation: ledger DeviceId/PendingId and all eight enrollment credits remain. Cleanup neither reads nor deletes the routing-only locator; its absence does not prove that a paused publisher stopped. A late locator Add stays within its original credit.

## Remaining lifecycle work

Redaction settles no authority. Capacity release and restricted physical retirement are described below. Completed-enrollment publisher cessation remains manual; #72 owns bounded independent invocation, and #35 owns throughput, scheduling, eligibility and zero-HTTP-replica acceptance. There is no unlimited enrollment or hosted cleanup guarantee. Live managed identity/provider/signing, restore acceptance, backup retention and Data Protection key-ring retention remain separate operational concerns.

## Outstanding and pending capacity release

`CapacityReclamation(IBrokerState, deploymentEpoch, TimeProvider)`, in the broker core, provides `ReclaimIssuanceAsync(operationId, generation, cancellationToken)` and `ReclaimEnrollmentAsync(idempotencyId, generation, cancellationToken)`. Each capacity-release call addresses one charged identity, performs at most 13 point reads and two EGTs, and has no scan, provider call, HTTP route, scheduler or implicit retry. Callers retry conflicts on a later invocation. Repository EGTs contain at most four actions (544 KiB under the existing conservative bound); global EGTs contain three. This is source-level invocation, not hosted cleanup acceptance.

The repository transaction first records a generation-bound release obligation and marks/decrements the matching repository charge exactly once. Issuance uses `release:<operationId>` and attempt `CapacityReleased`; pending uses `release:pending:<idempotencyId>` and pending `PendingCapacityReleased`. A runtime attempt also decrements its device count. Only then can the global transaction decrement Slots and conditionally delete the exact slot, or decrement enrollment Count and directory PendingCount, while marking the exact ledger complete. Repository obligations remain charged after completion and survive crashes beyond audit retention. Fixed-window budgets, retained counters, candidate entries and gate epoch are never refunded/reset. Capacity release alone does not reassign ownership; the restricted recovery transition below is separate. Unknown or missing settlement evidence remains charged.

Issuance settlement requires a definitely unsent reserved attempt winning the same gate/attempt ETags as send claim, a persisted successful provider revocation, or a known/released exact-scope token whose original provider expiry plus five minutes has passed. This assumes healthy synchronized broker UTC with no more than five minutes lead over GitHub's effective expiry clock. The five-minute allowance is conservative policy, not a vendor clock SLA or protection against arbitrary clock tampering; unhealthy time requires operator cessation/fencing and manual recovery. GitHub documents the actual expiry in the [mint response](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app); [.NET wall time](https://learn.microsoft.com/en-us/dotnet/standard/datetime/timeprovider-overview) uses the system clock, and [Azure time synchronization](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/time-sync) supports the normal-operation assumption without establishing an App Service numerical SLA. #35 owns actual hosted clock/provider acceptance. Invalid scope/expiry, sending/unknown outcome, JWT expiry, age, redaction and a new epoch never prove token settlement.

Pending occupancy releases after its original deadline, committed closure or acknowledged activation; unresolved token and publication obligations remain. Expired pending is closed under the gate/pending ETags, preventing delayed completion/ack from reviving it. Active completion identity remains. A global-only staged allocation is first fenced with a repository tombstone and release obligation, without decrementing a repository charge that never committed. Only the exact #78 absent-target tombstone shape, with every copied allocation value matching its ledger and no contrary/additional metadata, proves no repository charge. Ambiguous redaction tombstones remain conservatively charged.

Every repository admission evaluation captures its gate before validating the current global reservation; retries never use a fresh gate under an old global decision. Slot occupancy is separate from index: both mint paths choose the lowest absent key within the configured ceiling, then atomically Add that slot with the fresh operation/generation ledger and quota charge. Selection costs at most 128 point reads per evaluation, at most 512 across the existing four-evaluation request budget, with the existing request cancellation/deadline. Repeated lifecycles cannot add slot keys beyond slot:000..127. A stale release cannot delete a reused index because identity/generation and the slot's observed ETag must all match.

The capacity-release invocation deletes only global slot rows. Release obligations consume existing reserved credits: issuance ledger+attempt+release uses three of four; enrollment ledger+pending+device+locator+receipt+release uses six of eight. The 18,948-row bound is unchanged. Retained saturation still denies after outstanding occupancy becomes reusable. Unconditional completion locator publication remains charged and cannot be settled by absence or elapsed time; restricted retained retirement and stale-redactor fencing follow below. Acknowledged-owner handover remains #34 work.

## Expired unacknowledged owner recovery

On a later enrollment visit after global pending-capacity release, cleanup may release an expired owner that was **never acknowledged**. It requires the current epoch; matching ledger, pending, device, completion, repository, installation, profile and approval binding; the original expired deadline; a closed/released pending row and its generation-bound release proof; zero outstanding authority on both gate and device; and no verifier reference. Zero repository authority follows only from the existing positive issuance-settlement protocol. Unknown/sending or unexpired known capabilities continue to block recovery. An acknowledged owner is never released by this rule, even after device expiry.

One four-action repository transaction conditions the gate, pending and device ETags, permanently revokes the old device, creates or updates its existing reserved revocation receipt and makes the gate vacant. The receipt records the release time and reason. First-terminal time uses the original deadline when not already recorded; existing clocks, counters, epoch and retained credits remain. The capacity-release proof cannot retire while this completed enrollment's device/publication evidence exists. The recovery path uses ten point reads and one EGT, within the existing 13-read/two-EGT settlement ceiling. Conflicts and lost responses resume on a later visit; an old worker cannot release a newer owner.

A new enrollment needs a fresh device, private credential and repository approval. The expired credential remains denied; it is never renewed or resurrected. Completed-enrollment ledger/device/locator and audit evidence remain charged under the existing retention rules. This transition does not attest cessation of a delayed locator publisher, refund its credits, reset accounting or provide active-controller handover.


## Revoked acknowledged owner release

After pending-capacity release, the same bounded visit can release an acknowledged owner only when the common gate is already closed and still names that exact revoked device. It requires an existing matching revocation receipt, full current-epoch ledger/pending/device/completion/installation/profile/approval binding, the generation-bound pending release proof, no verifier reference, and positively settled zero gate/device capability counts. The pending row may retain acknowledged `active` completion identity or committed `closed` state. An active gate, expiry alone, missing receipt or incomplete binding cannot authorize this rule; unknown/sending capabilities remain charged and block replacement.

One four-action transaction conditions gate, pending, device and existing receipt ETags, makes the gate vacant, and records `OwnerReleasedAt` with reason `revoked-acknowledged`. It preserves original revocation, device activity/expiry and first-terminal clocks, revoked state, all audit/publication evidence and retained credits. The same ten-point-read/one-EGT path stays within the existing settlement ceiling. Stale workers cannot release a newer owner. This provides broker reassignment after settlement, not proof that native children stopped or that copied bearer capabilities were invalidated by a local cache/replica change; full live handover remains #34.

## Retained allocation retirement

The same two `Reclaim*Async` methods attempt retained retirement only when their ledger already records globally completed capacity release. Settlement and retirement are separate invocations; a settlement call never silently includes the retirement budget. There are no additional public methods, scans, scheduler, HTTP routes or automatic retries. Missing final ledgers are no-ops; storage conflicts propagate for a later caller invocation.

An eligible allocation passes five durable transactions: (1) conditionally mark its global ledger `RetirementState=retiring`, recording its original audit horizon; (2) condition gate, target and completed release obligation, delete the target by observed ETag and replace the existing release row with a bound deletion receipt; (3) conditionally record `repository-deleted` proof on the global ledger; (4) capture gate before revalidating that current proof and conditionally delete the receipt; (5) atomically delete the exact global ledger and decrement only its retained counter. A crash can leave the receipt or global proof for the next invocation. Missing target/release without the corresponding positive durable proof fails closed. Repeated or concurrent workers cannot double refund because ledger/quota/row ETags must match. No permanent per-generation tombstone remains after refund.

Issuance requires its completed global release, bound repository obligation, positive settlement and 30-day audit horizon. Expiry settlement uses validated original provider expiry plus five minutes; positive provider revocation uses original `SettledAt`; definitely-unsent/unpublished settlement uses its first persisted positive settlement time. A later retirement visit never starts a new clock. Missing or ambiguous evidence remains charged. An attempt still required by a live pending enrollment is preserved. Expired/terminal pending observations are conditioned in the deletion EGT. Runtime attempts can retire independently after their own device accounting even when their enrollment's publication credit remains charged. Only an exact matching gate verifier pointer is cleared; owner, epoch, barriers and unrelated pointers survive.

Automatic enrollment retirement is limited to newly allocated `ReclamationVersion=1` rows that never started mint admission and never completed. The version is written only by a new global allocation Add, then copied into its pending/tombstone; publishing an old unversioned allocation does not upgrade it. Mint work claims durably set sticky `MintAdmissionStarted=true` in the gate/pending EGT before any global mint charge. All replacements and redaction preserve it. Retirement requires matching version proof, no mint-started marker, no Attempt or CompletionId, closed and capacity-released pending, and no device, locator or revocation evidence. Its audit horizon comes from original terminal/deadline evidence. Cleanup competes with the work claim on pending/gate ETags: a winning mint claim keeps enrollment charged even if it crashes before recording pending.Attempt.

Completed, mint-started and unversioned enrollments remain charged. Completion locator Add is unconditional across partitions: a delayed publisher can recreate that locator regardless of age, absence, redaction or a newer gate/epoch. Automatic cleanup never deletes completed-enrollment locators or refunds those credits. Manual recovery requires stopping/fencing all old workers and positively inventorying and settling every authority/publication/release obligation; there is no online attestation or reset switch.

The longest retirement path performs **17 point reads**: six routing/schema/directory/gate/current-ledger reads; target plus release (two); three enrollment contrary-evidence probes; four final gate/current-proof/target/receipt reads; two final schema reads. Issuance with a pending reference uses 15, without one 14; resumed phases use no more. The frozen ceiling is 20 reads, five EGTs and four actions per EGT (544 KiB conservative allowance). Global ledger phase updates reuse transaction response ETags; the receipt is re-read before deletion. Settlement retains its separate 13-read/two-EGT bound. There is no per-allocation loop or implicit retry.

The release receipt replaces an existing charged row. Issuance remains at most three of four reserved rows; enrollment remains at most six of eight. Refund occurs only after non-ledger rows have been physically removed under writer fences; the maximum remains **18,948 rows**. Fixed candidate directories, repository gates/quotas, slot namespace, owner metadata and minute counters are never refunded or reset. CandidateCount can validly exceed RetainedEnrollmentCount after retirement; only that former schema relationship is removed. Hard maxima, complete nonnegative metadata, pending/outstanding <= retained and offline fail-closed activation remain.

## Independent bounded traversal

`cleanup --once` enumerates only `global:enrollment-v1` row keys in `[pending:, pending;)` and `global:issuance-v1` row keys in `[operation:, operation;)`. Existing charged ledgers cover each allocation; authoritative facades perform bounded exact directory/repository point reads. There is no whole-table scan, reconstructed accounting, key-ring access or provider call. Payload turns call the existing redaction facade; audit turns call existing capacity release/retirement separately, preserving original clocks and all positive-proof requirements.

The two formerly reserved fixed rows are `global:enrollment-v1/cleanup:payload-v1` and `global:enrollment-v1/cleanup:audit-v1`. They consume exactly the two reserved credits; the 18,948-row bound is unchanged. Each has SchemaVersion, NextFamily and Enrollment/Issuance LastKey, Cycle, StartedAt, ProgressAt, optional CompletedAt. Payload additionally has NextLane. Missing cursors can be conditionally added (a one-row entity group transaction) after valid quota/schema reads; malformed state is not reset. A row whose properties its record does not map exactly (an unknown property, or a value of another EDM type) is malformed: an unreadable cursor or quota fails the invocation before any turn, and any other unreadable row a turn reads fails that turn like a corrupt allocation. Every cursor replacement uses the observed ETag through the bounded BrokerTable transaction facade.

Durable lane/family rotation precedes work. One allocation is evaluated per turn; its last-successful key advances only after a successful authoritative call (including legitimate no-op), bounded observations and conditional checkpoint. A storage error/conflict/cancellation leaves the position unchanged and disables that stream for this invocation. Other streams still progress. A corrupt allocation can pin its own stream indefinitely and needs manual inspection; no growing failure ledger or skip-repair exists. Old cursor age and incomplete coverage expose that limitation. New keys inserted behind a position wait for its next cycle. An empty terminal page resets the key and begins the next cycle; a stream completes at most one traversal cycle per invocation. Completion means traversal, not settlement or absence of concurrent behind-cursor additions.

Azure may return an empty nonterminal page. Only in this case, optional EnrollmentContinuation/IssuanceContinuation fields hold the returned SDK token (maximum8,192 characters each) within the existing lane row. Each token belongs to that row's fixed lane/family, current LastKey, current Cycle and exact partition/prefix/filter; the query and those fields remain unchanged while consuming it. Every empty page consumes a logical query-page call and SDK dispatch, and every token checkpoint consumes a conditional SDK batch dispatch. Internal HTTP replays are covered by the reviewed envelope below. It does not move LastKey or complete the cycle. A successful allocation checkpoint clears that family's token together with LastKey advancement; a terminal-page checkpoint clears it with cycle transition. Failed conditional writes retain the prior durable token/key. No additional rows or authority rules are introduced. Empty pages are tested against the in-memory broker state only; Azure's empty-page behavior remains a separately stated verification limit.

SDK Table dispatches are counted at the transport boundary, including cursor/schema/metric reads, failures and SDK bearer-auth reissues. Limits remain 128 SDK Table dispatches, 32 SDK batch dispatches, 16 logical query-page calls with 32 entities/page and a 60-second cooperative deadline. Normal work admits the whole conservative 40-dispatch/8-batch turn before starting, with unused allowance available for later turns. Existing facade bounds are at most 25 SDK dispatches/5 batch dispatches; the turn additionally covers two cursor reads, two rotation batches, one page call, two pre-observation reads, three post-observation reads and one checkpoint batch (36 dispatches/8 batches before SDK-auth reissue headroom). A defensive hard ceiling reports an invariant failure if unexpected SDK activity exhausts the budget; it cannot split a submitted EGT. Deadline interruption can leave a multi-phase facade incomplete, whose original proof protocol remains resumable. Unconfirmed selected cursor/cycle ages are null on cancellation. No after-deadline or after-exhaustion repair read/write is performed.

The counter does not observe HTTP replays inside .NET. Cleanup uses an owned, disposed standard SocketsHttpHandler with proxies, redirects, cookies, origin/default proxy credentials and preauthentication disabled. Direct Table connectivity is required; proxy-required cleanup deployments are unsupported. Ordinary HTTP-service transport and identity-token acquisition are unchanged. With Azure.Core1.62.0 and .NET11.0.0-rc.3.26522.148 ([exact source revalidation](../../docs/code-quality.md#cleanup-http-request-envelope)), default non-upgrading HTTP1.x requests have at most three connection-failure retries beyond the first send. The summary's `reviewedHttp11Envelope` explicitly identifies that reference scope, reports `maxSendsPerSdkDispatch=4`, and calculates Table/batch upper bounds from `sdkTableDispatches`/`sdkBatchDispatches`. At fixed limits this is at most 512 Table sends and a coarse 128 batch sends, batches included in the total. `logicalQueryPages` is a logical-call count, not a wire count; SDK authentication reissues preclude a separate 64-query-wire claim.

These envelope fields are calculated source-based allowances, not measured wire traffic or proof of the running SDK/runtime version. They do not bound DNS/TCP/TLS, identity, intermediary work or future runtime/configuration variants. Future SDK/runtime/configuration changes require revalidation; hosted acceptance must confirm the reviewed scope before cost planning. The correction does not increase logical work, change clocks/retained capacity, or establish hosted throughput.

Unsettled counts describe observed ledgers whose global release marker is incomplete, including legitimate no-ops; they do not infer settlement from payload age or a changed epoch. Unknown/sending authority remains charged, original purge clocks and30-day resolved audit remain unchanged, and admission backpressure remains effective if scheduling stops. Cursor/metrics writes confer no authorization and refund no capacity.

Restore remains an operator procedure: stop/fence old workers and signing access; positively settle old capabilities and outstanding publication obligations; then supply a fresh external deployment epoch and fresh repository approval before enabling restored service. A runtime issuance request for a consistent stored grant from the previous epoch returns401 after validating its full stored binding and canonical approval marker; missing or inconsistent binding data remains503. This denial does not settle a token, release an owner or retained credit, discharge a publication obligation, or authorize restoring/resetting state. A revocation stored before backup remains a revocation after restore. Cleanup does not reset epochs or enable restore. Backup payload retention and Data Protection key retention are separate policies. Hosted managed identity, scheduling throughput/alerts, eligibility and bounded cleanup with zero HTTP replicas and real backup/restore acceptance remain #35/#28.
